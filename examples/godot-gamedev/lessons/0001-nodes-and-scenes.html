Nodes, Scenes & the Scene Tree

Lesson 1 · Game Development with Godot · ~10 min read
Win: You can explain Godot's composition architecture — why everything is a tree of nodes, how scenes provide reuse, and why this matters for building games.
After this lesson: You understand that every object in a Godot game is a tree of nodes, that scenes are reusable node trees saved to disk, and that composition (combining simple nodes) beats inheritance (deep class hierarchies). You know the lifecycle order and the "signal up, call down" communication rule.

The Core Idea: Everything is a Tree

In Godot, every game object — a character, a bullet, a UI menu, an entire level — is a tree of nodes. A node is a small building block with one job: display a sprite, detect collisions, play audio, run a timer. You build complex behavior by composing simple nodes into trees. [Godot Docs: Nodes and Scenes]

This is fundamentally different from engines where game objects are monolithic classes. In Godot, you don't have a "Player class with sprite, collision, and animation code." You have a tree of small, focused nodes — and that tree is your Player.

Scenes: Reusable Trees

When you save a node tree to disk (as a .tscn file), it becomes a scene. A scene is Godot's version of a prefab or component — a reusable blueprint you can instance anywhere:

  • Save the Player tree as player.tscn → instance it in every level
  • Save a Bullet tree → instance 100 of them during combat
  • Save the entire Level1 as a scene → load/unload it at runtime

Scenes nest inside scenes. Your game's main scene might instance a Level scene, which instances Enemy scenes, which each instance a HealthBar scene. It's composition all the way down. [Godot Docs: Instancing]

Composition over inheritance: Build complex objects by combining simple scenes (Has-A), not by creating deep class hierarchies (Is-A). A character doesn't inherit from Damageable — it has a Health component scene as a child.

The Scene Tree & Lifecycle

The SceneTree is the global tree managing all active nodes. When a node enters the tree, it receives lifecycle callbacks in order:

CallbackWhenUse for
_ready()Node + all children are in tree (once)Get references, connect signals, initialize state
_process(delta)Every rendered frame (~60/s)Visual updates, input, non-physics logic
_physics_process(delta)Every physics tick (fixed 60/s)Movement, collision, deterministic gameplay

The delta parameter is time since last frame in seconds. Always multiply movement by delta — this makes speed consistent regardless of framerate.

Communication: Signal Up, Call Down

Nodes need to talk to each other. Godot has one architectural rule for this:

  • Children signal up: A child emits a signal when something happens. It doesn't know or care who's listening. (Observer pattern)
  • Parents call down: A parent directly calls methods on children it owns. ($ChildName.method())
  • Siblings don't talk directly: An ancestor mediates.

This keeps scenes self-contained. A Health node emits health_changed — anyone can listen. The Player scene doesn't hardcode "tell the HUD to update." The HUD connects to the signal independently. [Godot Docs: Signals]

Check Your Understanding

Exercise: You're designing a chest that opens when the player walks near it, plays an animation, and drops loot. What nodes would you compose into this scene, and how would the chest communicate with the rest of the game?

Hint

Think about what each component needs to DO: detect proximity, display visuals, animate, and notify that loot should spawn. Each job = one node.

Answer

Should mention: (1) Area2D to detect when the player enters proximity, (2) Sprite2D for the chest graphic, (3) AnimationPlayer for the opening animation, (4) the chest emits a signal (e.g., "opened") — the level or loot spawner listens. The chest doesn't spawn loot itself (that's not its job). Key insight: the chest scene is self-contained and reusable because it signals what happened rather than directly manipulating other objects.
