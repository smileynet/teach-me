The Problem: Nodes Do Nothing Without Scripts

Lesson 1 showed that games are trees of nodes. But a CharacterBody2D with a Sprite2D just sits there — it has structure but no behavior. GDScript is how you make nodes DO things: respond to input, move, animate, communicate. Every script attaches to a node and extends its type. [Godot Docs: GDScript Basics]

Script Structure: extends + Callbacks

Every GDScript file follows the same shape:

Variables: Types, @export, @onready

GDScript is gradually typed — you can add type hints for safety and performance:

# Dynamic (works but no editor help)
var speed = 200

# Typed (catches errors, better autocomplete, faster)
var speed: float = 200.0

# Inferred (type determined from the value)
var speed := 200.0  # inferred as float

Best practice: Use static typing everywhere. It catches bugs before you run the game and gives you autocomplete in the editor.

@export exposes a variable in Godot's Inspector panel — designers can tweak values without touching code:

@export var speed: float = 200.0        # slider in Inspector
@export var max_health: int = 100
@export var bullet_scene: PackedScene   # drag-and-drop a scene file
@export_range(0, 100, 5) var volume: int = 80  # constrained range

@onready defers a variable's initialization until _ready() runs (when the node tree is built):

# This would fail at parse time (tree doesn't exist yet)
# var sprite = $Sprite2D  ← ERROR

# This works — waits until _ready()
@onready var sprite: Sprite2D = $Sprite2D
@onready var anim := $AnimationPlayer

Lifecycle Callbacks: When Your Code Runs

CallbackRunsUse for
_ready()Once (node + children in tree)Get references, connect signals, set initial state
_process(delta)Every rendered frameVisual movement, input response, UI updates
_physics_process(delta)Every physics tick (fixed rate)Physics movement, collision, raycasts
_input(event)On any input eventOne-shot actions (jump, pause, fire)

delta = seconds since last frame. Always multiply movement by delta: position.x += speed * delta. This makes your game run at the same speed on 30fps and 144fps machines. [Godot Docs: Processing]

Signals: How Nodes Talk

Signals are GDScript's observer pattern — a node announces something happened without knowing who cares:

# Declare a custom signal
signal health_changed(old_value: int, new_value: int)
signal died

# Emit it when something happens
func take_damage(amount: int) -> void:
    var old := health
    health -= amount
    health_changed.emit(old, health)
    if health <= 0:
        died.emit()

# Connect to it (in another node's _ready)
func _ready() -> void:
    $Player.health_changed.connect(_on_health_changed)

func _on_health_changed(old: int, new: int) -> void:
    health_bar.value = new

Signals keep scenes decoupled. The Player doesn't know a HUD exists. The HUD connects to the Player's signal independently. Either can be removed without breaking the other. [Godot Docs: Signals]

Putting It Together: A Moving Character

extends CharacterBody2D

@export var speed: float = 300.0
@onready var sprite: Sprite2D = $Sprite2D

func _physics_process(delta: float) -> void:
    var direction := Input.get_vector("left", "right", "up", "down")
    velocity = direction * speed
    move_and_slide()

    # Flip sprite based on direction
    if direction.x != 0:
        sprite.flip_h = direction.x < 0

This is a complete movement script: 10 lines, typed, uses @export (tunable speed), @onready (safe reference), _physics_process (deterministic movement), and the Input system. Attach it to a CharacterBody2D with a Sprite2D and CollisionShape2D — you have a moving character.

Check Your Understanding

Exercise: A beginner puts their movement code in _process() instead of _physics_process(). The game seems to work in testing. When would this cause a bug, and why?

Hint

Think about what happens when the framerate drops (lag spike) or is very high (144hz monitor). What's different about the timing of _process vs _physics_process?

Key points to hit

Should mention: (1) _process runs at variable rate tied to framerate — movement becomes inconsistent across machines, (2) _physics_process runs at a fixed rate (default 60/s) regardless of rendering speed, (3) physics collision detection expects consistent timing — variable-rate movement can cause tunneling through walls on lag spikes. Key insight: anything involving move_and_slide() or collision belongs in _physics_process for deterministic behavior.
