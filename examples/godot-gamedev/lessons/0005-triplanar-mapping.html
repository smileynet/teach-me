Triplanar Mapping

Lesson 5 · Godot Toon Shaders · ~12 min read
Win: You can apply world-space textures to meshes without UVs, explain why triplanar uses three samples, and control blending sharpness.
After this lesson: You understand that triplanar mapping projects a texture from three axes and blends by surface normal — eliminating UV seams, stretching, and the sliding-texture bug from using view-space coordinates.

The Problem: Textures Without UVs

In the previous lessons, we textured meshes using UV coordinates — the 2D mapping baked into the mesh by the artist. But some surfaces don't have usable UVs:

  • Procedural geometry — terrain, CSG, voxel meshes generated at runtime
  • Tiled surfaces — roads, sidewalks, walls where you want the texture to tile based on world position, not mesh topology
  • Multi-mesh scenes — dozens of building pieces that should look like one continuous surface

If you use UV on these, you get stretching (where the UV unwrap is poor) or visible seams (where mesh pieces meet). The fix: ignore the mesh's UVs entirely and project the texture from world space.

World Position in fragment()

From lesson 1 we know: VERTEX in fragment() is in view space (camera-relative). We need world space (scene-fixed). The solution is the same pattern we learned — compute it in vertex() and pass it via a varying:

varying vec3 world_pos;
varying vec3 world_normal;

void vertex() {
    world_pos = (MODEL_MATRIX * vec4(VERTEX, 1.0)).xyz;
    world_normal = normalize(MODEL_NORMAL_MATRIX * NORMAL);
}

Now world_pos and world_normal are available in fragment() — and they stay fixed to the scene regardless of camera movement. This is what makes world-space texturing stable.

Alternative: render_mode world_vertex_coords; — This render mode makes VERTEX arrive in world space everywhere (vertex, fragment, light), eliminating the need for varyings entirely. But it changes the coordinate space for ALL your vertex code — any vertex displacement, skinning, or other vertex() logic must now work in world space instead of model space. When to use which:
  • Explicit varying (what we did above) — the safe default. Use when your shader combines triplanar with other effects (toon lighting, vertex animation, outline extrusion) that expect model-space VERTEX. Each system gets the coordinate space it needs.
  • world_vertex_coords — simpler for pure-triplanar shaders where nothing else touches VERTEX. One line replaces two varyings + a vertex() function. Good for environment props (terrain, walls) with no vertex animation.
Rule of thumb: If your shader has a light() function or modifies VERTEX for any reason, use the explicit varying. If it's a simple fragment-only material, world_vertex_coords saves boilerplate.

Naive Approach: Single Projection

The simplest world-space texturing: use the XZ world position as UV coordinates. This projects the texture straight down, like painting the floor:

void fragment() {
    ALBEDO = texture(albedo_texture, world_pos.xz * tex_scale).rgb;
}

This works perfectly for horizontal surfaces (floors, roads, flat roofs). But look at a vertical wall — the texture stretches infinitely because XZ doesn't vary across a surface that faces sideways. Walls become smeared single-color bands.

You could project from the side instead (world_pos.xy) — but then floors stretch. No single projection works for all surface orientations. This is the problem triplanar solves.

Triplanar: Three Projections, Blended by Normal

The insight: sample the texture three times — once from each major axis — and blend the results based on which direction the surface faces. A floor (normal pointing up) gets the top-down projection. A wall (normal pointing sideways) gets the side projection. Angled surfaces get a weighted mix.

Here's the full triplanar shader — combining world-space texturing with our toon light() from the previous lessons:

shader_type spatial;
render_mode cull_disabled;

uniform sampler2D albedo_texture : source_color, repeat_enable, filter_linear_mipmap_anisotropic;
uniform float tex_scale : hint_range(0.01, 10.0) = 1.0;
uniform float blend_sharpness : hint_range(1.0, 20.0) = 5.0;
uniform int bands : hint_range(1, 8) = 3;

varying vec3 world_pos;
varying vec3 world_normal;

void vertex() {
    world_pos = (MODEL_MATRIX * vec4(VERTEX, 1.0)).xyz;
    world_normal = normalize(MODEL_NORMAL_MATRIX * NORMAL);
}

void fragment() {
    // Flip normal for backfaces — ensures triplanar works on both sides
    vec3 normal = FRONT_FACING ? world_normal : -world_normal;

    // Compute blending weights from surface normal
    vec3 blend = pow(abs(normal), vec3(blend_sharpness));
    blend /= (blend.x + blend.y + blend.z); // normalize to sum = 1.0

    // Sample texture from each axis
    vec3 x_proj = texture(albedo_texture, world_pos.zy * tex_scale).rgb;
    vec3 y_proj = texture(albedo_texture, world_pos.xz * tex_scale).rgb;
    vec3 z_proj = texture(albedo_texture, world_pos.xy * tex_scale).rgb;

    // Blend the three projections
    ALBEDO = x_proj * blend.x + y_proj * blend.y + z_proj * blend.z;

    // Fix normal for lighting on backfaces
    if (!FRONT_FACING) {
        NORMAL = -NORMAL;
    }
}

void light() {
    float NdotL = dot(NORMAL, LIGHT);
    float diffuse_amount = NdotL + (ATTENUATION - 1.0);
    float cuts_inv = 1.0 / float(bands);
    float stepped = clamp(diffuse_amount + mod(1.0 - diffuse_amount, cuts_inv), 0.0, 1.0);
    DIFFUSE_LIGHT = max(DIFFUSE_LIGHT, ALBEDO * LIGHT_COLOR * stepped);
}
Why cull_disabled and FRONT_FACING? Triplanar shaders are often applied to procedural geometry (CSG, voxels, terrain chunks) which frequently has inconsistent or inverted normals. Without cull_disabled, backfaces are invisible — you'll see through the mesh from one side. The FRONT_FACING check flips the normal for backfaces so the triplanar blend and lighting both work correctly regardless of winding order. On artist-modeled meshes with correct normals, this is harmless (FRONT_FACING is always true). On procedural geometry, it prevents the "invisible top, visible bottom" bug.

How the blending works

The key line is pow(abs(world_normal), vec3(blend_sharpness)). The surface normal tells us which direction the surface faces — abs() makes it work regardless of which side (left wall = right wall for texturing). The pow() sharpens the blending: at sharpness = 1.0 all three projections mix smoothly; at sharpness = 10.0 only the dominant axis contributes. The division by the sum normalizes the weights so they always add to 1.0.

Performance note: Triplanar costs 3x the texture samples of regular UV mapping. On mobile or with many triplanar materials, consider using the Y projection only for horizontal surfaces (check if abs(world_normal.y) > 0.7 and skip the other two samples).

Controlling the Blend

The blend_sharpness uniform is the artist's main control. Here's what different values look like on a 45-degree slope:

SharpnessBehaviorBest for
1.0Smooth blend across all anglesOrganic surfaces (terrain, rocks)
5.0Visible dominant axis, soft transitionsGeneral-purpose (default)
10.0+Nearly hard switch between axesArchitectural surfaces (clean edges)

Try it: Drag the blend_sharpness slider in the Inspector while looking at a corner where two walls meet a floor. At 1.0 the corner looks muddy. At 10.0+ the axes switch cleanly but you might see a visible seam line. 5.0 is usually the sweet spot.

Texture Scale and Tiling

Since we're projecting from world space, the tex_scale uniform controls how many meters each texture tile covers. A scale of 1.0 means one texture repetition per world unit; 0.5 means one repetition every 2 units (larger tiles); 2.0 means 2 repetitions per unit (smaller tiles).

This is powerful for scene consistency: every surface using the same shader at the same scale produces seamlessly tiling textures, even across separate meshes that were never UV'd together. Roads meet sidewalks cleanly because they share the same world-space coordinate system.

Check Your Understanding

Exercise: A colleague writes a triplanar shader but their textures slide around as the camera rotates. They're computing world position in fragment() like this:

void fragment() {
    vec3 wp = (MODEL_MATRIX * vec4(VERTEX, 1.0)).xyz;
    ALBEDO = texture(albedo_texture, wp.xz).rgb;
}

You already know this bug from lesson 1. But explain specifically: why does triplanar mapping make this bug obvious (the textures visibly slide), whereas a UV-based shader with the same mistake might not show it as clearly?

Hint

Think about what VERTEX means in fragment() (view space = camera-relative). When the camera moves, what happens to view-space positions? And for a UV-based shader, where does UV come from?

Answer

VERTEX in fragment() is in view space — it changes every frame as the camera moves. Applying MODEL_MATRIX (model→world) to a view-space value produces an output that shifts with the camera. The texture coordinates change every frame → textures visibly slide.

UV-based shaders don't show this because UV is a per-vertex attribute baked into the mesh — it doesn't depend on VERTEX or the camera at all. The mistake (wrong coordinate space) only manifests when you derive coordinates from position, which is exactly what triplanar does.

The fix (from lesson 1): compute world position in vertex() where VERTEX is still in model space, pass via a varying.
