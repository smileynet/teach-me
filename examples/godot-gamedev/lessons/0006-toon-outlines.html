Toon Outlines

Lesson 6 · Godot Toon Shaders · ~25 min read
Win: You can implement three outline approaches (inverted hull, screen-space edge detection, JFA distance field), explain the hard-edge problem and its fix, and select the right technique for a given art direction.
After this lesson: You can create an inverted hull outline (including the smooth-normals fix for hard edges), set up screen-space depth+normal edge detection, explain how JFA builds a distance field for wide outlines, and articulate why shipped games combine techniques for different object categories.

The Problem: Toon Shading Without Outlines Looks Unfinished

The banding shaders from the previous lessons give us discrete brightness steps — the "inside" of the cel look. But without outlines, the shapes don't pop off the background the way they do in anime or comic-book games. The dark border is what tells your brain "this is a stylized object, not a realistic one with flat lighting." [eldskald: Complete Cel Shader]

Two families of outline techniques exist:

  • Inverted hull (mesh-based) — renders the mesh a second time, inflated and front-face-culled, so you see a dark shell behind the original. Per-object, cheap, works everywhere.
  • Screen-space edge detection (post-process) — samples the depth/normal buffers and draws edges where values change sharply. Whole-scene, detects internal edges, but no per-object control.

This lesson teaches the inverted hull approach — it's the industry standard (Guilty Gear, Genshin Impact, Persona) and integrates cleanly with our existing toon_bands shader. We'll mention screen-space at the end with decision criteria for when you'd pick it instead.

The Inverted Hull Technique

The idea: render the mesh twice. First pass: your normal toon shader (banding, textures, lighting). Second pass: a separate shader that inflates the mesh slightly along its normals and only renders back faces. Since back faces point away from the camera, they're only visible around the edges — creating a silhouette outline.

In Godot 4, the second pass is applied via the material's next_pass property. This means the outline shader is completely independent of your lighting shader — you can use it with toon_bands, toon_ramp, or any other base material.

The Outline Shader

Create a new file toon_outline.gdshader. The entire shader is 12 lines — it inflates vertices, culls front faces, and outputs a solid color:

shader_type spatial;
render_mode cull_front, unshaded;

uniform float outline_width : hint_range(0.0, 0.1) = 0.02;
uniform vec4 outline_color : source_color = vec4(0.0, 0.0, 0.0, 1.0);

void vertex() {
    // Inflate vertices along their normals
    VERTEX += NORMAL * outline_width;
}

void fragment() {
    ALBEDO = outline_color.rgb;
}
Why cull_front? Normal rendering culls back faces (you don't see the inside of a mesh). Here we flip it — cull front faces so ONLY back faces render. The inflated back faces peek out behind the original mesh's silhouette. The original mesh (drawn first via the base material) covers everything that isn't an edge.
Why unshaded? The outline shouldn't respond to lighting — it's always the same flat color regardless of light direction. Without unshaded, the outline would have its own shading bands, which looks wrong.

Applying It via next_pass

In Godot's Inspector:

  1. Select the mesh that already has your toon material
  2. In the material's properties, find Next Pass
  3. Click → New ShaderMaterial
  4. Assign toon_outline.gdshader to it
  5. Adjust outline_width until it looks right (0.01–0.03 for characters, 0.005 for small props)

That's it. The outline renders after the base material on the same mesh, in the same draw call batch. No extra nodes, no viewports, no post-processing.

Problem: Outline Thickness Changes with Distance

The basic version inflates by a fixed world-space amount. Close to camera, the outline looks perfect. Far from camera, it's barely visible. Zoom in close, and it's comically thick. This happens because NORMAL * outline_width is in model space — a fixed number of meters regardless of how many pixels that maps to on screen.

The fix: expand in view space instead. After the modelview transform, multiply by the distance from camera so the outline stays a consistent pixel width:

 shader_type spatial;
 render_mode cull_front, unshaded;

 uniform float outline_width : hint_range(0.0, 0.1) = 0.02;
 uniform vec4 outline_color : source_color = vec4(0.0, 0.0, 0.0, 1.0);

 void vertex() {
-    // Inflate vertices along their normals
-    VERTEX += NORMAL * outline_width;
+    // Inflate in view space — consistent pixel width regardless of distance
+    vec4 clip_pos = MODELVIEW_MATRIX * vec4(VERTEX, 1.0);
+    vec3 view_normal = normalize((MODELVIEW_MATRIX * vec4(NORMAL, 0.0)).xyz);
+    clip_pos.xyz += view_normal * outline_width * -clip_pos.z;
+    POSITION = PROJECTION_MATRIX * clip_pos;
 }

 void fragment() {
     ALBEDO = outline_color.rgb;
 }

The key insight: -clip_pos.z is the distance from camera in view space (negative Z = forward in Godot). Multiplying by it scales the inflation proportionally to distance — farther objects get more inflation to maintain the same screen-space thickness.

Why write to POSITION instead of VERTEX? Once we transform manually via MODELVIEW_MATRIX, we've left model space. Writing to POSITION (a clip-space vec4) tells Godot "I've done the full transform myself — skip the built-in modelview+projection." This is the standard pattern for any vertex shader that needs to operate in view or clip space.

View-Space Outline (Distance-Independent)

Combining the view-space expansion with a small minimum thickness so outlines don't vanish completely at extreme distances:

shader_type spatial;
render_mode cull_front, unshaded;

uniform float outline_width : hint_range(0.0, 0.1) = 0.02;
uniform vec4 outline_color : source_color = vec4(0.0, 0.0, 0.0, 1.0);

void vertex() {
    vec4 clip_pos = MODELVIEW_MATRIX * vec4(VERTEX, 1.0);
    vec3 view_normal = normalize((MODELVIEW_MATRIX * vec4(NORMAL, 0.0)).xyz);
    clip_pos.xyz += view_normal * outline_width * -clip_pos.z;
    POSITION = PROJECTION_MATRIX * clip_pos;
}

void fragment() {
    ALBEDO = outline_color.rgb;
}

Try it: Apply this as next_pass on any of the toon-shaded meshes from previous lessons. Orbit the camera close and far — the outline stays the same apparent thickness. Change outline_color to dark blue or brown for a softer look than pure black.

The Hard-Edge Problem

Try the outline on a cube and you'll see it immediately: the outline is disjointed, with visible gaps at every edge. The sphere looked fine — so what's different?

Hard-edge meshes (cubes, swords, architectural details) split vertices at every sharp edge. A cube corner that joins three faces has three separate vertices at the same position, each with a normal pointing along its respective face. When the shader extrudes VERTEX += NORMAL * width, those three co-located vertices move in three divergent directions — tearing the inflated hull apart. [Poiyomi Docs: Outlines]

The fix: extrude along smoothed normals instead of the mesh's split normals. Since the outline hull is rendered as a solid color (unshaded), it doesn't need correct shading normals — it only needs a consistent extrusion direction so all vertices at the same position move the same way.

The Smooth Normals Fix (Vertex Color Approach)

The most common production technique is to pre-compute averaged normals in Blender, store them in the mesh's vertex color channel, and read COLOR.rgb in the shader instead of NORMAL. The encoding maps [-1, 1] → [0, 1] for storage, then decodes in the shader: [Duncan Readle: Smooth Outlines]

shader_type spatial;
render_mode cull_front, unshaded;

uniform float outline_width : hint_range(0.0, 0.1) = 0.02;
uniform vec4 outline_color : source_color = vec4(0.0, 0.0, 0.0, 1.0);

void vertex() {
    // Decode smooth normals from vertex color (stored as n*0.5+0.5 in Blender)
    vec3 smooth_normal = normalize(COLOR.rgb * 2.0 - 1.0);

    // Inflate in view space using the smooth normal direction
    vec4 clip_pos = MODELVIEW_MATRIX * vec4(VERTEX, 1.0);
    vec3 view_normal = normalize((MODELVIEW_MATRIX * vec4(smooth_normal, 0.0)).xyz);
    clip_pos.xyz += view_normal * outline_width * -clip_pos.z;
    POSITION = PROJECTION_MATRIX * clip_pos;
}

void fragment() {
    ALBEDO = outline_color.rgb;
}

The only change from the basic version: smooth_normal decoded from COLOR.rgb replaces NORMAL. This gives every vertex at a shared position the same extrusion direction, eliminating the gaps entirely.

New concept — vertex color encoding: Vertex colors store values in [0, 1] range (RGBA, 8 bits per channel). Normals range from [-1, 1]. The standard encoding is color = normal * 0.5 + 0.5 and decoding is normal = color * 2.0 - 1.0. This is the same trick normal maps use — just stored per-vertex instead of per-texel. [Poiyomi Docs]
Blender pipeline required: The smooth normals must be baked into vertex colors before export. This involves a Blender Python script that iterates vertices, averages normals at shared positions, and writes to a color attribute. This is a standard production workflow used by Guilty Gear Strive, Genshin Impact, and most anime-style games. [Philipp-Seifried: Normals to Vertex Color addon]
When to use which fix: If you control the art pipeline (Blender → Godot), bake smooth normals — it's the standard production approach used by Guilty Gear and Genshin Impact. If you can't modify meshes (asset store models, prototyping), use screen-space edge detection instead — it operates on the rendered image, so mesh topology is irrelevant.

Approach B: Screen-Space Edge Detection (Production Quality)

The inverted hull gives you control per object — different characters can have different outline widths and colors. But it only outlines the silhouette. Internal creases, folds in clothing, sharp edges within the mesh — those don't get outlines. And as we just saw, hard-edge meshes require extra pipeline work to avoid artifacts.

Screen-space edge detection solves all of this. Instead of modifying geometry, it reads the depth and normal buffers after the scene renders and draws lines wherever values change sharply. Every edge in the scene gets an outline — silhouettes AND internal details — with zero mesh preparation. [MInteractive: Simple Outline For, CC0]

This shader runs as a post-process on a full-screen quad (a MeshInstance3D with a QuadMesh sized 2×2, placed as a child of the camera or at the scene root).

shader_type spatial;
render_mode unshaded, depth_test_disabled;

uniform sampler2D DEPTH_TEXTURE : hint_depth_texture, filter_linear;
uniform sampler2D NORMAL_TEXTURE : hint_normal_roughness_texture, filter_nearest;
uniform float depth_threshold : hint_range(0.0, 2.0) = 0.4;
uniform float normal_threshold : hint_range(0.0, 2.0) = 0.6;
uniform vec4 outline_color : source_color = vec4(0.0, 0.0, 0.0, 1.0);
uniform float outline_thickness : hint_range(0.5, 5.0) = 1.0;

float getLinearDepth(vec2 uv, mat4 inv_proj) {
    float raw = texture(DEPTH_TEXTURE, uv).r;
    vec3 ndc = vec3(uv * 2.0 - 1.0, raw);
    vec4 view = inv_proj * vec4(ndc, 1.0);
    view.xyz /= view.w;
    return -view.z;
}

void vertex() {
    // Fullscreen quad — bypass model transform
    POSITION = vec4(VERTEX.xy, 1.0, 1.0);
}

void fragment() {
    vec2 pixel = outline_thickness / VIEWPORT_SIZE;

    // Sample depth at 4 neighbors
    float depth_center = getLinearDepth(SCREEN_UV, INV_PROJECTION_MATRIX);
    float depth_left   = getLinearDepth(SCREEN_UV + vec2(-pixel.x, 0.0), INV_PROJECTION_MATRIX);
    float depth_right  = getLinearDepth(SCREEN_UV + vec2( pixel.x, 0.0), INV_PROJECTION_MATRIX);
    float depth_up     = getLinearDepth(SCREEN_UV + vec2(0.0,  pixel.y), INV_PROJECTION_MATRIX);
    float depth_down   = getLinearDepth(SCREEN_UV + vec2(0.0, -pixel.y), INV_PROJECTION_MATRIX);

    // Depth edge: difference between opposing neighbors
    float depth_diff = abs(depth_left - depth_right) + abs(depth_up - depth_down);
    float depth_edge = smoothstep(depth_threshold * 0.1, depth_threshold, depth_diff);

    // Sample normals at 4 neighbors
    vec3 normal_center = texture(NORMAL_TEXTURE, SCREEN_UV).rgb * 2.0 - 1.0;
    vec3 normal_left   = texture(NORMAL_TEXTURE, SCREEN_UV + vec2(-pixel.x, 0.0)).rgb * 2.0 - 1.0;
    vec3 normal_right  = texture(NORMAL_TEXTURE, SCREEN_UV + vec2( pixel.x, 0.0)).rgb * 2.0 - 1.0;
    vec3 normal_up     = texture(NORMAL_TEXTURE, SCREEN_UV + vec2(0.0,  pixel.y)).rgb * 2.0 - 1.0;
    vec3 normal_down   = texture(NORMAL_TEXTURE, SCREEN_UV + vec2(0.0, -pixel.y)).rgb * 2.0 - 1.0;

    // Normal edge: how much normals diverge from center
    float normal_diff = 0.0;
    normal_diff += 1.0 - dot(normal_center, normal_left);
    normal_diff += 1.0 - dot(normal_center, normal_right);
    normal_diff += 1.0 - dot(normal_center, normal_up);
    normal_diff += 1.0 - dot(normal_center, normal_down);
    float normal_edge = smoothstep(normal_threshold, normal_threshold * 2.0, normal_diff);

    // Combine: either signal triggers the outline
    float edge = max(depth_edge, normal_edge);

    ALBEDO = outline_color.rgb;
    ALPHA = edge * outline_color.a;
}

Setting up the full-screen quad

  1. Add a MeshInstance3D as a child of your Camera3D
  2. Set its Mesh to a QuadMesh with size (2, 2)
  3. Set Transform → Position to (0, 0, -1) — one unit in front of camera
  4. Assign a new ShaderMaterial with toon_outline_screen.gdshader
  5. In the material, set Render Priority to 1 (draws after scene)
Why depth_test_disabled? Without it, the quad would be occluded by scene geometry (it's only 1 unit from camera). In Godot 4.4+, this render mode is required for screen-space post-process shaders to work correctly — without it, outlines only appear against the sky.
New concept — hint_normal_roughness_texture: Godot's G-buffer stores surface normals (and roughness in the alpha channel) in a texture accessible via this sampler hint. Only available in Forward+ and Mobile renderers — NOT in Compatibility. This is why screen-space outlines don't work on all platforms. Docs: Spatial Shader

Try it: Adjust depth_threshold and normal_threshold independently. Depth edges catch silhouettes and object boundaries. Normal edges catch surface creases and hard edges within a single mesh. Lower thresholds = more lines; higher = only the strongest edges.

Approach C: Jump Flood Algorithm (Wide Pixel-Perfect Outlines)

Screen-space edge detection works beautifully for thin outlines (1–3 pixels). But what if your art direction calls for thick, dramatic borders — 10, 20, even 50 pixels wide? Simply increasing the sample offset in the Sobel shader produces fuzzy, inconsistent results because edge detection doesn't understand distance. [Ben Golus: The Quest for Very Wide Outlines]

The Jump Flood Algorithm (JFA) solves this by computing a distance field — every pixel knows exactly how far it is from the nearest edge. That distance drives the outline: if distance < threshold, draw outline color. The result is mathematically clean, works at any width, and costs only O(log₂ n) passes regardless of how thick the outline is.

How JFA Works (The Concept)

JFA builds a distance field in three stages:

  1. Extraction: Run edge detection (Sobel on viewport color, or a depth/normal check). Pixels at edges become "seeds" and store their own screen coordinates. Non-seeds get a sentinel value (infinity).
  2. Jump Flood (repeated N times): Each pass, every pixel checks 8 neighbors at a decreasing grid offset (128, 64, 32, 16, 8, 4, 2, 1). If a neighbor has a closer seed, adopt it. After all passes, every pixel knows the coordinates of its nearest edge pixel.
  3. Overlay: Compute distance = length(my_position - nearest_seed_position). If distance is within the outline threshold, draw the outline color. The smooth distance field allows anti-aliasing, gradients, glow effects, and any width.

The key insight: each JFA pass doubles the propagation range. After 5 passes, seeds have propagated 32 pixels outward. After 7 passes, 128 pixels. A 100-pixel outline costs the same as a 64-pixel one — both need 7 passes. This is why JFA outperforms naive dilation (which needs N passes for N-pixel width).

JFA in Godot: Two Implementations

JFA requires multiple render passes with ping-pong textures, which makes it more complex to set up than a single-shader solution. In Godot 4.3+, two community implementations exist:

When to use which JFA implementation:
  • pink-arcana/godot-distance-field-outlines (150★, MIT) — two versions: a CanvasItem shader version (works in Compatibility renderer + web exports) and a CompositorEffect compute shader version (Forward+ only, faster). Best choice for learning and cross-platform support.
  • L0UARN/godot-outlines (MIT) — C# + compute shaders via CompositorEffect. Forward+ only. Supports per-node outline colors via a special "outlineable" material flag.
Default recommendation: Start with pink-arcana's DFOutlineNode (CanvasItem version) — it works on all renderers and is the simplest to understand. Move to the CompositorEffect version when you need better performance at high resolutions.

The core JFA pass is conceptually simple — here's the essential logic (adapted from pink-arcana, MIT license):

shader_type canvas_item;
render_mode blend_mix;

// This shader runs multiple times with decreasing offset values
uniform sampler2D in_texture : hint_screen_texture, filter_nearest;
uniform float offset; // Halves each pass: 128, 64, 32, 16, 8, 4, 2, 1
uniform float distance_denominator;
uniform bool last_pass;

const vec2 NEIGHBOR_OFFSETS[8] = {
    vec2(-1.0,-1.0), vec2(0.0,-1.0), vec2(1.0,-1.0),
    vec2(-1.0,0.0),                   vec2(1.0,0.0),
    vec2(-1.0,1.0),  vec2(0.0,1.0),  vec2(1.0,1.0) };

void fragment() {
    vec2 texture_size = vec2(textureSize(in_texture, 0));
    vec2 pixel_size = 1.0 / texture_size;
    vec2 tex_coord = UV / pixel_size; // Current pixel coordinate

    // Read current best seed (packed as UV coordinates in RG channels)
    vec4 seed_color = texelFetch(in_texture, ivec2(tex_coord), 0);
    vec2 seed_coord = seed_color.rg * texture_size;
    bool valid_seed = seed_color.a > 0.5;
    float min_dist_sq = valid_seed ? distance(tex_coord, seed_coord) : 1000000.0;
    min_dist_sq = min_dist_sq * min_dist_sq;

    // Check 8 neighbors at current offset distance
    for (int i = 0; i < 8; i++) {
        vec2 neighbor_coord = tex_coord + NEIGHBOR_OFFSETS[i] * offset;
        neighbor_coord = clamp(neighbor_coord, vec2(0.0), texture_size - vec2(1.0));

        vec4 neighbor_color = texelFetch(in_texture, ivec2(neighbor_coord), 0);
        if (neighbor_color.a < 0.5) continue; // No seed here

        vec2 neighbor_seed = neighbor_color.rg * texture_size;
        float dist_sq = distance(tex_coord, neighbor_seed);
        dist_sq = dist_sq * dist_sq;

        if (dist_sq < min_dist_sq) {
            min_dist_sq = dist_sq;
            seed_coord = neighbor_seed;
            seed_color = neighbor_color;
            valid_seed = true;
        }
    }

    if (last_pass) {
        // Output normalized distance (0 = on edge, 1 = far from edge)
        float dist = valid_seed ? sqrt(min_dist_sq) / distance_denominator : 1.0;
        COLOR = vec4(dist, 0.0, 0.0, 1.0);
    } else {
        // Pass seed coordinates to next iteration
        COLOR = valid_seed ? vec4(seed_coord / texture_size, 0.0, 1.0) : vec4(0.0);
    }
}

This single shader runs multiple times — each invocation halves the offset uniform. After all passes complete, every pixel contains its distance to the nearest seed. The overlay pass then thresholds this distance to produce the final outline.

Why this is more complex to set up: Unlike the inverted hull (one shader on one mesh) or screen-space (one shader on one quad), JFA needs orchestration — multiple render passes with intermediate textures. In Godot, you'd use SubViewports for the CanvasItem version or CompositorEffect for the compute version. The pink-arcana addon handles all this scaffolding for you.

Choosing Your Outline Technique

You now have three outline techniques, each solving different problems. The progression isn't "basic → advanced" in a simple line — each has a distinct niche. Here's how to select:

When to use which — the decision tree:
  • Need per-object artistic control (character outlines)? → Inverted hull. Bake smooth normals if the mesh has hard edges.
  • Need thin outlines everywhere with internal detail? → Screen-space Sobel. Zero setup, catches every crease and fold.
  • Need wide outlines (10+ pixels)? → JFA. It's the only technique that produces clean results at any width.
  • Need outline effects (glow, gradient, animation)? → JFA. The distance field unlocks all of these as a free bonus.
  • Targeting Compatibility renderer / web? → Inverted hull (always works) or JFA CanvasItem version (pink-arcana).

The Production Combination

Shipped games rarely use just one technique. The industry standard — used by Guilty Gear Strive, Hi-Fi Rush, Genshin Impact, and Borderlands — combines techniques by category:

  • Characters: Inverted hull (artistic control over thickness per body part, with smooth normals baked in Blender)
  • Environment: Screen-space edge detection (automatic coverage, catches every architectural edge)
  • UI/Selection highlights: JFA (wide glowing outlines that look clean at any width)

The progression for learning is: inverted hull first (teaches vertex manipulation and render passes), then screen-space (teaches buffer access and post-processing), then JFA (teaches multi-pass algorithms and distance fields). Each builds shader mechanics competence that the next technique assumes.

Check Your Understanding

Exercise: Your art director wants three different outline styles in the same scene:

  • The player character needs a thick (8px) outline with per-limb width control
  • Environmental architecture (all hard-edge cubes and pillars) needs thin outlines at every crease
  • The selected interactable object needs a wide (30px) glowing highlight

Which technique from this lesson would you use for each, and why can't the others do the job?

Hint

Think about what each technique is good at: per-object control, internal edges, outline width range. One technique fails on wide outlines. One fails on per-object control. One fails on internal edges.

Answer

Character (8px, per-limb): Inverted hull — it's the only technique with per-mesh width/color control. Needs smooth normals baked into vertex colors (Blender pipeline) since character meshes have some hard edges. Screen-space can't do per-object. JFA could work but is overkill for a single mesh.

Architecture (thin, every crease): Screen-space edge detection — it detects internal edges (normal discontinuities) which inverted hull can't, and works perfectly on hard-edge geometry without any mesh preparation. JFA would only catch silhouettes (misses interior creases). Inverted hull would need smooth normals baked on every environment mesh.

Selection highlight (30px, glowing): JFA distance field — it's the only technique that produces pixel-perfect wide outlines. The distance field naturally supports smooth falloff/glow effects. Screen-space edge detection can only do 1-3px practically. Inverted hull at 30px world-space would look terrible (non-uniform, distorted by geometry).
