Toon Outlines

Lesson 6 · Godot Toon Shaders · ~16 min read
Win: You can implement both outline approaches (inverted hull for per-object control, screen-space for production quality) and explain when to use each.
After this lesson: You can create an inverted hull outline via next_pass, set up a screen-space depth+normal edge detection shader on a fullscreen quad, and articulate why shipped games combine both techniques for different object categories.

The Problem: Toon Shading Without Outlines Looks Unfinished

The banding shaders from the previous lessons give us discrete brightness steps — the "inside" of the cel look. But without outlines, the shapes don't pop off the background the way they do in anime or comic-book games. The dark border is what tells your brain "this is a stylized object, not a realistic one with flat lighting." [eldskald: Complete Cel Shader]

Two families of outline techniques exist:

  • Inverted hull (mesh-based) — renders the mesh a second time, inflated and front-face-culled, so you see a dark shell behind the original. Per-object, cheap, works everywhere.
  • Screen-space edge detection (post-process) — samples the depth/normal buffers and draws edges where values change sharply. Whole-scene, detects internal edges, but no per-object control.

This lesson teaches the inverted hull approach — it's the industry standard (Guilty Gear, Genshin Impact, Persona) and integrates cleanly with our existing toon_bands shader. We'll mention screen-space at the end with decision criteria for when you'd pick it instead.

The Inverted Hull Technique

The idea: render the mesh twice. First pass: your normal toon shader (banding, textures, lighting). Second pass: a separate shader that inflates the mesh slightly along its normals and only renders back faces. Since back faces point away from the camera, they're only visible around the edges — creating a silhouette outline.

In Godot 4, the second pass is applied via the material's next_pass property. This means the outline shader is completely independent of your lighting shader — you can use it with toon_bands, toon_ramp, or any other base material.

The Outline Shader

Create a new file toon_outline.gdshader. The entire shader is 12 lines — it inflates vertices, culls front faces, and outputs a solid color:

shader_type spatial;
render_mode cull_front, unshaded;

uniform float outline_width : hint_range(0.0, 0.1) = 0.02;
uniform vec4 outline_color : source_color = vec4(0.0, 0.0, 0.0, 1.0);

void vertex() {
    // Inflate vertices along their normals
    VERTEX += NORMAL * outline_width;
}

void fragment() {
    ALBEDO = outline_color.rgb;
}
Why cull_front? Normal rendering culls back faces (you don't see the inside of a mesh). Here we flip it — cull front faces so ONLY back faces render. The inflated back faces peek out behind the original mesh's silhouette. The original mesh (drawn first via the base material) covers everything that isn't an edge.
Why unshaded? The outline shouldn't respond to lighting — it's always the same flat color regardless of light direction. Without unshaded, the outline would have its own shading bands, which looks wrong.

Applying It via next_pass

In Godot's Inspector:

  1. Select the mesh that already has your toon material
  2. In the material's properties, find Next Pass
  3. Click → New ShaderMaterial
  4. Assign toon_outline.gdshader to it
  5. Adjust outline_width until it looks right (0.01–0.03 for characters, 0.005 for small props)

That's it. The outline renders after the base material on the same mesh, in the same draw call batch. No extra nodes, no viewports, no post-processing.

Problem: Outline Thickness Changes with Distance

The basic version inflates by a fixed world-space amount. Close to camera, the outline looks perfect. Far from camera, it's barely visible. Zoom in close, and it's comically thick. This happens because NORMAL * outline_width is in model space — a fixed number of meters regardless of how many pixels that maps to on screen.

The fix: expand in view space instead. After the modelview transform, multiply by the distance from camera so the outline stays a consistent pixel width:

 shader_type spatial;
 render_mode cull_front, unshaded;

 uniform float outline_width : hint_range(0.0, 0.1) = 0.02;
 uniform vec4 outline_color : source_color = vec4(0.0, 0.0, 0.0, 1.0);

 void vertex() {
-    // Inflate vertices along their normals
-    VERTEX += NORMAL * outline_width;
+    // Inflate in view space — consistent pixel width regardless of distance
+    vec4 clip_pos = MODELVIEW_MATRIX * vec4(VERTEX, 1.0);
+    vec3 view_normal = normalize((MODELVIEW_MATRIX * vec4(NORMAL, 0.0)).xyz);
+    clip_pos.xyz += view_normal * outline_width * -clip_pos.z;
+    POSITION = PROJECTION_MATRIX * clip_pos;
 }

 void fragment() {
     ALBEDO = outline_color.rgb;
 }

The key insight: -clip_pos.z is the distance from camera in view space (negative Z = forward in Godot). Multiplying by it scales the inflation proportionally to distance — farther objects get more inflation to maintain the same screen-space thickness.

Why write to POSITION instead of VERTEX? Once we transform manually via MODELVIEW_MATRIX, we've left model space. Writing to POSITION (a clip-space vec4) tells Godot "I've done the full transform myself — skip the built-in modelview+projection." This is the standard pattern for any vertex shader that needs to operate in view or clip space.

The Final Outline Shader

Combining the view-space expansion with a small minimum thickness so outlines don't vanish completely at extreme distances:

shader_type spatial;
render_mode cull_front, unshaded;

uniform float outline_width : hint_range(0.0, 0.1) = 0.02;
uniform vec4 outline_color : source_color = vec4(0.0, 0.0, 0.0, 1.0);

void vertex() {
    vec4 clip_pos = MODELVIEW_MATRIX * vec4(VERTEX, 1.0);
    vec3 view_normal = normalize((MODELVIEW_MATRIX * vec4(NORMAL, 0.0)).xyz);
    clip_pos.xyz += view_normal * outline_width * -clip_pos.z;
    POSITION = PROJECTION_MATRIX * clip_pos;
}

void fragment() {
    ALBEDO = outline_color.rgb;
}

Try it: Apply this as next_pass on any of the toon-shaded meshes from previous lessons. Orbit the camera close and far — the outline stays the same apparent thickness. Change outline_color to dark blue or brown for a softer look than pure black.

Approach B: Screen-Space Edge Detection (Production Quality)

The inverted hull gives you control per object — different characters can have different outline widths and colors. But it only outlines the silhouette. Internal creases, folds in clothing, sharp edges within the mesh — those don't get outlines. And on hard-edge meshes (swords, architectural details), the inflated normals create spiky artifacts.

Screen-space edge detection solves all of this. Instead of modifying geometry, it reads the depth and normal buffers after the scene renders and draws lines wherever values change sharply. Every edge in the scene gets an outline — silhouettes AND internal details — with zero mesh preparation. [MInteractive: Simple Outline For, CC0]

This shader runs as a post-process on a full-screen quad (a MeshInstance3D with a QuadMesh sized 2×2, placed as a child of the camera or at the scene root).

shader_type spatial;
render_mode unshaded, depth_test_disabled;

uniform sampler2D DEPTH_TEXTURE : hint_depth_texture, filter_linear;
uniform sampler2D NORMAL_TEXTURE : hint_normal_roughness_texture, filter_nearest;
uniform float depth_threshold : hint_range(0.0, 2.0) = 0.4;
uniform float normal_threshold : hint_range(0.0, 2.0) = 0.6;
uniform vec4 outline_color : source_color = vec4(0.0, 0.0, 0.0, 1.0);
uniform float outline_thickness : hint_range(0.5, 5.0) = 1.0;

float getLinearDepth(vec2 uv, mat4 inv_proj) {
    float raw = texture(DEPTH_TEXTURE, uv).r;
    vec3 ndc = vec3(uv * 2.0 - 1.0, raw);
    vec4 view = inv_proj * vec4(ndc, 1.0);
    view.xyz /= view.w;
    return -view.z;
}

void vertex() {
    // Fullscreen quad — bypass model transform
    POSITION = vec4(VERTEX.xy, 1.0, 1.0);
}

void fragment() {
    vec2 pixel = outline_thickness / VIEWPORT_SIZE;

    // Sample depth at 4 neighbors
    float depth_center = getLinearDepth(SCREEN_UV, INV_PROJECTION_MATRIX);
    float depth_left   = getLinearDepth(SCREEN_UV + vec2(-pixel.x, 0.0), INV_PROJECTION_MATRIX);
    float depth_right  = getLinearDepth(SCREEN_UV + vec2( pixel.x, 0.0), INV_PROJECTION_MATRIX);
    float depth_up     = getLinearDepth(SCREEN_UV + vec2(0.0,  pixel.y), INV_PROJECTION_MATRIX);
    float depth_down   = getLinearDepth(SCREEN_UV + vec2(0.0, -pixel.y), INV_PROJECTION_MATRIX);

    // Depth edge: difference between opposing neighbors
    float depth_diff = abs(depth_left - depth_right) + abs(depth_up - depth_down);
    float depth_edge = smoothstep(depth_threshold * 0.1, depth_threshold, depth_diff);

    // Sample normals at 4 neighbors
    vec3 normal_center = texture(NORMAL_TEXTURE, SCREEN_UV).rgb * 2.0 - 1.0;
    vec3 normal_left   = texture(NORMAL_TEXTURE, SCREEN_UV + vec2(-pixel.x, 0.0)).rgb * 2.0 - 1.0;
    vec3 normal_right  = texture(NORMAL_TEXTURE, SCREEN_UV + vec2( pixel.x, 0.0)).rgb * 2.0 - 1.0;
    vec3 normal_up     = texture(NORMAL_TEXTURE, SCREEN_UV + vec2(0.0,  pixel.y)).rgb * 2.0 - 1.0;
    vec3 normal_down   = texture(NORMAL_TEXTURE, SCREEN_UV + vec2(0.0, -pixel.y)).rgb * 2.0 - 1.0;

    // Normal edge: how much normals diverge from center
    float normal_diff = 0.0;
    normal_diff += 1.0 - dot(normal_center, normal_left);
    normal_diff += 1.0 - dot(normal_center, normal_right);
    normal_diff += 1.0 - dot(normal_center, normal_up);
    normal_diff += 1.0 - dot(normal_center, normal_down);
    float normal_edge = smoothstep(normal_threshold, normal_threshold * 2.0, normal_diff);

    // Combine: either signal triggers the outline
    float edge = max(depth_edge, normal_edge);

    ALBEDO = outline_color.rgb;
    ALPHA = edge * outline_color.a;
}

Setting up the full-screen quad

  1. Add a MeshInstance3D as a child of your Camera3D
  2. Set its Mesh to a QuadMesh with size (2, 2)
  3. Set Transform → Position to (0, 0, -1) — one unit in front of camera
  4. Assign a new ShaderMaterial with toon_outline_screen.gdshader
  5. In the material, set Render Priority to 1 (draws after scene)
Why depth_test_disabled? Without it, the quad would be occluded by scene geometry (it's only 1 unit from camera). In Godot 4.4+, this render mode is required for screen-space post-process shaders to work correctly — without it, outlines only appear against the sky.
New concept — hint_normal_roughness_texture: Godot's G-buffer stores surface normals (and roughness in the alpha channel) in a texture accessible via this sampler hint. Only available in Forward+ and Mobile renderers — NOT in Compatibility. This is why screen-space outlines don't work on all platforms. Docs: Spatial Shader

Try it: Adjust depth_threshold and normal_threshold independently. Depth edges catch silhouettes and object boundaries. Normal edges catch surface creases and hard edges within a single mesh. Lower thresholds = more lines; higher = only the strongest edges.

Comparison: When to Use Each

CriterionInverted HullScreen-Space
Internal edges (creases, folds)NoYes
Per-object controlYes (different width/color per mesh)No (scene-wide uniform settings)
Renderer supportAll (Forward+, Mobile, Compatibility)Forward+ and Mobile only
Mesh preparation neededYes (smooth normals, or vertex colors)None
Hard-edge artifactsYes (spiky on low-poly)No
PerformanceCheap (1 extra pass per outlined mesh)Moderate (9 texture samples per pixel)
Transparent objectsWorksDoesn't detect (no depth written)
When to use which:
  • Inverted hull — use for characters and key props where you need per-object artistic control (hero gets thick outlines, background props get thin). Works on all renderers including Compatibility/web.
  • Screen-space — use for production environments where every surface should have consistent outlines and you want internal edge detail. The better visual result for most scenes.
  • Both combined — the industry standard. Characters get inverted hull (artistic control over thickness). Environment gets screen-space (automatic coverage of all geometry). This is what Guilty Gear, Hi-Fi Rush, and Borderlands do.
Default recommendation: Start with screen-space (better visual quality, zero mesh prep). Add inverted hull only on specific characters that need custom outline thickness.
Inverted Hull: Per-object control, silhouette only, all renderers, cheap, needs smooth normals
Screen-Space: All edges, scene-wide, Forward+/Mobile only, no per-object control, no mesh prep, production quality

Check Your Understanding

Exercise: A colleague adds the inverted hull outline to their character but reports two problems:

  1. The outline is thick when the camera is close but vanishes when zoomed out
  2. The character's sword (a thin, sharp-edged mesh) has spiky artifacts on the outline

For each problem: what's causing it, and what would you change?

Hint

Problem 1: Think about what coordinate space the inflation happens in. Problem 2: Think about what NORMAL means on a hard-edge mesh.

Answer

1. Outline vanishes at distance: They're using the basic version (VERTEX += NORMAL * width) which inflates by a fixed world-space amount. At distance, that amount maps to sub-pixel thickness. Fix: use the view-space version that multiplies by -clip_pos.z so the inflation scales with distance.

2. Spiky artifacts: Hard-edge meshes have split normals at sharp edges — the same vertex has different normals for each face it belongs to. When inflated along these normals, adjacent faces push apart, creating gaps and spikes. Fix: either (a) add a smooth-normal layer to the mesh in Blender (split into a separate UV channel), or (b) use vertex colors to paint per-vertex outline direction, or (c) use the radial expansion variant that pushes outward from the object center instead of along normals.
