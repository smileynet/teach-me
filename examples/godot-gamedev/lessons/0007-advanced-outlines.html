Advanced Outlines — Per-Object & Wide

Lesson 7 · Godot Toon Shaders · ~15 min read
Win: You can implement a dual-viewport color-ID outline system for per-object screen-space control, explain how JFA builds distance fields for arbitrarily wide outlines, and select the right technique for any art direction.
After this lesson: You understand two advanced outline architectures — dual-viewport color-ID (per-object control without geometry modification) and JFA distance fields (pixel-perfect at any width) — and can articulate which of the four total techniques fits a given production scenario.

The Gap Between Hull and Sobel

The previous lesson taught two fundamental approaches:

  • Inverted hull — per-object control, but geometry-based (needs mesh prep for hard edges, silhouette only)
  • Screen-space Sobel — image-based (no mesh prep, catches creases), but no per-object control (everything gets the same outline)

What if you need both — screen-space quality (consistent pixel width, no mesh prep) AND per-object control (different colors, toggle per object)? And what if you need outlines wider than the 1–3px that Sobel handles well?

This lesson introduces two techniques that solve these problems: a dual-viewport color-ID approach for per-object screen-space outlines, and the Jump Flood Algorithm (JFA) for wide outlines at any pixel width.

Dual-Viewport Color-ID Outlines

The idea: render the scene twice into separate viewports. The first viewport renders normally. The second renders every object as a flat color (its "ID color"). A post-process shader then finds pixels where the ID color changes — those are the outlines. Since each object has its own ID color, you get per-object control while operating entirely in screen space. [SimonPiCarter: Pixel Outline Demo]

Architecture: Render Layers + CAMERA_VISIBLE_LAYERS

The trick is that both cameras see the same objects — but the shader outputs different colors depending on which camera is rendering. Godot's CAMERA_VISIBLE_LAYERS built-in tells the shader which camera's cull mask triggered this draw call:

shader_type spatial;
render_mode unshaded;

uniform vec4 original_color : source_color = vec4(1.0);
uniform vec4 outline_color : source_color = vec4(1.0, 0.0, 0.0, 1.0);

// Bit masks for render layers
const int LAYER_NORMAL = 1;    // Layer 1: normal render
const int LAYER_OUTLINE = 16;  // Layer 5: color-ID render (1 << 4)

void fragment() {
    if ((int(CAMERA_VISIBLE_LAYERS) & LAYER_NORMAL) != 0) {
        // Camera A sees us — render normally
        ALBEDO = original_color.rgb;
    } else if ((int(CAMERA_VISIBLE_LAYERS) & LAYER_OUTLINE) != 0) {
        // Camera B sees us — output flat ID color for edge detection
        ALBEDO = outline_color.rgb;
    }
}

Each object's outline_color uniform is its unique identifier. Objects that should share an outline boundary get different colors. Objects that shouldn't outline against each other get the same color.

New concept — CAMERA_VISIBLE_LAYERS: A shader built-in that exposes which render layers the current camera can see (its cull_mask). By checking specific bits, a single shader can branch its behavior per camera — rendering lit color for the main camera and flat ID color for the outline camera. This avoids duplicating materials.
Simplified example: This shader uses render_mode unshaded for clarity, so both branches output flat color. In production, you'd use your normal lit toon shader (e.g., toon_bands) for the main viewport and only the flat color-ID output for the outline camera — either via two separate materials on different render layers, or by adding the CAMERA_VISIBLE_LAYERS branch to your existing toon shader. The outline SubViewport's clear color must have alpha = 0 (transparent) so the background doesn't generate false outlines.

The Edge Detection Shader (Canvas Post-Process)

The outline camera's viewport renders flat-colored silhouettes. A canvas_item shader composited on top detects where adjacent pixels have different colors — those color boundaries are the outlines:

shader_type canvas_item;

uniform vec4 outline_color : source_color = vec4(0.0, 0.0, 0.0, 1.0);
uniform float outline_width : hint_range(0.5, 8.0) = 1.0;

const vec2 DIRECTIONS[8] = {
    vec2(1.0, 0.0), vec2(0.0, 1.0), vec2(-1.0, 0.0), vec2(0.0, -1.0),
    vec2(1.0, 1.0), vec2(-1.0, 1.0), vec2(-1.0, -1.0), vec2(1.0, -1.0)
};

void fragment() {
    vec4 center = texture(TEXTURE, UV);
    float edge = 0.0;

    // Compare center pixel to 8 neighbors
    for (int i = 0; i < 8; i++) {
        vec2 offset = DIRECTIONS[i] * TEXTURE_PIXEL_SIZE * outline_width;
        vec4 neighbor = texture(TEXTURE, UV + offset);

        // Color difference = different objects = edge
        float diff = abs(neighbor.r - center.r)
                   + abs(neighbor.g - center.g)
                   + abs(neighbor.b - center.b);

        // Only outline if neighbor is "behind" (lower alpha or black background)
        float is_boundary = step(0.01, diff);
        edge = max(edge, is_boundary);
    }

    COLOR.rgb = outline_color.rgb;
    COLOR.a = edge * center.a; // No outline on transparent background
}

The logic is simple: if any neighbor pixel has a different color than the center pixel, this is an edge. Multiply by center.a so transparent background areas don't generate outlines.

Scene Setup

The architecture requires two SubViewports with synchronized cameras:

  1. All meshes: Set layers to include both layer 1 (normal) and layer 5 (outline)
  2. Main SubViewport: Camera with cull_mask that includes layer 1 but NOT layer 5
  3. Outline SubViewport: Camera with cull_mask that includes layer 5 but NOT layer 1
  4. CanvasLayer: Two TextureRect nodes — one showing the main viewport, one showing the outline viewport with the edge detection shader
  5. Camera sync: Use a RemoteTransform3D on the main camera targeting the outline camera (keeps them in lockstep)
Performance cost: This technique renders the scene twice — every object is drawn in both viewports. For simple scenes this is fine. For complex scenes with many draw calls, consider limiting which objects participate in the outline pass (remove layer 5 from background props that don't need outlines).
When to use dual-viewport over inverted hull: When you need per-object outline colors AND consistent pixel width without worrying about mesh topology (no smooth normals baking). The trade-off is doubled render cost and more complex scene setup. Use it for selection highlights, interaction feedback, or stylized games where every object needs its own outline color.

Jump Flood Algorithm (Wide Pixel-Perfect Outlines)

Both the screen-space Sobel (from the previous lesson) and the dual-viewport approach above produce outlines that are 1–8 pixels wide at most. Increase the sample radius further and you get artifacts — gaps at corners, inconsistent thickness, fuzzy edges. The fundamental problem: edge detection doesn't understand distance from the edge. [Ben Golus: The Quest for Very Wide Outlines]

The Jump Flood Algorithm (JFA) solves this by computing a distance field — every pixel knows exactly how far it is from the nearest edge. That distance drives the outline: if distance < threshold, draw outline color. The result is mathematically clean at any width — 5px or 500px — with O(log₂ n) cost.

How JFA Works

JFA builds a distance field in three stages:

  1. Extraction: Run edge detection (Sobel on viewport color). Pixels at edges become "seeds" and store their screen coordinates. Non-seeds get a sentinel value.
  2. Jump Flood (repeated N times): Each pass, every pixel checks 8 neighbors at a decreasing grid offset (128, 64, 32, 16, 8, 4, 2, 1). If a neighbor has a closer seed, adopt it. After all passes, every pixel knows its nearest edge pixel.
  3. Overlay: Compute distance to nearest seed. If within threshold, draw outline. The smooth distance field allows anti-aliasing, gradients, and glow effects for free.

The key insight: each JFA pass doubles the propagation range. A 100-pixel outline costs the same as a 64-pixel one — both need 7 passes. This is why JFA outperforms naive dilation (which needs N passes for N-pixel width).

JFA in Godot

JFA requires multi-pass rendering with ping-pong textures. Two community implementations handle the orchestration:

When to use which JFA implementation:
  • pink-arcana/godot-distance-field-outlines (150★, MIT) — CanvasItem version (all renderers + web) and CompositorEffect version (Forward+ only, faster). Best for learning.
  • L0UARN/godot-outlines (MIT) — C# + compute shaders via CompositorEffect. Supports per-node outline colors.
Default: Start with pink-arcana's DFOutlineNode (CanvasItem) — works everywhere, simplest to understand.

The core flood pass — the essential algorithm that runs N times with halving offsets (adapted from pink-arcana, MIT):

shader_type canvas_item;
render_mode blend_mix;

uniform sampler2D in_texture : hint_screen_texture, filter_nearest;
uniform float offset; // Halves each pass: 128, 64, 32, 16, 8, 4, 2, 1
uniform float distance_denominator;
uniform bool last_pass;

const vec2 NEIGHBOR_OFFSETS[8] = {
    vec2(-1.0,-1.0), vec2(0.0,-1.0), vec2(1.0,-1.0),
    vec2(-1.0,0.0),                   vec2(1.0,0.0),
    vec2(-1.0,1.0),  vec2(0.0,1.0),  vec2(1.0,1.0) };

void fragment() {
    vec2 texture_size = vec2(textureSize(in_texture, 0));
    vec2 pixel_size = 1.0 / texture_size;
    vec2 tex_coord = UV / pixel_size;

    vec4 seed_color = texelFetch(in_texture, ivec2(tex_coord), 0);
    vec2 seed_coord = seed_color.rg * texture_size;
    bool valid_seed = seed_color.a > 0.5;
    float min_dist_sq = valid_seed ? distance(tex_coord, seed_coord) : 1000000.0;
    min_dist_sq = min_dist_sq * min_dist_sq;

    for (int i = 0; i < 8; i++) {
        vec2 neighbor_coord = tex_coord + NEIGHBOR_OFFSETS[i] * offset;
        neighbor_coord = clamp(neighbor_coord, vec2(0.0), texture_size - vec2(1.0));

        vec4 neighbor_color = texelFetch(in_texture, ivec2(neighbor_coord), 0);
        if (neighbor_color.a < 0.5) continue;

        vec2 neighbor_seed = neighbor_color.rg * texture_size;
        float dist_sq = distance(tex_coord, neighbor_seed);
        dist_sq = dist_sq * dist_sq;

        if (dist_sq < min_dist_sq) {
            min_dist_sq = dist_sq;
            seed_coord = neighbor_seed;
            seed_color = neighbor_color;
            valid_seed = true;
        }
    }

    if (last_pass) {
        float dist = valid_seed ? sqrt(min_dist_sq) / distance_denominator : 1.0;
        COLOR = vec4(dist, 0.0, 0.0, 1.0);
    } else {
        COLOR = valid_seed ? vec4(seed_coord / texture_size, 0.0, 1.0) : vec4(0.0);
    }
}

Each invocation halves offset. After all passes, every pixel contains its normalized distance to the nearest seed. The overlay pass thresholds this to produce the final outline.

Why JFA is more complex to set up: Unlike single-shader techniques, JFA needs orchestration — multiple render passes with intermediate textures. In Godot, the CanvasItem version uses SubViewports (ping-ponging between them each pass). The CompositorEffect version uses compute dispatches. Both addons handle this automatically — you don't write the multi-pass loop yourself.

You now have four outline techniques across two lessons. The progression builds competence: each technique teaches a new shader architecture pattern.

The decision tree:
  • Need per-object control + consistent pixel width? → Dual-viewport color-ID. Best when you can afford the double render.
  • Need thin outlines everywhere with internal creases? → Screen-space Sobel. Zero setup, catches every fold.
  • Need per-object control but can modify meshes? → Inverted hull (cheapest, all renderers).
  • Need wide outlines (10+ pixels) or effects? → JFA. Only technique with clean results at any width.
  • Targeting Compatibility/web? → Hull (always works) or JFA CanvasItem version.

The Production Combination

Shipped games combine techniques by category — Guilty Gear Strive, Hi-Fi Rush, Genshin Impact, and Borderlands all use multiple approaches simultaneously:

  • Characters: Inverted hull (artistic control over thickness per body part, smooth normals baked)
  • Environment: Screen-space Sobel (automatic coverage, catches every architectural crease)
  • Selection/Interaction: Dual-viewport or JFA (wide glowing outlines for the selected object)

The learning progression mirrors this: hull teaches vertex manipulation, Sobel teaches buffer access, dual-viewport teaches multi-viewport architecture, JFA teaches multi-pass algorithms. Each builds competence the next assumes.

Check Your Understanding

Exercise: Your art director wants three different outline styles in the same scene:

  • The player character needs a thick (8px) outline with per-limb width control
  • Environmental architecture (all hard-edge cubes and pillars) needs thin outlines at every crease
  • The selected interactable object needs a wide (30px) glowing highlight

Which technique would you use for each, and why can't the others do the job?

Hint

Think about what each technique excels at: per-object control, internal edges, outline width range, effects support. One technique fails on wide outlines. One can't do per-object. One can't detect creases.

Answer

Character (8px, per-limb): Inverted hull — per-mesh width/color control, cheapest option that gives artistic per-limb control. Needs smooth normals baked if the character has hard edges. Dual-viewport could also work but is more expensive and doesn't offer per-limb variation as naturally.

Architecture (thin, every crease): Screen-space Sobel — detects internal edges (normal discontinuities) which no other technique can. Works perfectly on hard-edge geometry without mesh prep. The others only catch silhouettes.

Selection highlight (30px, glowing): JFA distance field — the only technique producing pixel-perfect wide outlines. The distance field naturally supports glow/gradient effects. Screen-space maxes out at ~3px. Dual-viewport maxes at ~8px before artifacts. Hull at 30px world-space distorts badly.
