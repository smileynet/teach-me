Palette Snapping — Color Ramp and 1D Lookup

Lesson 17 · Blender to Godot Texture Prep · ~15 min read
Win: You can map any albedo to an art-directed palette two ways — an editable Constant Color Ramp and a scalable 1D lookup texture — explain when to reach for each, and reason about why palette color count and shader band count are independent.
After this lesson: Posterization asks how many colors; palette snapping asks which colors. Snapping every pixel to a shared, deliberately-designed palette is what makes a whole scene of independently-prepped assets look like one art direction.

The Problem

In the previous lesson you built a node group that posterizes an albedo to N flat bands. That controls how many colors survive — but not which ones. Posterizing the barrel gives you four tones, but they're whatever the photo happened to average to: muddy mid-browns nobody chose. Posterize a crate beside it and you get a different four browns. The scene fragments into assets that were each simplified correctly but don't share a color story.

The fix is palette snapping: map every pixel to the nearest color in a fixed, art-directed palette. Now the barrel, the crate, and the character all draw from the same six colors — instant scene cohesion, and a palette you can redesign in one place. This lesson builds it two ways in Blender nodes.

Snapping is a lookup keyed on brightness

Both methods share one idea: collapse a pixel's color to a single luminance value (how bright it is), then use that number to pick a palette swatch. A dark pixel picks the shadow color, a bright pixel picks the highlight color, and the mid-tones fill in between. The luminance-to-slot map is the same floor quantization posterization used, but instead of producing a grey level it produces a palette index:

lum = luminance(color)              // 0..1, via RGB to BW
idx = floor(lum * N)                // which of N palette slots, 0..N-1
snapped = palette[idx]              // the chosen swatch

The two methods differ only in how they store palette[] and do the lookup — a Color Ramp, or a tiny image sampled as a table. We'll build both as node groups so they chain onto lesson 16's Posterize RGB group.

Method A — Color Ramp with Constant interpolation

The quickest, most visual approach uses a single Color Ramp node. Convert the color to luminance with RGB to BW, feed that into the ramp's Fac, and place one color stop per palette entry.

Image Texture (Color) ─▶ RGB to BW ─▶ Color Ramp [CONSTANT] ─▶ Base Color

The critical setting is the ramp's interpolation mode: Constant. By default a Color Ramp blends smoothly between stops (Linear) — which would give you a gradient, the opposite of what you want. Constant makes each stop hold its exact color until the next stop, producing hard, flat bands. Place your six swatches at positions 0, 1/6, 2/6, … and every luminance snaps to the swatch on its left.

New concept — Constant interpolation: A Color Ramp mode where each color stop holds until the next, with no blending. This is what turns a ramp from a gradient generator into a discrete lookup table. It's the node-editor equivalent of the shader's floor.

Method A is ideal when you're designing the palette by eye: drag a stop, watch the band recolor live in the viewport. Its limit is that it keys on a single 0→1 axis (luminance), so it can't express a palette that varies by hue independent of brightness.

Method B — 1D palette texture (a lookup table)

The scalable approach stores the palette as a tiny N×1-pixel image — one pixel per swatch — and samples it as a color lookup table. Instead of ramp stops living inside one material, the palette is a shareable asset: point ten materials at the same strip and they snap to one palette; edit the strip and the whole scene updates.

Luminance becomes the horizontal coordinate into the strip. A Combine XYZ node builds a lookup position with the luminance on X (and a fixed Y=0.5 to sample the middle of the one-pixel-tall image):

Image Texture ─▶ RGB to BW ─▶ Combine XYZ (X=lum, Y=0.5) ─▶ Palette Strip [Closest]

Two settings make or break this method. First, the palette Image Texture's interpolation must be Closest, not Linear — Linear would blend adjacent swatches and defeat the whole point. Second, the palette strip's color space must be Non-Color, so Blender stores your authored swatches verbatim instead of applying an sRGB view transform that would shift every color.

Rather than hand-place pixels, this script builds the strip and the sampling group in one run. Open it in Blender's Scripting workspace and press Run, then add Group → Palette Snap B (LUT) to any material.

import bpy

# 6-color warm-toon palette (sRGB), darkest -> lightest.
PALETTE = [
    (0.101, 0.078, 0.145), (0.239, 0.157, 0.216), (0.451, 0.247, 0.235),
    (0.647, 0.400, 0.271), (0.831, 0.596, 0.361), (0.965, 0.831, 0.569),
]
N = len(PALETTE)

def build_palette_image():
    img = bpy.data.images.new("toon_palette_6", width=N, height=1, alpha=False)
    img.colorspace_settings.name = "Non-Color"   # don't view-transform the swatches
    px = []
    for (r, g, b) in PALETTE:
        px += [r, g, b, 1.0]
    img.pixels = px
    return img

def build_lut_group():
    ng = bpy.data.node_groups.new("Palette Snap B (LUT)", "ShaderNodeTree")
    ng.interface.new_socket("Color", in_out="INPUT", socket_type="NodeSocketColor")
    ng.interface.new_socket("Color", in_out="OUTPUT", socket_type="NodeSocketColor")
    nodes, links = ng.nodes, ng.links
    gin, gout = nodes.new("NodeGroupInput"), nodes.new("NodeGroupOutput")

    bw = nodes.new("ShaderNodeRGBToBW")
    combine = nodes.new("ShaderNodeCombineXYZ")
    combine.inputs["Y"].default_value = 0.5       # middle of the 1px-tall strip
    tex = nodes.new("ShaderNodeTexImage")
    tex.interpolation = "Closest"                 # REQUIRED — no blending
    tex.extension = "EXTEND"
    tex.image = build_palette_image()

    links.new(gin.outputs["Color"], bw.inputs[0])
    links.new(bw.outputs[0], combine.inputs["X"]) # luminance drives the lookup
    links.new(combine.outputs["Vector"], tex.inputs["Vector"])
    links.new(tex.outputs["Color"], gout.inputs["Color"])
    return ng

if __name__ == "__main__":
    build_lut_group()
Gotcha — sample the texel center, not its edge. Luminance maps to a lookup coordinate, and you want it to land in the middle of a swatch's pixel: (idx + 0.5) / N. If a value lands exactly on a texel border (idx / N), floating-point jitter can tip Closest into the neighbouring swatch — an off-by-one that shows up as a wrong color at band edges. Sampling from a quantized luminance keeps you at centers. (The lesson's oracle sweeps this: center-sampling has zero off-by-one; edge-sampling misses all five interior borders.)

Which method?

When to use which:
  • Method A — Color Ramp (Constant): use when you're hand-designing the palette and want to drag stops and see bands recolor live. Fastest to iterate; best with a handful of colors on a single material.
  • Method B — 1D lookup texture (Closest): use when many assets must share one palette, or you want the palette swappable at runtime — sample the same strip in a Godot shader instead of baking it in (see the runtime palette_snap.gdshader in the color-simplification lesson for the nearest-color counterpart).
Default: design with Method A, ship with Method B. The ramp is your studio; the lookup texture is the reusable, swappable production asset.

Designing a palette that reads

A snap is only as good as its palette. A few principles make six colors read as a coherent, lit surface rather than six random paints:

  • Value first. The swatches are brightness steps — order them darkest to lightest and make them readable in greyscale. If the values are right, the hues can be almost anything.
  • Hue-shift across the ramp. Don't just darken one color. Shift shadows cooler (toward blue/violet) and highlights warmer (toward yellow/orange), ~15–20° of hue per step. This temperature contrast is what makes a flat band read as a lit volume.
  • Saturation peaks in the midtones. Pull saturation down at both the darkest and lightest ends; never pair maximum saturation with maximum brightness (it "burns").

The palette in the script above follows this: a cool violet-black shadow, warming through plum and brown to a warm tan and cream highlight — six steps of rising value with a cool-to-warm hue drift.

The combined Toon Prep chain

Palette snapping composes with lesson 16's group. Chain them into one reusable flow and bake the result through an Emission node (light-independent flat output):

Image Texture ─▶ Posterize RGB ─▶ Palette Snap ─▶ Emission ─▶ (bake) Base Color

Posterize first flattens the color count; snap then maps those flattened tones onto your palette. Baking freezes the result into a new texture — cheap at runtime, but the palette is now fixed. If you want to recolor later, skip the bake and keep Method B's strip as a live, swappable texture in your Godot material.

Check Your Understanding

Exercise: A teammate has a 4-band toon shader and a beautiful 8-color palette. They snap their character's albedo to all 8 colors expecting richer shading, but on the lit model they only ever see 4 flat colors — half the palette seems to do nothing. They ask you why the extra colors "aren't showing up," and whether adding more palette colors would fix it. What do you tell them?

Hint

What decides how many distinct tones appear on the lit model — the palette, or the shader? Which stage samples which?

Answer

Band count and palette count are independent axes. The shader decides how many lighting bands exist (here, 4); the palette only decides which color each band shows. With 4 bands sampling an 8-color palette, only ~4 swatches are ever hit — the other 4 are never selected, which is exactly why half the palette "does nothing." Adding more palette colors makes this worse, not better: you can't create more visible tones by adding swatches, because nothing samples them.

To get more distinct tones on the lit model, they must add lighting bands in the shader (and supply a deliberately hue-shifted swatch per band). If instead they want the 8 colors to appear in the albedo texture itself (independent of lighting), that's the bake path from this lesson — snapping the albedo to 8 shows all 8 in the base color, before the shader's 4-band lighting is applied on top. The fix depends on which they actually want: richer lighting → more bands; richer base color → the albedo snap already does it.
