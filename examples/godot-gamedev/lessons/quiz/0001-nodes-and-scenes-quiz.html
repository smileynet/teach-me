Why does Godot prefer composition (combining nodes) over inheritance (deep class hierarchies)?

Should mention: (1) composition keeps scenes self-contained and reusable — each component has one job, (2) Has-A is more flexible than Is-A, (3) a character doesn't inherit from Damageable — it HAS a Health component as a child.

Explain the "signal up, call down" rule and why it matters for scene reusability.

Should mention: (1) children emit signals (observer pattern — don't know who listens), (2) parents call $Child.method() directly, (3) siblings never talk directly. Why: keeps scenes self-contained — a Health node works in any game because it signals rather than referencing specific objects.

apply

Design a chest that opens when the player approaches. What nodes would you compose and how would it communicate?

Should mention: (1) Area2D for proximity detection, (2) Sprite2D for visuals, (3) AnimationPlayer for open animation, (4) emits an "opened" signal — level/spawner listens. The chest doesn't spawn loot itself — it signals what happened.

Section: Composition · Tags: area2d, signals, design
predict

What happens if you add a child node to a scene at runtime but forget to call add_child()? Where does it exist?

Should mention: (1) the node exists in memory but is NOT in the SceneTree, (2) it won't receive _ready(), _process(), or any callbacks, (3) it won't be visible, process physics, or respond to input. It's an orphan — allocated but inactive. You must add_child() to make it live.

How well could you explain this?

Section: Scene Tree · Tags: scene-tree, add-child, lifecycle
quick-check

Name the 3 lifecycle callbacks and when each fires:

_ready(): once when node + children enter tree. _process(delta): every rendered frame. _physics_process(delta): every physics tick (fixed 60/s).
