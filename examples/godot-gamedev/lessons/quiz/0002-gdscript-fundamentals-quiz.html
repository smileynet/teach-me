predict

A beginner puts movement code (move_and_slide) in _process() instead of _physics_process(). When would this break?

Should mention: (1) _process runs at variable rate — movement becomes inconsistent across machines, (2) _physics_process is fixed (60/s) regardless of framerate, (3) collision detection expects consistent timing — variable rate causes tunneling on lag spikes. Key: move_and_slide() belongs in _physics_process.

explain

Why must you use @onready for node references instead of assigning them at the top of the script?

Should mention: (1) at parse time the node tree doesn't exist — $Path would fail, (2) @onready defers until _ready() when children are in tree, (3) equivalent to assigning in _ready() but keeps declarations at the top of the file.

apply

When would you use @export vs a regular variable? Give an example of each.

Should mention: (1) @export for designer-tunable values visible in Inspector (speed, health, scene references), (2) regular var for internal state (current velocity, state machine state). Example: @export var speed := 200.0 vs var current_dir := Vector2.ZERO.

explain

Why use static typing (var x: float = 5.0) instead of dynamic (var x = 5) in GDScript?

Should mention: (1) catches type errors at write-time without running the game, (2) enables better editor autocomplete, (3) improves performance (optimized opcodes), (4) self-documenting code. Trade-off: slightly more verbose, but the safety and tooling benefits are worth it.

quick-check

Name the 3 lifecycle callbacks, when each runs, and what belongs in each:

_ready(): once when node enters tree — init, references, signals. _process(delta): every frame — visuals, UI, non-physics. _physics_process(delta): fixed 60/s — movement, collision, raycasts. Always multiply by delta.
