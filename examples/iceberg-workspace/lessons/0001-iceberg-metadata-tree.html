The Iceberg Metadata Tree

Lesson 1 · Apache Iceberg on AWS · ~10 min read
Win: You can explain how Iceberg tracks table state without a database — and why that matters for your customer's lakehouse.
After this lesson: You can explain the four metadata layers below the catalog, why they eliminate file listing, give snapshot isolation, and enable schema evolution — and what maintenance they require.

The Problem Iceberg Solves

A traditional data lake is just files in S3 with a schema bolted on top (think Hive metastore pointing at s3://bucket/table/year=2024/month=01/). This breaks in three specific ways that matter for your customer:

  • Listing is the bottleneck. To plan a query, the engine must list directories to discover files. At scale (millions of files), listing is slow and eventually rate-limited by S3.
  • No isolation. A reader scanning files mid-write sees partial data. There's no "transaction" — just files appearing.
  • Schema and partition changes are surgery. Changing a partition scheme means rewriting all existing data. Evolving a schema risks breaking downstream consumers.

Iceberg solves all three with a single design: it tracks exactly which files belong to a table at any point in time, in a metadata tree stored alongside the data. [Iceberg Spec]

The Metadata Tree

Below the catalog, Iceberg has four layers of metadata, each pointing to the next. The catalog itself is external to the table spec — it's just a pointer to get you started. [Iceberg Spec §Overview]

Catalog → Metadata File → Manifest List → Manifest Files → Data/Delete Files
The catalog says "where is the current version?" The metadata file holds schema, partitions, and snapshots (each snapshot points to a manifest list). Manifests say "which specific files, with what stats?"
LayerWhat it storesWhere it lives
Catalog (external) A pointer to the current metadata file (one per table) AWS Glue Data Catalog or REST catalog endpoint
Table metadata file Schema history, partition spec history, sort order, and a list of snapshots (each pointing to a manifest list) JSON in S3 (metadata/v*.metadata.json)
Manifest list One per snapshot — lists which manifest files are active, added, or deleted in that snapshot Avro in S3 (metadata/snap-*.avro)
Manifest file Lists data files AND delete files with per-file stats (row count, column min/max, null counts) Avro in S3 (metadata/*.avro)
Data files The actual table rows Parquet (or ORC/Avro) in S3 (data/)
Delete files (V2+) Track which rows have been deleted or updated — position deletes, equality deletes, or deletion vectors (V3) Parquet in S3 (data/)

Key detail: Snapshots are not a separate layer — they're JSON objects inside the metadata file. Each snapshot records a timestamp, a sequence number, and a pointer to its manifest list. This is the most commonly misunderstood aspect of the tree.

Why This Matters for Your Customer

No more file listing

Query engines read the manifest files to find exactly which data files to scan — they never list S3 directories. At scale (millions of files), S3 listing is slow and rate-limited, making it unusable for query planning. The manifests also carry column-level stats, so the engine can skip entire files that can't contain matching rows — the spec calls this scan planning with data filtering. [Iceberg Spec §Scan Planning]

How does pruning actually work?

Each manifest file records min/max values per column for every data file it references. When a query has a WHERE timestamp > '2024-06-01' predicate, the engine checks the manifest stats first. If a data file's max timestamp is 2024-05-15, that entire file is skipped without opening it. This can eliminate 90%+ of I/O for selective queries.

Snapshot isolation (MVCC)

Every write creates a new snapshot — a manifest list pointing to the file set as of that write. Readers see a consistent view by reading from a snapshot. Writers create a new snapshot atomically (the catalog pointer updates, or it doesn't). No partial reads, no coordination needed between readers and writers.

How does conflict detection work?

When a writer tries to commit, it checks whether the catalog's current pointer still matches the snapshot it started from. If another writer updated it in the meantime, the commit fails and the writer retries — re-reading the new snapshot, rewriting metadata against it, and attempting the commit again. On AWS Glue, this is implemented via conditional updates on the catalog entry.

Schema and partition evolution without rewrites

The metadata file stores schema history and partition spec history. Old data files keep their original schema and partitioning; new files use the new spec. The engine handles the translation at query time. Your customer's producers can evolve schemas without rewriting their lake. [Iceberg Docs]

The One-Liner to Remember

Iceberg is a file-tracking metadata tree on top of object storage — it gives you transactions, time travel, and schema evolution without a database, without rewriting data, and without listing directories.

Limitations Worth Knowing

Maintenance is mandatory, not optional. Every write adds metadata files and manifests. Without regular maintenance, metadata bloats, query planning slows, and S3 costs climb. This is the #1 and #2 production problem for Iceberg tables. [Iceberg: Table Maintenance]

Five operations must run regularly, in this order:

  1. Expire snapshots — remove old snapshot references (but not the files yet)
  2. Remove orphan files — delete files no longer referenced by any snapshot
  3. Rewrite manifests — merge small manifests into fewer large ones
  4. Compact data files — merge small data files into optimally-sized ones
  5. Remove delete files — apply pending deletes and remove the delete file overhead
What happens if you skip maintenance?

Metadata files accumulate without bound. Each query must read more manifests to plan. S3 API costs grow linearly with metadata volume. At a major streaming platform, skipping compaction for two months resulted in query planning taking 30+ seconds and S3 costs climbing to $60K/month on metadata reads alone.

  • Write concurrency is limited. On AWS Glue, the catalog pointer update is serialized — roughly 15 transactions per second. High-frequency writers (many small commits per second) will hit conflicts. Design for fewer, larger commits. [SageMaker Lakehouse]
  • Not a query engine. Iceberg is a table format — it doesn't execute queries. You still need Athena, Spark, Trino, etc. on top.
  • Catalog is a single point of coordination. Concurrent writers must go through the catalog for atomic commit. On AWS, Glue handles this — but see the TPS limit above.
When Iceberg isn't the answer: For tables under 100 GB, the metadata overhead adds friction with zero benefit — plain Parquet + Athena is simpler. For real-time sub-second visibility needs, Iceberg's batch atomicity model adds latency. For high-frequency keyed upserts (many small updates per second), Apache Hudi's record-level index is faster. Iceberg shines for large-scale analytics with concurrent readers/writers, schema evolution, and time travel — not every workload.

Key points to hit

A crawler still lists directories (slow at scale, rate-limited). It gives no isolation — a query mid-crawl sees partial state. And changing the partition scheme requires rewriting all existing data. Iceberg's metadata tree solves all three: manifests replace listing, snapshots give isolation, and versioned specs enable evolution without rewrites.
