Data Ingestion & Change Capture

The Ingestion Landscape

Data enters an Iceberg table via one of three patterns. Each has different latency, complexity, and operational characteristics:

Three ingestion patterns — batch, streaming, and CDC — differ in latency, commit frequency, and file-sizing behavior.

PatternLatencyComplexityFile sizingBest for
Batch Minutes to hours Low Large, well-sized files Scheduled loads, historical backfills
Streaming Seconds to minutes High Small files (needs compaction) Near-real-time analytics, event streams

Write Mechanics: COW vs MOR

Before talking about specific services, you need to understand how Iceberg handles writes — because this determines which ingestion patterns work well and which create pain.

Every write to Iceberg creates new files. Iceberg never modifies data in place. For appends, this is simple — write a new Parquet file, add it to the manifest, commit. For updates and deletes, there are two strategies.

Copy-on-Write (COW)

When you update or delete a row, the engine rewrites the entire data file containing that row — producing a new file without the deleted rows (or with the updated values). The old file is removed from the manifest.

  • Read performance: Excellent — readers see clean files with no extra work
  • Write cost: High — changing one row means rewriting potentially millions of rows in that file
  • When to use: Tables where reads vastly outnumber writes, or where updates touch whole partitions (e.g., daily dimension table refresh)

Merge-on-Read (MOR)

Instead of rewriting data files, the engine writes a small delete file that says "these rows in that data file are gone." Readers merge the delete file with the data file at read time. [Iceberg Spec §Delete Formats]

  • Write performance: Fast — small delete files are cheap to produce
  • Read cost: Higher — every scan must reconcile delete files against data files
  • When to use: High-frequency updates where write speed matters more than read speed (streaming CDC, frequent upserts)

The COW vs MOR comparison shows why this choice shapes your ingestion architecture.

AWS-specific: Athena supports merge-on-read only for updates and deletes. If your customer queries with Athena, they can't choose COW — and they'll pay the read-time merge cost on every query that touches updated rows. EMR Spark and Glue support both modes. [AWS Prescriptive Guidance]

Iceberg V3: Deletion Vectors

Iceberg V3 (supported on AWS since Nov 2025 in EMR 7.12, Glue, and SageMaker) introduces deletion vectors — a bitmap-based delete format that's faster than position delete files. Instead of listing row positions in a separate file, a deletion vector is a compact bitmap attached to a data file. Reads check one bitmap instead of joining against a delete file. [Iceberg Spec V3]

Batch Ingestion

Batch is the simplest and most common pattern. Scheduled jobs process accumulated data and write well-sized files to Iceberg.

AWS Glue ETL

Glue is the default choice for batch Iceberg writes on AWS. A Glue job reads from any source (S3, JDBC, Kafka), transforms data with Spark, and writes to an Iceberg table registered in the Glue Data Catalog.

  • Native Iceberg connector (no custom JARs needed since Glue 4.0+)
  • Supports both COW and MOR write modes
  • Can handle schema evolution during writes
  • Write-audit-publish pattern: write to a staging snapshot, validate, then commit
Why batch produces well-sized files

A batch job accumulates data (minutes to hours of events), then writes all at once. This naturally produces large data files (128-512 MB — Iceberg's sweet spot) because there's enough data per partition to fill a file. Contrast with streaming, where you must commit frequently and each commit may contain very little data per partition.

EMR Spark

For larger workloads or when you need full Spark control, EMR gives you the same Iceberg Spark integration with more tuning knobs: custom Spark configurations, cluster sizing, and Spark's native conflict resolution for concurrent writes.

Athena CTAS / INSERT INTO

For ad-hoc or simple transformations, Athena can write to Iceberg directly:

  • CREATE TABLE ... AS SELECT (CTAS) — creates a new Iceberg table from a query
  • INSERT INTO — appends to an existing table
  • MERGE INTO — upserts (merge-on-read only)

Good for light workloads and prototyping. Not suitable for heavy ETL — Athena's serverless model charges per-scan and gives you no control over file sizing.

Streaming Ingestion

Streaming is where Iceberg gets harder. The fundamental tension: stream processing wants to commit frequently (for low latency), but Iceberg wants large, infrequent commits (for file sizing and catalog TPS).

The streaming paradox: Every Iceberg commit creates at least one data file per partition. Commit every 30 seconds across 100 partitions = 2,880 files/hour = mandatory compaction or your table drowns in small files.

Amazon Data Firehose (direct Iceberg delivery)

Firehose can deliver directly to Iceberg tables — no Spark/Flink needed. It buffers records and writes Parquet files to S3, then commits to the Iceberg catalog.

  • Throughput cap: 5 MiB/s per delivery stream — not suitable for high-volume without fan-out [AWS Prescriptive Guidance]
  • Buffers by size (minimum 64 MB) or time (minimum 60s) before committing
  • Append-only — no updates or deletes
  • Lowest operational complexity for moderate-volume append streams
When Firehose fits your customer's use case

If the source is under 5 MiB/s and only needs appends (event logs, clickstream, telemetry), Firehose is the simplest streaming path. No clusters to manage, automatic retry, dead-letter queue for failures. The 60-second minimum buffer helps with file sizing — you won't get the tiny-file problem as badly as with Flink checkpointing every 10 seconds.

Apache Flink on Amazon MSK / Kinesis

For higher throughput or when you need transformations on the stream, Flink (via Amazon Managed Service for Apache Flink, or self-managed on EMR) is the standard choice. Flink's Iceberg sink commits on every checkpoint.

  • Full transformation capability (joins, windowing, dedup)
  • Checkpoint interval = commit frequency (typically 30s–5min)
  • Produces small files that require aggressive compaction
  • Can handle updates/deletes via the Iceberg sink's upsert mode

The commit budget

Remember from Lesson 1: the Glue Catalog caps at roughly 15 commits per second. Every streaming job that commits to the same table shares that budget. Three Flink jobs checkpointing every 30 seconds to the same table = 6 commits/minute — well within budget. But 50 microservices each writing independently at 1-second intervals = conflict storm. [SageMaker Lakehouse]

Design rule: Funnel multiple producers through a single writer (a Flink job or Glue job) rather than having each producer commit directly. This consolidates commits and produces better-sized files.

Change Data Capture (CDC)

CDC keeps your lakehouse in sync with operational databases. A row changes in PostgreSQL or MySQL — that change flows to Iceberg as an insert, update, or delete.

The CDC pipeline

The standard CDC flow into Iceberg on AWS — DMS captures changes, a staging layer buffers them, and a merge job applies them to the Iceberg table.

AWS DMS (Database Migration Service)

DMS reads the database's write-ahead log (WAL/binlog) and emits change records. On AWS, DMS can target S3 directly (as Parquet or CSV), which then feeds a Glue/EMR job that applies the changes to Iceberg.

  • Full load + CDC: Initial snapshot of the entire table, then ongoing changes
  • Change records include: operation type (INSERT/UPDATE/DELETE), before/after values, transaction timestamp
  • DMS does NOT write to Iceberg directly — it lands changes to S3 or Kinesis, and a downstream job applies them

The MERGE pattern

The downstream job that applies CDC records to Iceberg typically uses MERGE INTO:

MERGE INTO target_table t
USING staged_changes s
ON t.id = s.id
WHEN MATCHED AND s.op = 'D' THEN DELETE
WHEN MATCHED AND s.op = 'U' THEN UPDATE SET *
WHEN NOT MATCHED AND s.op = 'I' THEN INSERT *

This is where COW vs MOR matters most. A MERGE touching 1,000 rows in a million-row partition:

  • COW: Rewrites the entire file (expensive but readers are fast later)
  • MOR: Writes a small delete file + new data file (fast but readers pay at scan time)
Alternative: Debezium → Kafka → Flink → Iceberg

For teams already running Kafka (MSK), Debezium can replace DMS as the change capture engine. Debezium reads the database WAL and publishes change events to Kafka topics. A Flink job then consumes these topics and writes to Iceberg using the Flink Iceberg sink's upsert mode. This eliminates the S3 staging layer but adds Kafka operational overhead. Better for teams that already have Kafka infrastructure and want sub-minute latency.

CDC frequency tradeoff

How often you run the MERGE job is a latency-vs-cost decision:

FrequencyLatencyCostFile impact
Every 5 min~5 minHigh (many small commits)Small files accumulate fast
Every hour~1 hourMediumReasonable file sizes
Every 6 hours~6 hoursLowWell-sized files

For most PoC lakehouse designs, hourly CDC is the sweet spot — fresh enough for analytics, infrequent enough to avoid the small-file tax.

The Small Files Problem

This is the single biggest operational concern with streaming and frequent CDC ingestion into Iceberg.

Why small files hurt: (1) More manifests to read during query planning → slower planning. (2) More files to open during scans → higher S3 GET costs and latency. (3) More metadata in the metadata tree → bigger snapshots. The cure is compaction (rewrite_data_files), but compaction itself consumes compute.

Iceberg's target file size is typically 128–512 MB. A streaming job checkpointing every minute with 10 partitions writes 600 files/hour — most far smaller than 128 MB unless volume is extremely high. After a day: 14,400 files that should have been ~100.

Design rule for your customer: Budget for compaction as a first-class part of the architecture, not an afterthought. If you're streaming into Iceberg, plan a scheduled compaction job (Glue or EMR) that runs frequently enough to keep the file count under control. A common pattern: compact hourly for hot partitions, daily for warm ones.

Choosing an Ingestion Strategy

Here's the decision framework for your customer's PoC:

Source typeLatency needRecommended pathWhy
Operational DB (Postgres, MySQL) Hourly is fine DMS → S3 → Glue MERGE Simple, well-sized files, manageable commits
Operational DB Minutes DMS → Kinesis → Flink MERGE Near-real-time CDC, but needs compaction budget
Event stream (moderate, <5 MiB/s) Minutes Firehose → Iceberg Zero-ops streaming, automatic buffering
Event stream (high volume) Seconds–minutes MSK → Flink → Iceberg Full control, needs compaction + monitoring
Periodic data exports Hours Glue batch ETL Simplest path, best file sizing, lowest cost
Backfill / migration One-time EMR Spark Full control over parallelism and file sizing

The One-Liner to Remember

Getting data INTO Iceberg is easy. Getting it in at the right size, frequency, and cost is the architecture problem. Every ingestion choice is a tradeoff between latency (how fresh?), file sizing (how many small files?), and commit frequency (how close to the 15 TPS ceiling?).

Check Your Understanding

Exercise: Your customer has three data sources: (1) a PostgreSQL orders database that needs hourly freshness in the lakehouse, (2) a clickstream at ~2 MiB/s that needs minute-level freshness, and (3) a daily vendor data dump in CSV. Design the ingestion architecture — which service for each source, and what maintenance do you need?

Key points to hit

(1) DMS → S3 → hourly Glue MERGE job for the orders DB. COW is fine at hourly frequency since you're only merging once per hour. (2) Firehose → Iceberg for clickstream — under 5 MiB/s, append-only, 60s buffer gives reasonable file sizes. (3) Glue batch ETL for the CSV dump — simplest path, daily schedule. Maintenance: scheduled compaction for the Firehose table (most small-file risk), less critical for the others since they produce fewer, larger files.
