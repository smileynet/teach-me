Quiz: Iceberg Metadata Tree

Read each question, form your answer, then reveal to check. Rate your confidence honestly.

explain

Why does Iceberg need a separate manifest list layer between the metadata file and the manifest files?

Should mention: (1) groups manifests into an atomic set for one snapshot — the metadata file points to ONE manifest list per snapshot, not N manifests, (2) enables atomic commit — swapping the catalog pointer changes the entire file set in one operation. Bonus: without this indirection, adding/removing manifests during a commit would require multiple pointer updates (non-atomic).

predict

What would happen to query planning if you skipped table maintenance (compaction) for several months on a heavily-written Iceberg table?

Should mention: (1) manifests accumulate — each write adds new ones, so query planning must read more files to discover which data to scan, (2) planning latency grows (30+ seconds in extreme cases), (3) S3 API costs climb linearly with metadata volume. Bonus: small data files also accumulate, hurting scan performance even after planning.

Your customer has a 50 GB table with simple append-only writes and no concurrent readers. They're evaluating Iceberg. What would you advise?

Should mention: (1) Iceberg adds metadata overhead with zero benefit at this scale — plain Parquet + Athena is simpler, (2) the maintenance burden (5 mandatory operations) isn't justified for a small append-only workload. Key insight: Iceberg's value appears at scale (concurrent access, schema evolution, time travel) — not every table needs it.

explain

Where do snapshots actually live in the Iceberg metadata tree? Why does this matter?

Should mention: (1) snapshots are JSON objects INSIDE the table metadata file (not a separate layer or file), (2) each snapshot contains a timestamp, sequence number, and pointer to a manifest list. Why it matters: the metadata file IS the version history — reading one file gives you access to all past states of the table (time travel).

explain

Why can't two Iceberg writers commit at exactly the same time on AWS? What limits the throughput?

Should mention: (1) the catalog pointer update is serialized — optimistic concurrency with compare-and-swap, (2) on AWS Glue, this is capped at ~15 TPS. Key insight: the catalog is a single-writer bottleneck by design — it's what makes commits atomic. High-throughput writes need fewer, larger commits (batch), not many small ones.
