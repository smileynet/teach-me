Your customer's streaming Flink job checkpoints every 30 seconds into an Iceberg table with 50 partitions. What operational problem will emerge within days, and what's the fix?

Should mention: (1) small files accumulate — each checkpoint creates at least one file per active partition = 100 files/minute = 144,000/day, most far under Iceberg's 128-512 MB target, (2) query planning slows as manifests grow, S3 GET costs rise, (3) fix is scheduled compaction (rewrite_data_files) — compact hourly for hot partitions, daily for warm. Bonus: could also increase checkpoint interval to reduce commit frequency.

explain

Explain the tradeoff between copy-on-write and merge-on-read to a data engineer who's deciding how to handle CDC merges into their Iceberg table.

Should mention: (1) COW rewrites entire data files on update/delete — expensive writes but readers see clean files, (2) MOR writes small delete files — fast writes but readers pay reconciliation cost at scan time, (3) for CDC: if MERGE runs hourly with large batches, COW is fine (amortized over many changes). If MERGE runs every few minutes, MOR avoids rewriting files repeatedly. Key: the choice depends on read/write ratio and merge frequency.

apply

Your customer wants sub-minute data freshness from their PostgreSQL orders database into the Iceberg lakehouse. They're considering DMS → S3 → Glue MERGE every 5 minutes. What problems will they hit, and what's a better architecture?

Should mention: (1) 5-minute MERGE produces small files that need aggressive compaction, (2) high commit frequency eats into the 15 TPS catalog budget, (3) COW MERGE every 5 min rewrites files repeatedly (wasteful). Better: DMS → Kinesis/MSK → Flink with Iceberg upsert sink using MOR mode. Flink handles the streaming merge continuously with configurable checkpoint intervals. Still needs compaction but avoids repeated batch MERGE overhead.

explain

Why can't 50 independent microservices each write directly to the same Iceberg table at 1-second intervals? What's the architectural fix?

Should mention: (1) the Glue Catalog pointer update is serialized via OCC — ~15 TPS limit, (2) 50 writers at 1/sec = 50 TPS → massive commit conflicts, retries, failures, (3) fix: funnel producers through a single writer (Flink job or Kafka → Glue batch). The writer consolidates many small records into fewer, larger commits. Key insight: Iceberg's commit model is designed for few large commits, not many small ones.

apply

Your customer uses Athena as their primary query engine. They're planning CDC ingestion with frequent updates. What constraint should you warn them about?

Should mention: (1) Athena supports merge-on-read ONLY — no COW option, (2) this means every query that touches updated rows pays the read-time merge cost (reconciling delete files against data files), (3) implication: if the table has heavy updates and heavy read workloads, Athena queries will be slower than they would with COW on EMR/Glue. May need to run compaction (remove_delete_files) more aggressively to keep read performance acceptable.
