Data Ingestion & Change Capture

Reference · Companion to Lesson 2

Core Concept

Get data from source systems into your analytics layer reliably. The choice between batch, streaming, and CDC determines your latency, cost, and complexity tradeoffs.

Write Mechanics

ModeHowWhen to use
Copy-on-Write (COW)Rewrites affected data files on every writeRead-heavy workloads, fewer writes
Merge-on-Read (MOR)Writes deltas, merges at query timeWrite-heavy workloads, CDC streams

Ingestion Strategies

StrategyLatencyComplexityUse when
Batch (scheduled)HoursLowReports, daily aggregates, historical loads
Micro-batchMinutesMediumNear-real-time dashboards, frequent updates
StreamingSecondsHighReal-time alerts, live features, event processing
CDCSeconds-minutesMedium-HighReplicating operational DB changes into analytics

Change Data Capture (CDC)

  • What: Captures row-level changes (INSERT/UPDATE/DELETE) from source databases
  • How: Reads the database's transaction log (WAL/binlog) — no source load
  • Tools: Debezium, AWS DMS, Fivetran, Airbyte
  • Output: Stream of change events → land in Iceberg as upserts via MOR

The Small Files Problem

  • Streaming/CDC produces many small files (one per micro-batch)
  • Too many small files → slow query planning, high S3 API costs
  • Fix: Run compaction regularly (merge small files into larger ones)
  • Rule of thumb: target 128-256 MB per data file

Decision Aid

"What ingestion strategy should I use?"

  • Data is in a database and you need near-real-time → CDC (Debezium/DMS)
  • Data arrives as events/messages → Streaming (Kafka → Flink/Spark)
  • Data is files or API dumps, daily is fine → Batch (Spark/Glue job)
  • Need faster than daily but streaming is overkill → Micro-batch (5-15 min Spark jobs)

"COW or MOR?"

  • Mostly reading, few updates → COW (read performance, no merge overhead)
  • Heavy updates/deletes, CDC workload → MOR (fast writes, merge on read)
  • Not sure → Start with COW, switch if write latency becomes a problem
