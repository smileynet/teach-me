Functions & Tunnels

Lesson 4 · Ink + Godot · ~14 min read
Win: You can write reusable ink logic — functions for inline computation, tunnels for portable scenes that return to their caller, and temp variables for scratch work within a knot.
After this lesson: You can extract repeated logic into functions (called inline in text), package reusable narrative scenes as tunnels (with full choices and flow), pass data into knots via parameters, and split growing stories across multiple files.

Temp Variables: Scratch Paper

In lesson 03, a note showed ~ temp roll = RANDOM(1,6) without fully explaining it. Here's the full picture: a temp variable is scratch space that exists only within the current knot. When flow leaves that knot, the temp is gone:

-> encounter

=== encounter ===
~ temp roll = RANDOM(1, 6)
~ temp success = roll >= 4
{success: You dodge the blow!|The hit connects.}
-> END

~ temp declares a local variable. Unlike VAR (which persists for the entire story), temps die when flow leaves the knot. Use them for calculations you need right now but never again — dice rolls, intermediate math, comparison results.

Why not just use VAR for everything? Because a story with 200 globally-named variables becomes impossible to reason about. Temps keep the global namespace clean — only state that matters across knots deserves a VAR.

Knot Parameters

What if you have one scene that works with different data — an accusation directed at three different suspects, or a shop selling different items? Parameters let you pass values into a knot at divert-time:

-> accuse("Hastings")

=== accuse(who) ===
"I accuse {who}!" Poirot declared.
"Really?" Japp replied. "{who}?"
"And why not?" Poirot shot back.
-> END

The parameter who acts like a temp variable inside the knot — it holds whatever value was passed in. You can pass strings, numbers, or booleans. Multiple parameters use commas: === trade(item, cost) ===.

Parameters solve the "almost identical knots" problem. Without them, you'd copy-paste a knot for each suspect/item/enemy. With them, one knot serves many callers — the data varies, the structure stays the same. Parameters are passed by value — the knot receives a copy of the data, not the original variable. Modifying a parameter inside doesn't affect the caller.

Functions: Inline Computation

Parameters make knots reusable. But what if you need a reusable calculation — something you can call inside a line of text? That's a function:

VAR health = 65

-> status

=== function describe_condition(hp) ===
{
- hp > 75:
    ~ return "strong"
- hp > 40:
    ~ return "battered"
- hp > 10:
    ~ return "barely standing"
- else:
    ~ return "near death"
}

=== status ===
You feel {describe_condition(health)}.
-> END

Two things make functions special: (1) they're declared with === function name() ===, and (2) they can be called inline with {function_name(args)} — the return value is inserted directly into the text. "You feel battered." — the function computed the word.

The trade-off: functions cannot contain choices, diverts, or stitches. They're pure computation — data in, value out. If you need choices or flow control in a reusable section, you need a tunnel (next section).

Functions That Don't Return

Not every function computes a value. Some just print text conditionally — a reusable prose snippet you can drop into any scene:

VAR gold = 12

-> town

=== function gold_status() ===
{
- gold > 15:
    Your purse is heavy with coin.
- gold > 5:
    You have a modest amount of gold.
- else:
    Your pockets are nearly empty.
}

=== town ===
{gold_status()}
The market awaits.
-> END

Calling {gold_status()} runs the function and prints whatever text its conditionals produce — but returns no value. This is useful for status descriptions you want consistent across scenes without copy-pasting the conditional logic.

New concept — the function contract: Functions cannot modify global variables, offer choices, or divert flow. They can read globals, accept parameters, use temps internally, and either return a value or print text. This constraint is what makes them safe to call inline — they can't disrupt the story's flow.

Tunnels: Sub-Scenes That Return

Functions are limited to computation. But what about a reusable scene — with choices, diverts, and multiple paths — that returns to where it was called? That's a tunnel:

VAR player_health = 80

-> forest

=== camp ===
The fire crackles. You rest and eat.
~ player_health = player_health + 20
{player_health > 100:
    ~ player_health = 100
}
* [Stare into the flames]
    The embers shift. Tomorrow will be harder.
* [Sleep immediately]
    Unconscious before your head hits the bedroll.
- Dawn breaks.
->->

=== forest ===
A quiet clearing.
* [Make camp]
    -> camp ->
    Refreshed, you continue. Health: {player_health}.
    -> forest
* [Continue onward]
    -> END

The key syntax: -> camp -> calls the tunnel (note the second -> after the knot name). Inside camp, the ->-> at the end means "return to the caller." Flow resumes right after -> camp -> — the line "Refreshed, you continue." prints after camp finishes.

Tunnels have full story capabilities — choices, diverts to other knots, variables, conditionals. The only rule: every path through the tunnel must end with ->-> (or divert to END/DONE). If you forget, the story silently stops — no compiler warning.

Gotcha — missing ->->: Unlike most ink errors, a tunnel that forgets to return doesn't produce a compile-time warning. The story just ends silently at that point. Always verify tunnels return by playing through every path.

When to Use What

You now have four reuse mechanisms. Here's when each one fits:

When to use which:
  • Temp variable — scratch calculation within one knot. Dies when flow leaves.
  • Parameter — pass data into a knot/function. One knot, many callers with different data.
  • Function — reusable computation or text snippet. Can call inline in text. Cannot use choices or diverts.
  • Tunnel — reusable scene with full story features. Runs and returns. Use for encounters, conversations, cutscenes.
  • Knot + divert — one-way jump. No return. Use when flow permanently moves to a new scene.
  • Stitch — sub-section within a knot. Use for local organization (hub-and-spoke within one location).
Rule of thumb: Can it be computed without choices? → Function. Does it need choices/flow but should return? → Tunnel. Is it a permanent scene change? → Knot + divert.

INCLUDE: Splitting Into Files

As stories grow, a single file becomes unwieldy. INCLUDE lets you split across files:

// main.ink
INCLUDE functions.ink
INCLUDE camp_scene.ink
INCLUDE forest.ink
INCLUDE cave.ink

-> forest_path

INCLUDE statements go at the top of your main file. They paste the contents of the included file at that position — there's no namespacing, no isolation. A function defined in functions.ink is callable from cave.ink as if they were one file.

Common organization patterns for larger projects:

  • By type: functions.ink, tunnels.ink, variables.ink, then scene files
  • By location: forest.ink, cave.ink, town.ink — each containing that area's knots
  • Shared + specific: shared/combat.ink, shared/camp.ink, then per-area files that call the shared tunnels
No namespacing: All INCLUDE'd files share one global namespace. Two functions named roll_dice in different files will conflict. Use prefixes if your project has many contributors: combat_roll_dice, social_roll_dice.

The Complete Reference Story

A forest-and-cave adventure where functions compute damage and describe health, tunnels handle reusable camp and battle scenes with full choices, and parameters let one battle knot serve multiple enemies:

// 04_functions_and_tunnels.ink
// Reference story for Lesson 04: Functions & Tunnels
// Demonstrates: temp variables, knot parameters, functions (with/without return),
//               tunnels (->knot->), ->->, INCLUDE concept, "when to use what"

VAR player_health = 100
VAR gold = 20

-> forest_path

// --- FUNCTIONS ---

=== function roll_dice(sides) ===
    ~ return RANDOM(1, sides)

=== function calculate_damage(base, armor) ===
    ~ temp result = base - armor
    {
    - result < 0:
        ~ return 0
    - else:
        ~ return result
    }

=== function describe_condition(hp) ===
    {
    - hp > 75:
        ~ return "strong"
    - hp > 40:
        ~ return "battered"
    - hp > 10:
        ~ return "barely standing"
    - else:
        ~ return "near death"
    }

=== function gold_text() ===
    {
    - gold > 15:
        Your purse is heavy with coin.
    - gold > 5:
        You have a modest amount of gold.
    - else:
        Your pockets are nearly empty.
    }

// --- TUNNELS ---

=== camp ===
The fire crackles. You rest your legs and eat dried provisions.
~ player_health = player_health + 20
{player_health > 100:
    ~ player_health = 100
}
You feel {describe_condition(player_health)}.
+ [Stare into the flames]
    The embers shift. Tomorrow will be harder.
+ [Sleep immediately]
    You're unconscious before your head hits the bedroll.
- Dawn breaks. Time to move.
->->

=== battle(enemy, enemy_attack, enemy_armor) ===
The {enemy} lunges at you!

~ temp enemy_roll = roll_dice(6) + enemy_attack
~ temp your_roll = roll_dice(6) + 3
~ temp damage_taken = calculate_damage(enemy_roll, 2)
~ temp damage_dealt = calculate_damage(your_roll, enemy_armor)

{
- your_roll > enemy_roll:
    You strike true! The {enemy} takes {damage_dealt} damage.
- your_roll == enemy_roll:
    Blades clash — neither lands a blow.
- else:
    The {enemy} hits you for {damage_taken} damage!
    ~ player_health = player_health - damage_taken
}

You feel {describe_condition(player_health)}.

{player_health <= 0:
    You fall. The {enemy} stands over you.
    -> defeat
}

+ [Press the attack] -> battle(enemy, enemy_attack, enemy_armor)
+ [Disengage and flee]
    You break away, gasping.
-
->->

// --- MAIN STORY ---

=== forest_path ===
The forest road is quiet. You are {describe_condition(player_health)}.
{gold_text()}

+ [Enter the dark grove]
    A wolf emerges from the shadows.
    -> battle("wolf", 2, 1) ->
    The wolf limps away. You find 5 gold on a nearby corpse.
    ~ gold = gold + 5
    -> forest_path

+ [Make camp for the night]
    -> camp ->
    -> forest_path

+ [Continue to the cave]
    -> cave_entrance

=== cave_entrance ===
The cave mouth yawns before you. Cold air seeps out.
{gold_text()}

+ [Enter the cave]
    A goblin shrieks and charges!
    -> battle("goblin", 3, 2) ->
    The goblin collapses. A glint of gold catches your eye.
    ~ gold = gold + 8
    -> cave_entrance

+ [Rest outside the cave]
    -> camp ->
    -> cave_entrance

+ {gold >= 15} [Pay the troll toll (15 gold)]
    ~ gold = gold - 15
    The troll steps aside with a grunt.
    -> victory

+ [Turn back to the forest]
    -> forest_path

=== victory ===
Beyond the troll, the pass opens into sunlit meadows.
You made it through — {describe_condition(player_health)} but alive.
{gold_text()}
-> END

=== defeat ===
Your journey ends here, in the dark.
-> END

Play through this multiple times — try fighting everything, try resting between battles, try saving gold for the troll toll. Notice how battle and camp are called from different locations but behave identically. That's the tunnel pattern: write once, call from anywhere, return to the caller.

Check Your Understanding

Exercise: Write a story with: (1) a function roll_dice(sides) that returns RANDOM(1, sides), (2) a tunnel === encounter(enemy) === that rolls the dice, prints "The {enemy} attacks for {damage}!" and offers "fight or flee" choices (with ->-> to return), (3) call the tunnel from two different knots with different enemy names. Verify both encounters return to their callers.

Hint

Structure: function at top (=== function roll_dice(sides) === with ~ return RANDOM(1, sides)), then the tunnel (=== encounter(enemy) === with ~ temp damage = roll_dice(6), text, choices, and ->->). Two calling knots that each do -> encounter("troll") -> then continue with local text.

Answer

Any structure with a function, a parameterized tunnel, and two callers works:

-> village

=== function roll_dice(sides) ===
~ return RANDOM(1, sides)

=== encounter(enemy) ===
~ temp damage = roll_dice(6)
The {enemy} attacks for {damage} damage!
* [Fight back]
    You swing wildly. The {enemy} staggers.
* [Flee]
    You turn and run.
-
->->

=== village ===
The village is under attack!
-> encounter("bandit") ->
You survived the village. Onward to the bridge.
-> bridge

=== bridge ===
A troll blocks the path.
-> encounter("troll") ->
The troll retreats. The road is clear.
-> END

The key insight: tunnels are portable scenes — the encounter doesn't know or care whether it was called from the village or the bridge. It runs its content, offers its choices, then ->-> returns control to wherever it was called from. This is how shipped games handle hundreds of reusable dialogue segments.
