First Godot Integration

Lesson 5 · Ink + Godot · ~15 min read
Win: You can load a compiled ink story in Godot, display its text on screen, and handle player choices through the InkPlayer runtime loop.
After this lesson: You can wire a compiled .ink.json into a Godot scene, drive it with continue-and-read, render choices as buttons, and read ink variables back into GDScript — the bridge from writing narrative to playing it.

From Writing to Playing

Lessons 01–04 taught you to write ink — knots, choices, variables, functions. You proved each story was correct without an engine: mise run ink:validate compiled it, and a golden transcript pinned its output. That validation-first habit pays off now. You are about to run the story inside Godot, and when something looks wrong you will already know the story itself is sound — the bug is in the wiring.

This lesson uses inkgd, the pure-GDScript ink runtime. It needs no .NET, so it runs anywhere Godot runs — the right fit for learning and for the ink-test-project in this track.

When to use which:
  • inkgd (GDScript) — no .NET dependency, works on every export target. What this track uses.
  • godot-ink (C#) — wraps the official ink runtime, ~50× faster, the studio default.
Rule of thumb: use godot-ink if you can ship a .NET build and need the speed for a large game; otherwise inkgd keeps setup simple. The runtime loop you learn here is nearly identical in both.

The Runtime Loop

Playing an ink story is a loop with two phases: a one-time setup that builds the story, then a repeating advance cycle that pulls text and feeds back the player's choice.

The diagram below shows both. Notice the split: setup ends at a signal, and only after that signal do you touch the story.

The one rule that trips everyone up: never read the story's text or advance it before the loaded signal fires with true. Building the story is asynchronous — the result arrives through a signal, not on the next line. Touch the story only inside the signal handler.

Setup: Build the Story

The setup phase has a fixed order. Each step depends on the one before it, and the last step hands off to a signal:

func _ready():
    _ink_player = InkPlayerFactory.create()   # 1. make the player
    _ink_player.loads_in_background = false    # 2. load synchronously (small story)
    add_child(_ink_player)                     # 3. InkPlayer is a Node — add it to the tree

    _ink_player.ink_file = load("res://stories/05_first_godot_integration.ink.json")  # 4. the COMPILED story
    _ink_player.connect("loaded", Callable(self, "_on_story_loaded"))                  # 5. wait for the signal

    call_deferred("_create_story")             # 6. build it — next frame

Step 4 assigns the compiled .ink.json, not the raw .ink source — Godot imports your story to JSON, and that is what the runtime plays. Step 5 connects the loaded signal before building, because building reports its result through that signal.

Gotcha — why create_story() is deferred: inkgd installs a runtime autoload (__InkRuntime) when you enable the plugin. In _ready() that autoload may not be in the tree yet, so calling create_story() immediately can fail with nothing on screen. call_deferred waits one frame so the runtime is ready. This is the most common inkgd setup error. 
func _create_story():
    _ink_player.create_story()   # builds the story, then emits `loaded`

Print Before You Paint

Before wiring any UI, prove the wiring works by printing one line to the Output console. This is the smallest possible confirmation that the story loaded and text is flowing:

func _on_story_loaded(successfully: bool):
    if not successfully:
        push_error("Story failed to load")
        return
    print(_ink_player.continue_story_maximally())   # one passage → Output panel

Run the scene. If the cave-entrance text appears in the Output panel, the story is connected. Now — and only now — is it worth putting text on screen. Debugging a blank Label is harder than reading a printed line.

The Full Player

Now replace the print with real rendering. The handler reads the accumulated text into a RichTextLabel, then branches: if the story is waiting on choices, render a button per choice; otherwise the story has ended, so read a variable back to prove GDScript and ink share state.

Here is the complete script. Attach it to a Control with two direct children: TextLabel (a RichTextLabel, with BBCode enabled so the coloured messages render) and ChoicesContainer (a VBoxContainer).

# story_player.gd
# First Godot integration for an ink story using the inkgd GDScript runtime.
# Loads a compiled .ink.json, displays text, renders choices as buttons, and
# reads a story variable when the story ends.
#
# Node setup (attach this to a Control):
#   Control (this script)
#   +- TextLabel        : RichTextLabel   -- story text (BBCode enabled)
#   +- ChoicesContainer : VBoxContainer   -- choice buttons appear here
extends Control

var InkPlayerFactory := preload("res://addons/inkgd/ink_player_factory.gd") as GDScript

var _ink_player = null

@onready var _text_label: RichTextLabel = $TextLabel
@onready var _choices_container: VBoxContainer = $ChoicesContainer


func _ready():
    # 1. Create the player and put it in the tree (InkPlayer is a Node).
    _ink_player = InkPlayerFactory.create()
    _ink_player.loads_in_background = false
    add_child(_ink_player)

    # 2. Assign the COMPILED story (.ink.json, not the raw .ink source).
    _ink_player.ink_file = load("res://stories/05_first_godot_integration.ink.json")

    # 3. Wait for the story to finish building before touching it.
    _ink_player.connect("loaded", Callable(self, "_on_story_loaded"))

    # 4. Defer create_story() so the __InkRuntime autoload is ready this frame.
    call_deferred("_create_story")


func _create_story():
    _ink_player.create_story()


# Only interact with the story once it has loaded successfully.
func _on_story_loaded(successfully: bool):
    if not successfully:
        _text_label.text = "[color=red]ERROR: Story failed to load.[/color]"
        return
    _advance_story()


# Step ONE line at a time, accumulating each line's text. Through inkgd's
# InkPlayer, continue_story_maximally() returns only the LAST line (it discards
# the story's concatenated text), so a single-step loop is how you show a whole
# passage — read each line's return value and append it. Ink's line text already
# ends in a newline, so append it as-is (adding "\n" here double-spaces output).
func _advance_story():
    while _ink_player.can_continue:
        var text = _ink_player.continue_story()
        if text != "":
            _text_label.text += text

    if _ink_player.has_choices:
        _show_choices()
    elif not _ink_player.can_continue:
        _on_ended()


# Render one button per available choice.
func _show_choices():
    for child in _choices_container.get_children():
        child.queue_free()

    var choices = _ink_player.current_choices
    for i in range(choices.size()):
        var btn = Button.new()
        btn.text = choices[i].text          # each choice is an object; use .text
        btn.connect("pressed", Callable(self, "_on_choice_selected").bind(i))
        _choices_container.add_child(btn)


func _on_choice_selected(index: int):
    for child in _choices_container.get_children():
        child.queue_free()

    _ink_player.choose_choice_index(index)  # tell the runtime which choice
    _advance_story()                         # then continue


# The story ended -- read a variable to prove GDScript shares ink's state.
func _on_ended():
    var torch_lit = _ink_player.get_variable("torch_lit")
    _text_label.text += "\n[color=gray]torch_lit = %s[/color]" % str(torch_lit)

Walk the advance cycle: the while _ink_player.can_continue loop calls continue_story() once per line and appends each line's returned text — that's how a whole passage reaches the screen. If has_choices is true, each entry in current_choices is an object — read its .text for the button label. Pressing a button calls choose_choice_index(i), which tells the runtime which branch to take, then advances again. When a continue produces no choices and can_continue is false, the story is over, and get_variable reads the ink global torch_lit — proof the two languages share one state.

Gotcha — why not continue_story_maximally(): maximally sounds simpler — one call for a whole passage. But through inkgd's InkPlayer it returns only the last line (it discards the story's concatenated text), so a naive text = continue_story_maximally() silently drops every line but the last. Step one line at a time with continue_story() and append each line's returned text — that's the reliable way to show a full passage. (Lesson 6 reuses this same loop to read each line's tags.)

Check Your Understanding

Exercise: A teammate wires up their first ink story like this, expecting the opening line to print — but the console shows an empty string:

func _ready():
    _ink_player = InkPlayerFactory.create()
    add_child(_ink_player)
    _ink_player.ink_file = load("res://stories/intro.ink.json")
    _ink_player.create_story()
    print(_ink_player.current_text)   # prints "" — why?

Why is current_text empty here, and what should they do instead?

Hint

Look at the order things happen in. Does create_story() finish building the story before the very next line runs? How does the runtime tell you it's done?

Answer

Building the story is asynchronous. create_story() starts the build and returns immediately — it does not hand back a ready story on the next line. The result arrives later, through the loaded signal. So print(_ink_player.current_text) runs before the story exists, and every read-only property returns its empty default ("") rather than crashing — which is exactly why the bug looks like "nothing happened" instead of an error.

The fix is to connect loaded first and read the story only inside the handler:

    _ink_player.connect("loaded", Callable(self, "_on_loaded"))
    _ink_player.create_story()

func _on_loaded(successfully: bool):
    if not successfully:
        return
    print(_ink_player.continue_story_maximally())   # now the story exists

Key insight: at the engine–script boundary, "call then read the next line" is a sequential mental model that breaks. The signal is the return channel — act when it fires, not before.
