Tags as Commands

Lesson 6 · Ink + Godot · ~16 min read
Win: You can design a tag protocol that drives game systems from ink — parsing # key: value tags into engine actions — without coupling your story to engine code.
After this lesson: Your ink lines can command a speaker label, a sound effect, or a hidden side effect through tags. The story says what should happen; a small GDScript dispatcher decides how — and you add new commands without touching the story.

The Pain of Hardcoding

In lesson 05 your story drove text and choices. Real dialogue needs more: who is speaking, a sound when a coin drops, a portrait swap. The tempting first move is to hardcode it in GDScript by looking at the text:

func _advance_story():
    var text = _ink_player.continue_story()
    # Guess the speaker from the words on screen...
    if text.begins_with("\"Fancy a look"):
        _speaker_label.text = "Alfoz"
        _play_sound("cart_creak")
    _text_label.text += text

This works — until the writer fixes a typo, rephrases the line, or you translate the game. The moment the text changes, the begins_with match silently fails: no error, just a missing speaker and a dead sound cue. Every new line of dialogue adds another brittle branch. You have coupled your engine logic to the exact words the player sees — the one thing writers change most.

The Protocol: Tags Carry Intent

ink lets you attach tags to any line with #. A tag is stripped from the visible text and delivered separately — so it is a perfect place to carry a command for the engine. By convention we write # key: value:

"Fancy a look at my wares, traveler?" # speaker: Alfoz # sound: cart_creak
The needle always points home, he claims. # hidden

The colon is not ink syntax — it is plain text your code will split. The story now declares intent (speaker: Alfoz) instead of leaving the engine to guess it from the words. This is the tag protocol: a contract between the writer and the game. Change the line's wording all you like — the tag stays put.

The engine reads each line's tags and routes them to the right subsystem. The story never mentions Godot; the GDScript never reads the story's prose. That is the decoupling:

One Line at a Time

There is a catch — and it's why lesson 05 already stepped one line at a time. If you advance with continue_story_maximally() (one call for several lines), the tags collapse: current_tags ends up holding only the last line's tags, and every command in between is lost. (It's the same reason maximal-continue drops all but the last line of text — lesson 05's gotcha, now biting the tags too.)

So you keep the same continue_story() loop from lesson 05 — you just read each line's tags inside it, right where you already read the line's text:

func _advance_story():
    while _ink_player.can_continue:
        var text = _ink_player.continue_story()          # ONE line
        var show_line = _process_tags(_ink_player.current_tags)
        if show_line and text.strip_edges() != "":
            _text_label.text += text
    if _ink_player.has_choices:
        _show_choices()

Each pass reads one line's text and that same line's tags, so nothing is lost. _process_tags returns whether the line's text should be shown — which brings us to the dispatcher itself.

The Dispatcher

The dispatcher splits each tag on its colon and routes the key with a match. Two keys carry a value (speaker, sound); one is a bare flag (hidden) that suppresses the line's text. Crucially, side effects run either way — only the text is gated:

# story_player.gd
# Tags-as-commands integration for an ink story using the inkgd runtime.
# Extends Lesson 05: instead of one maximal continue, it steps line-by-line so
# each line's tags are available, then dispatches those tags to game systems.
#
# Tag protocol (a contract between the writer and this parser):
#   # speaker: NAME  -> set the name label
#   # sound: NAME    -> play a sound effect
#   # hidden         -> run side effects but do NOT show this line's text
#
# Node setup (attach this to a Control):
#   Control (this script)
#   +- SpeakerLabel     : Label          -- who is speaking
#   +- TextLabel        : RichTextLabel   -- story text (BBCode enabled)
#   +- ChoicesContainer : VBoxContainer   -- choice buttons appear here
extends Control

var InkPlayerFactory := preload("res://addons/inkgd/ink_player_factory.gd") as GDScript

var _ink_player = null

@onready var _speaker_label: Label = $SpeakerLabel
@onready var _text_label: RichTextLabel = $TextLabel
@onready var _choices_container: VBoxContainer = $ChoicesContainer


func _ready():
	_ink_player = InkPlayerFactory.create()
	_ink_player.loads_in_background = false
	add_child(_ink_player)

	_ink_player.ink_file = load("res://stories/06_tags_as_commands.ink.json")
	_ink_player.connect("loaded", Callable(self, "_on_story_loaded"))
	call_deferred("_create_story")


func _create_story():
	_ink_player.create_story()


func _on_story_loaded(successfully: bool):
	if not successfully:
		_text_label.text = "[color=red]ERROR: Story failed to load.[/color]"
		return
	_advance_story()


# Step ONE line at a time. continue_story_maximally() would collapse several
# lines into one and leave current_tags reflecting only the last line -- we would
# lose the per-line tags. A single-step loop keeps each line's tags intact.
func _advance_story():
	while _ink_player.can_continue:
		var text = _ink_player.continue_story()

		# Read THIS line's tags and dispatch them. The return value decides
		# whether the line's text is shown; side effects run either way.
		var show_line = _process_tags(_ink_player.current_tags)

		if show_line and text.strip_edges() != "":
			_text_label.text += text

	if _ink_player.has_choices:
		_show_choices()


# Parse "key: value" tags and route each to a game system.
# Returns false if a tag says this line's text should be hidden.
func _process_tags(tags: Array) -> bool:
	var show_line := true

	for tag in tags:
		var parts = (tag as String).split(":", false, 1)
		var key = parts[0].strip_edges()
		var value = parts[1].strip_edges() if parts.size() > 1 else ""

		match key:
			"speaker":
				_speaker_label.text = value
			"sound":
				_play_sound(value)      # your audio system
			"hidden":
				show_line = false
			_:
				push_warning("Unhandled tag: %s" % tag)   # no handler -- a no-op

	return show_line


func _play_sound(sound_name: String):
	# Stub: a real project would look up and play an AudioStream here.
	print("[sound] %s" % sound_name)


func _show_choices():
	for child in _choices_container.get_children():
		child.queue_free()

	var choices = _ink_player.current_choices
	for i in range(choices.size()):
		var btn = Button.new()
		btn.text = choices[i].text
		btn.connect("pressed", Callable(self, "_on_choice_selected").bind(i))
		_choices_container.add_child(btn)


func _on_choice_selected(index: int):
	for child in _choices_container.get_children():
		child.queue_free()

	_ink_player.choose_choice_index(index)
	_advance_story()
The protocol is a contract: to add a new command — a portrait, a camera move — you teach the dispatcher one new key in the match. You never edit the story. The writer keeps writing tags; the engine grows one handler at a time.
Gotcha — a tag with no handler: if the writer types # speakr: Alfoz, the match falls through to _ and push_warning fires — a no-op, not a crash. ink itself never validates tags, so misspellings fail quietly. The warning is your safety net; keep it.
New concept — global tags: tags at the very top of the file (above the first knot) describe the whole story, not one line. Read them once with get_global_tags() — handy for a title, author, or default theme. Per-line tags use current_tags, as above.

The Suppress Contract

Notice that _process_tags returns a bool, and only # hidden flips it false. Every other tag runs its side effect and leaves the flag alone. This separation — the suppress contract, where side effects always fire but text is gated — is what lets a production story do this:

You spot the hidden lever. # check: passed
You see nothing unusual. # hidden

Both lines' tags run; the dispatcher shows one line's text and hides the other's, based on game state. In Esoteric Ebb this same drain-and-dispatch loop scales to about thirty command families — skill checks, variable writes, camera, combat — but they all extend the exact pattern you just wrote.

Check Your Understanding

Exercise: A teammate skips tags and sets the speaker by reading the text instead:

func _process_line(text: String):
    if text.begins_with("\"Fancy a look"):
        _speaker_label.text = "Alfoz"
    _text_label.text += text

It works in their test. Two weeks later the writer rephrases the line to "Care to see my wares?" and also ships a French translation. The speaker label goes blank on that line, with no error in the console. Why does this approach break, and what does the tag protocol give them instead?

Hint

What is the code matching on — something the writer controls and changes often, or something stable? What channel is the speaker information travelling in?

Answer

The code keys off the displayed text — the exact words the player sees. But display text is a moving target: rephrasing, typo fixes, and translation all change it, and none of them raise an error. The begins_with match just silently stops matching, so the speaker label goes blank. Worse, in French the line is entirely different words, so the match can never succeed.

A tag protocol fixes this by putting the speaker in a separate, stable channel: # speaker: Alfoz. The writer can rephrase or translate the visible line freely — the tag is untouched, so the dispatcher still sets the label. The engine keys off the protocol key, never the prose.

Key insight: display text is for humans; the protocol key is for the machine. Never make one channel do both jobs — the moment the words change, code that reads the words breaks.
