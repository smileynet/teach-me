State Bridge

Lesson 7 · Ink + Godot · ~16 min read
Win: You can open a two-way channel between ink and your game: ink calls out to game logic with an external function, your game reacts to ink state changes with a variable observer, and you persist the whole story with save/load.
After this lesson: Lesson 06 sent commands one way — ink told the engine what to do. Now you'll wire the return path: the story can ask the game a question mid-scene, the game can watch a story variable and keep a HUD in sync, and a player can quit and resume exactly where they left off.

The Pain: A Sealed Monologue

Tags let ink command the engine, but the story still can't ask it anything. Suppose a price should depend on the player's standing with the guild — a number that lives in your game, not the story. You can't hardcode it in ink, because ink doesn't know it. And when ink changes a variable the player cares about — gold, health — your HUD has no idea it happened. The story is a sealed monologue: it talks, but it can't listen, and nothing outside can hear it change.

Three bridges open the channel. We'll add them in order of how tightly they couple ink to the engine: a call out, a reaction in, and finally persistence of the whole state.

Bridge 1: External Functions (ink calls out)

An external function lets ink call a method you define in GDScript. The story declares the function with EXTERNAL, calls it like any ink function, and your engine supplies the answer:

EXTERNAL discount_for(rep)

=== market ===
~ temp off = discount_for(reputation)
~ temp price = 12 - off
{off > 0: "For a friend of the guild — {price} coins." }

On the engine side you bind the name to a method — after the story is created, before the first line runs:

_ink_player.bind_external_function("discount_for", self, "_discount_for", true)

func _discount_for(rep: int) -> int:
    return 3 if rep >= 2 else 0

Now the writer asks a question in the story's own language and the game answers it. The story stays portable — it names what it needs (a discount), not how it's computed.

Gotcha — lookahead safety: ink evaluates a little ahead to know which choices to show, and it calls external functions during that lookahead. A pure function like discount_for is fine to call twice, so we pass lookahead_safe = true. But a function with a side effect — spend gold, play a sound — would fire spuriously during the preview. Bind those with lookahead_safe = false so ink only calls them for real.

Bridge 2: Variable Observers (the game reacts)

The external function is a pull — ink asks, the game answers. Often you want the opposite: the story changes gold, and the HUD should update on its own. Polling the variable every frame is wasteful and easy to forget. A variable observer is a push — register once, and inkgd calls you back whenever that variable changes:

_ink_player.observe_variable("gold", self, "_on_gold_changed")

func _on_gold_changed(_name: String, new_value) -> void:
    _gold_label.text = "Gold: %d" % int(new_value)
Gotcha — observers fire on change, not on registration: after you call observe_variable, the callback does not run for the current value — only when the variable next changes. So the HUD would start blank until the first purchase. Seed it once yourself right after registering: _on_gold_changed("gold", _ink_player.get_variable("gold")). Then the observer keeps it in sync from there.
When to use which:
  • External function — the story needs a value or action from the game at a specific point (a computed price, a dice roll, spend gold).
  • Variable observer — the game needs to react whenever a story variable changes (keep a HUD, portrait, or music state in sync).
They are not interchangeable: calling an external function again will never update a HUD, and observing a variable will never compute a value for the story. Reach for the direction the data actually flows.

Bridge 3: Save / Load (persist the whole story)

The player quits mid-scene and comes back. Without persistence they restart at line one — every choice, visit count, and variable gone. inkgd serializes the entire story to a string with get_state(), and restores it with set_state():

func save_game():
    _saved_state = _ink_player.get_state()   # one JSON string: everything

func load_game():
    _ink_player.set_state(_saved_state)
Gotcha — it's the whole state or nothing: get_state() captures variables, visit counts, the call stack, and the RNG seed together. The tempting shortcut — "I'll just save my three variables" — silently drops the current knot and every read count, so the restored story resumes in the wrong place with once-only content re-enabled. Save the one blob; don't hand-pick fields.

The Full Player

Here is the complete player wiring all three bridges. It's the lesson 05/06 single-step loop with the bindings added in _on_story_loaded — the one place where the story exists but hasn't run yet:

# story_player.gd
# State-bridge integration for an ink story using the inkgd runtime.
# Extends Lesson 06's single-step loop with the three ink<->engine bridges:
#   1. External function  -- ink calls OUT to game logic (discount_for)
#   2. Variable observer  -- the game reacts TO an ink VAR change (gold -> HUD)
#   3. Save / load         -- persist and restore the whole story state
#
# Node setup (attach this to a Control):
#   Control (this script)
#   +- SpeakerLabel     : Label          -- who is speaking
#   +- TextLabel        : RichTextLabel   -- story text (BBCode enabled)
#   +- GoldLabel        : Label           -- HUD mirror of the ink `gold` VAR
#   +- ChoicesContainer : VBoxContainer   -- choice buttons appear here
extends Control

var InkPlayerFactory := preload("res://addons/inkgd/ink_player_factory.gd") as GDScript

var _ink_player = null
var _saved_state := ""   # a snapshot for the save/load demo

@onready var _speaker_label: Label = $SpeakerLabel
@onready var _text_label: RichTextLabel = $TextLabel
@onready var _gold_label: Label = $GoldLabel
@onready var _choices_container: VBoxContainer = $ChoicesContainer


func _ready():
	_ink_player = InkPlayerFactory.create()
	_ink_player.loads_in_background = false
	add_child(_ink_player)

	_ink_player.ink_file = load("res://stories/07_state_bridge.ink.json")
	_ink_player.connect("loaded", Callable(self, "_on_story_loaded"))
	call_deferred("_create_story")


func _create_story():
	_ink_player.create_story()


func _on_story_loaded(successfully: bool):
	if not successfully:
		_text_label.text = "[color=red]ERROR: Story failed to load.[/color]"
		return

	# BRIDGE 1 -- External function. The story declared `EXTERNAL discount_for(rep)`;
	# we bind it AFTER create_story() and BEFORE the first continue. It's pure (no
	# side effects), so lookahead_safe = true: ink may call it while previewing
	# choices, and that's harmless here. A function that PLAYED A SOUND or SPENT
	# GOLD would need lookahead_safe = false, or it would fire during preview.
	_ink_player.bind_external_function("discount_for", self, "_discount_for", true)

	# BRIDGE 2 -- Variable observer. The engine reacts to `gold` changing inside
	# ink (push, not poll) -- but the observer only fires on a CHANGE, not on
	# registration. So seed the HUD once from the current value, then let the
	# observer keep it in sync from here on.
	_ink_player.observe_variable("gold", self, "_on_gold_changed")
	_on_gold_changed("gold", _ink_player.get_variable("gold"))

	_advance_story()


# BRIDGE 1 target: given the player's reputation, return a coin discount.
# This is GAME logic the writer doesn't have to hardcode in ink.
func _discount_for(rep: int) -> int:
	return 3 if rep >= 2 else 0


# BRIDGE 2 target: (variable_name, new_value). Mirror gold onto the HUD.
func _on_gold_changed(_variable_name: String, new_value) -> void:
	_gold_label.text = "Gold: %d" % int(new_value)


# Step ONE line at a time (Lesson 05/06 loop). Ink's line text already ends in a
# newline, so append it as-is (adding "\n" here double-spaces output).
func _advance_story():
	while _ink_player.can_continue:
		var text = _ink_player.continue_story()
		var show_line = _process_tags(_ink_player.current_tags)
		if show_line and text.strip_edges() != "":
			_text_label.text += text

	if _ink_player.has_choices:
		_show_choices()


func _process_tags(tags: Array) -> bool:
	var show_line := true
	for tag in tags:
		var parts = (tag as String).split(":", false, 1)
		var key = parts[0].strip_edges()
		var value = parts[1].strip_edges() if parts.size() > 1 else ""
		match key:
			"speaker":
				_speaker_label.text = value
			"hidden":
				show_line = false
			_:
				pass
	return show_line


# BRIDGE 3 -- Save / load. get_state() returns the WHOLE story state as one JSON
# string (variables, visit counts, callstack, RNG seed). Never hand-save vars one
# by one -- you'd drop the current knot and read counts. set_state() restores it.
func save_game() -> void:
	_saved_state = _ink_player.get_state()


func load_game() -> void:
	if _saved_state != "":
		_ink_player.set_state(_saved_state)


func _show_choices():
	for child in _choices_container.get_children():
		child.queue_free()

	var choices = _ink_player.current_choices
	for i in range(choices.size()):
		var btn = Button.new()
		btn.text = choices[i].text
		btn.connect("pressed", Callable(self, "_on_choice_selected").bind(i))
		_choices_container.add_child(btn)


func _on_choice_selected(index: int):
	for child in _choices_container.get_children():
		child.queue_free()
	_ink_player.choose_choice_index(index)
	_advance_story()

Check Your Understanding

Exercise: A teammate wants the gold counter in the HUD to update whenever the story spends gold. They bind an external function and call it from ink every time gold changes:

EXTERNAL update_gold_hud(amount)
// ...in the story, after every purchase:
~ update_gold_hud(gold)

It works, but now every line that touches gold needs a manual update_gold_hud call, and they keep forgetting one — the HUD drifts out of sync. They ask you to help them "add more external calls to cover the missing spots." Why is that the wrong fix, and what should they use instead?

Hint

Which direction is the data flowing — is the story asking the game for something, or is the game reacting to a story change? Which bridge matches that direction?

Answer

An external function is a pull: ink calls out when it wants a value or action. Using it to update the HUD means the story is now responsible for remembering to notify the engine on every change — exactly the manual bookkeeping that keeps drifting out of sync. Adding more calls just adds more places to forget.

The data is flowing the other way: gold changes in ink, and the game needs to react. That's a variable observer. Register once with observe_variable("gold", self, "_on_gold_changed") and inkgd pushes every change to you automatically — the story never has to announce anything. One registration replaces every scattered call, and it can't drift because nothing has to remember to fire it.

Key insight: match the bridge to the direction of the data. Game-needs-a-value-from-the-story is an external function; game-reacts-to-a-story-change is an observer. Reaching for the wrong direction turns into exactly this kind of manual, drift-prone glue.
