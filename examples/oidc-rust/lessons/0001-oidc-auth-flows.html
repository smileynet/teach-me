OIDC Authorization Code Flow & PKCE

Lesson 1 · OIDC in Rust · ~10 min read
Win: You can draw the authorization code flow on a whiteboard, explain what PKCE prevents, and describe what your Rust code does at each step.
After this lesson: You understand the redirect dance between your app, the browser, and the identity provider — and why every step exists. You know what a "code" is, why it's exchanged server-to-server, and how PKCE prevents interception attacks.

The Problem: Your App Doesn't Know Who the User Is

Your Rust web service handles requests, but it has no idea who's making them. You could build your own login system — password hashing, email verification, session management, password reset, MFA — or you could delegate identity to someone who already solved it (Google, Microsoft, your company's Keycloak). [OIDC Core 1.0]

OpenID Connect (OIDC) is the protocol that makes this delegation work. When a user clicks "Sign in with Google," OIDC is what's happening underneath — a carefully choreographed redirect sequence that ends with your app holding a cryptographically signed proof of who the user is.

The Two Layers: OAuth2 + OIDC

OAuth 2.0 answers "what is this app allowed to do?"
OIDC adds "who is the user?" — it's an identity layer ON TOP of OAuth 2.0.

Every OIDC flow is also an OAuth2 flow. OIDC adds three things to OAuth2:

  • The openid scope (signals "I want identity, not just authorization")
  • The ID token — a signed JWT proving who logged in
  • The UserInfo endpoint — for fetching additional user claims

In practice: you request the openid scope, and you get back an ID token along with the access token. The ID token is for YOUR app (identity). The access token is for calling APIs (authorization).

The Authorization Code Flow (Step by Step)

This is the standard flow for web apps and the one you'll implement in Rust. The key insight: the user's credentials never touch your app. They authenticate directly with the identity provider.

Notice the split: steps 1-5 happen through the browser (redirects). Steps 6-7 happen server-to-server — your Rust code talks directly to the IdP's token endpoint. This is crucial: tokens never transit through the browser URL bar.

PKCE: Why the Code Alone Isn't Enough

The authorization code travels through the browser (in the redirect URL). If something intercepts it — a malicious browser extension, a compromised redirect, a rogue app registered with the same custom scheme — they could exchange it for tokens.

PKCE (Proof Key for Code Exchange) ties the code to whoever started the flow. An interceptor has the code but can't prove they're the original requester.

How it works:

  1. Before the auth request: Generate a random code_verifier (43-128 chars, URL-safe). Store it in your session.
  2. Compute the challenge: code_challenge = BASE64URL(SHA256(code_verifier))
  3. Send in auth request: Include code_challenge and code_challenge_method=S256
  4. At token exchange: Send the original code_verifier
  5. Server verifies: Hashes the verifier, confirms it matches the challenge from step 3

An attacker who intercepts the code from the redirect cannot exchange it — they never saw the code_verifier (it was generated and stored on your server, never sent through the browser). [RFC 7636]

PKCE is now recommended for ALL clients, not just native apps. The OAuth 2.1 draft makes it mandatory. The oauth2 Rust crate supports PKCE natively — you generate it with one function call.

The Discovery Shortcut

You might have noticed the flow needs several URLs (authorization endpoint, token endpoint, JWKS URI). You don't hardcode these. Every OIDC provider publishes everything you need at a single URL:

https://accounts.google.com/.well-known/openid-configuration

This JSON document contains all the metadata your client needs: endpoints, supported scopes, signing algorithms, PKCE methods. This is the discovery document — in Rust, the openidconnect crate fetches and parses it with one async call:

let metadata = CoreProviderMetadata::discover_async(
    IssuerUrl::new("https://accounts.google.com".to_string())?,
    async_http_client,
).await?;

Fetch once at startup, cache it, use the endpoints for all subsequent requests. If your IdP changes its token endpoint URL, your app picks it up automatically on next restart. [OIDC Discovery 1.0]

The Critical Security Properties

Why does the flow have so many steps? Each one prevents a specific attack:

MechanismWhat it prevents
state parameterCSRF — someone tricking a user into logging in as the attacker
nonce in ID tokenReplay — using an old ID token to impersonate someone
PKCECode interception — stealing the authorization code from the redirect
Server-to-server token exchangeToken exposure — tokens never appear in browser history or logs
ID token signature verificationForgery — someone crafting a fake ID token claiming to be a user

If you skip any of these, you have a security vulnerability. The openidconnect crate enforces most of them at the type level — you literally can't forget to verify the nonce because the compiler won't let you extract claims without providing it.

Check Your Understanding

Exercise: A colleague proposes sending tokens directly back in the redirect URL (the "implicit flow") instead of exchanging a code. What's wrong with this for a server-rendered Rust app?

Key points to hit

Tokens in the URL fragment are exposed in browser history, can be leaked via Referer headers, and there's no PKCE protection. The authorization code flow keeps tokens off the browser entirely — they're exchanged server-to-server. The implicit flow was designed for JS-only apps that couldn't make back-channel requests, and even those should use code+PKCE now.
