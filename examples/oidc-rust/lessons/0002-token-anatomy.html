Token Anatomy — ID Tokens, Access Tokens & Validation

Lesson 2 · OIDC in Rust · ~12 min read
Win: You can decode a JWT by hand, explain what each standard claim does, and walk through the 8-step validation checklist your Rust middleware must perform.
After this lesson: You know the difference between ID tokens and access tokens (and which goes where), the structure of a JWT, what every standard claim means, and exactly what your Rust code must verify before trusting a token. When validation fails in production, you'll know which step broke.

Two Tokens, Two Audiences

After the authorization code exchange (Lesson 1), your app receives multiple tokens. The critical distinction:

TokenPurposeAudienceFormat
ID tokenProves who logged inYour client appAlways JWT
Access tokenAuthorizes API callsResource server (API)Opaque or JWT
Refresh tokenGets new access tokensAuthorization server onlyOpaque
The rule: ID tokens prove identity TO YOUR APP. Access tokens prove authorization TO AN API. Never send an ID token to an API as a bearer token. Never use an access token to determine who a user is.

This matters in Rust because you'll build two different pieces: (1) a login flow that receives and validates ID tokens, and (2) middleware that validates access tokens on API endpoints. Same JWT format, different validation rules, different trust model. [OIDC Core 1.0 §2]

JWT Structure: Three Parts, Dot-Separated

A JWT is three base64url-encoded segments separated by dots:

The header says HOW it's signed (algorithm + key ID). The payload contains the CLAIMS (facts about the user and token). The signature proves it hasn't been tampered with — created using the IdP's private key, verified with their public key.

The Standard Claims (What Each One Means)

An ID token's payload contains claims. Some are required by the OIDC spec, others are optional but common:

ClaimFull nameWhat it isWhy it matters
issIssuerURL of the IdP that created this tokenReject tokens from unknown issuers
subSubjectUnique identifier for the user (at this IdP)This is the user's stable ID — not their email
audAudienceWho this token is intended for (your client_id)Reject tokens meant for a different app
expExpirationUnix timestamp — token invalid after this timeReject expired tokens (allow ~30s clock skew)
iatIssued AtWhen the token was createdDetect unreasonably old tokens
nonceNonceRandom value YOU sent in the auth requestReplay protection — proves freshness
auth_timeAuth TimeWhen the user actually entered credentialsEnforce max session age if needed
at_hashAccess Token HashHash of the access tokenBinds the ID token to its companion access token

Beyond the standard claims, providers add profile data based on what scopes you requested:

  • openid → always gives you sub
  • profile → adds name, given_name, family_name, picture
  • email → adds email, email_verified

The 8-Step Validation Checklist

This is what your Rust code MUST do before trusting a token. Miss any step and you have a security hole:

  1. Decode the header — find the kid (key ID) and alg (algorithm)
  2. Fetch the provider's public keys — from the jwks_uri in the discovery document
  3. Verify the signature — using the key that matches the token's kid
  4. Check iss — must exactly match your configured issuer URL
  5. Check aud — must contain your client_id
  6. Check exp — must be in the future (allow ≤60s clock skew)
  7. Check nonce — must match what you stored when starting the auth flow
  8. Optionally check iat — reject tokens issued unreasonably long ago

In Rust with the openidconnect crate, steps 1-6 happen automatically when you call the token verifier. You supply the nonce for step 7. The crate's type system makes it hard to skip steps — verification returns a typed IdTokenClaims only after all checks pass. [OIDC Core 1.0 §3.1.3.7]

JWKS: Where the Public Keys Live

The IdP signs tokens with a private key. Your app verifies them with the corresponding public key. But the IdP rotates keys — so you can't hardcode a key. Instead, you fetch them from the JWKS (JSON Web Key Set) endpoint:

GET https://accounts.google.com/.well-known/jwks.json

{
  "keys": [
    {
      "kty": "RSA",
      "kid": "abc123",          // matches the kid in token headers
      "use": "sig",
      "n": "0vx7agoebGc...",   // RSA modulus
      "e": "AQAB"              // RSA exponent
    }
  ]
}

Your validation logic: decode the JWT header → find kid → look up the matching key in the JWKS → verify the signature. If the kid isn't in your cached JWKS, refetch — the IdP probably rotated keys.

Token Validation in Rust (Two Approaches)

For login flows: openidconnect crate

The openidconnect crate validates ID tokens as part of the token exchange — you don't manually fetch JWKS or check claims:

// The crate handles discovery, JWKS fetch, and all 8 checks
let id_token_claims = id_token
    .claims(&verifier, &nonce)  // verifier has the IdP's keys
    .map_err(|e| format!("ID token validation failed: {}", e))?;

// If we get here, the token is valid — extract user info
let subject = id_token_claims.subject().to_string();
let email = id_token_claims.email().map(|e| e.to_string());

For API middleware: jsonwebtoken + JWKS fetch

For resource servers validating access tokens on every request, you want lower-level control (and caching):

use jsonwebtoken::{decode, DecodingKey, Validation, Algorithm};

// Cache JWKS at startup, refresh when kid not found
let key = jwks.find(&token_kid)
    .ok_or("Unknown key ID — possible key rotation")?;
let decoding_key = DecodingKey::from_jwk(key)?;

let mut validation = Validation::new(Algorithm::RS256);
validation.set_issuer(&["https://accounts.google.com"]);
validation.set_audience(&["my-api-audience"]);

let token_data = decode::<Claims>(&bearer_token, &decoding_key, &validation)?;

Or use the jwtk crate which handles JWKS fetching and caching for you:

let verifier = jwtk::RemoteJwksVerifier::new(jwks_uri);
let claims = verifier.verify::<MyClaims>(&token).await?;

The Production Gotchas

Token validation that works in development breaks in production for predictable reasons:

ProblemSymptomFix
Key rotationSignature verification fails for new tokensRefetch JWKS when kid not found in cache
Clock skewexp check rejects valid tokensAllow 30-60s leeway in expiration checks
Stale JWKS cacheAll tokens fail after IdP rotatesCache with TTL (1h) + force-refresh on miss
Wrong audienceTokens from another app acceptedAlways validate aud — never skip this check
Multi-tenant confusionTokens from wrong tenant acceptedValidate iss matches expected issuer exactly

Check Your Understanding

Exercise: Your API returns 401 Unauthorized for a token that was working 5 minutes ago. The user hasn't logged out. What's your debugging checklist? (Think about which of the 8 steps could have broken.)

Key points to hit

Most likely causes in order: (1) token expired — check exp claim vs current time, (2) key rotation — the kid in the token no longer matches your cached JWKS, refetch and retry, (3) clock skew — your server's clock drifted more than the leeway allows. Less likely: issuer URL changed (IdP config update), audience changed (client registration modified). The fix for most production issues is: add JWKS cache refresh on miss + generous clock skew tolerance (60s).
