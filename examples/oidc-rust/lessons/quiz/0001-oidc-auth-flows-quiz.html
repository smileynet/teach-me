Quiz: OIDC Authorization Code Flow & PKCE

Read each question, form your answer, then reveal to check. Rate your confidence honestly.

explain

Why does the authorization code flow exchange a code server-to-server instead of returning tokens directly in the browser redirect?

Should mention: (1) tokens in the redirect URL would be exposed in browser history, logs, and Referer headers, (2) server-to-server exchange means tokens never transit through the browser — they go directly from IdP to your backend. Key insight: the code is useless without the code_verifier (PKCE) or client_secret, so intercepting it alone isn't enough.

explain

What does PKCE prevent, and how does it work mechanically?

Should mention: (1) prevents authorization code interception — an attacker who captures the code from the redirect can't exchange it, (2) mechanism: generate random code_verifier → hash it to code_challenge → send challenge in auth request → send verifier at token exchange → server confirms hash matches. The verifier never goes through the browser, so interceptors don't have it.

apply

Your Rust callback handler receives a request with ?code=abc&state=xyz. Before exchanging the code, what must you verify and why?

Should mention: (1) verify the state parameter matches what you stored in the session before redirecting — this prevents CSRF (someone tricking a user into logging in on an attacker-controlled session), (2) if state doesn't match, reject the request entirely — it may be a forged callback.

explain

What's the difference between OAuth 2.0 and OIDC? What does OIDC add?

Should mention: (1) OAuth 2.0 handles authorization ("what can this app do?"), OIDC adds authentication ("who is this user?"), (2) OIDC adds three things: the openid scope, the ID token (signed JWT proving identity), and the UserInfo endpoint. Every OIDC flow is also an OAuth2 flow — OIDC is strictly additive.

How well could you explain this?

Section: The Two Layers · Tags: oauth2, oidc, identity, authorization
predict

What would happen if you hardcoded the IdP's token endpoint URL instead of using discovery?

Should mention: (1) it works until the provider changes the URL — then your app breaks silently, (2) you'd also need to hardcode the JWKS URI, authorization endpoint, and supported algorithms. Discovery gives you all of these from one fetch, and your app auto-adapts to provider changes on restart. Bonus: some providers use different endpoints per tenant/region.

How well could you explain this?

Section: The Discovery Shortcut · Tags: discovery, well-known, configuration, resilience
apply

You're building a CLI tool in Rust that needs to authenticate users via OIDC. There's no web server to receive callbacks. How do you handle the redirect?

Should mention: (1) start a temporary local HTTP server on 127.0.0.1 with a random port as the redirect_uri, (2) open the browser for login, (3) receive the callback locally with the authorization code, (4) PKCE is mandatory here since there's no client_secret. The local server shuts down after receiving the code. This is how most CLI OAuth tools work (gh, gcloud, etc.).
