explain

Why should you never send an ID token to an API as a bearer token?

Should mention: (1) ID tokens prove identity TO YOUR APP — their audience (aud) is your client_id, not the API, (2) access tokens are what authorize API calls — their audience is the resource server. Sending an ID token to an API means the API can't properly validate the audience claim, and you're using a credential outside its intended scope.

apply

Your API suddenly returns 401 for tokens that worked 5 minutes ago. Users haven't logged out. What's your debugging checklist?

Should mention: (1) check exp claim vs current time — token probably expired, (2) check if kid in token header matches your cached JWKS — IdP may have rotated keys, (3) check server clock drift (clock skew beyond your leeway tolerance). Less likely: iss URL changed, aud changed. Fix: JWKS cache refresh on kid miss + 60s clock skew tolerance.

What is the kid claim in a JWT header, and why does your validation code need it?

Should mention: (1) kid = Key ID — identifies which public key from the JWKS was used to sign this token, (2) your code uses it to look up the correct key for signature verification — IdPs publish multiple keys (for rotation), so you need to match the right one. If kid isn't in your cached JWKS, refetch — the IdP probably rotated.

Section: JWKS · Tags: kid, jwks, key-rotation, signature-verification
predict

What happens if you skip the aud (audience) validation in your token middleware?

Should mention: (1) tokens issued for OTHER applications at the same IdP would be accepted by your API, (2) this means any app sharing the same IdP could forge authorized requests to your API using their own tokens. The aud check ensures a token was specifically issued FOR your service, not just by a trusted issuer.

Why does the openidconnect crate handle validation differently than jsonwebtoken for your use case?

Should mention: (1) openidconnect is for the login flow — it does discovery, PKCE, token exchange, AND validates ID tokens as part of the exchange (all-in-one), (2) jsonwebtoken is for resource servers validating incoming bearer tokens on every request — lower-level, you manage JWKS fetching/caching yourself. Different roles: openidconnect = client doing login, jsonwebtoken = API checking credentials.

explain

What's the nonce claim, and why is it only relevant for ID tokens (not access tokens)?

Should mention: (1) nonce is a random value YOUR app sends in the auth request — the IdP echoes it in the ID token, (2) you verify it matches to prevent replay attacks (someone reusing an old ID token), (3) it's for ID tokens specifically because they prove identity in a request-response flow where freshness matters. Access tokens are short-lived and validated differently (exp is sufficient).

List the 8 steps of token validation in order:

(1) Decode header → find kid + alg, (2) Fetch public keys from jwks_uri, (3) Verify signature with matching key, (4) Check iss matches issuer, (5) Check aud contains client_id, (6) Check exp > now, (7) Check nonce matches stored value, (8) Optionally check iat is recent.
