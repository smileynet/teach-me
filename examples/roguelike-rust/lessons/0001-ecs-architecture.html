Why ECS — The Architecture That Fits Roguelikes

Lesson 1 · Roguelikes in Rust · ~12 min read
Win: You can explain why Entity-Component-System fits roguelikes better than inheritance, and sketch how you'd model a player, a goblin, and a potion in ECS.
After this lesson: You understand the three parts of ECS (entities, components, systems), why composition beats inheritance for roguelikes, and how Rust's ownership model makes ECS natural.

The Problem: Everything Is a Little Bit Different

A roguelike has hundreds of "things" — the player, monsters, items, traps, doors, stairs. They share some behaviors but differ in others:

  • A goblin has position, health, and AI. A potion has position but no health or AI.
  • A trap has position and triggers on contact — like a monster's attack, but it's not a monster.
  • The player has position, health, and inventory — but no AI (the human controls it).

In OOP inheritance, you'd try to build a class hierarchy: Entity → Creature → Monster, Entity → Item → Potion. This breaks quickly — where does "thing that blocks movement" go? The trap blocks, the monster blocks, the closed door blocks, but the potion doesn't. You end up with multiple inheritance or endless flags.

ECS: Composition Over Inheritance

ECS splits every game object into three concerns:

Entity = just an ID (a number). No data, no behavior.
Component = a bag of data attached to an entity. Position, Health, AI, Renderable — each is a separate component.
System = logic that runs on all entities with a specific set of components.

A goblin is entity #42 with components: Position, Health, AI, Renderable, BlocksMovement.

A potion is entity #107 with components: Position, Renderable, Item, Consumable.

A trap is entity #89 with components: Position, Hidden, TriggersOnContact, DealsDamage.

No hierarchy. No "is-a" relationships. Just entities with different combinations of data.

Systems: Where Behavior Lives

A system queries for entities that have specific components and operates on them:

// The movement system: runs on anything with Position + WantsToMove
fn movement_system(world: &mut World) {
    for (entity, pos, wants_move) in world.query::<(&mut Position, &WantsToMove)>() {
        pos.x += wants_move.dx;
        pos.y += wants_move.dy;
    }
    // Clean up: remove all WantsToMove components (intent consumed)
    world.remove_all::<WantsToMove>();
}

This system doesn't care if the entity is a player, a monster, or a boulder someone pushed. If it has Position and WantsToMove, it moves. That's the power of composition — new entity types get movement for free by having the right components.

Why Rust Makes ECS Natural

Rust's ownership model and ECS are a good fit because:

  • Components are owned by the world, not by entities. Each component type lives in its own storage (a Vec<T> or sparse set). This means you can borrow &mut Position for all entities while simultaneously borrowing &Health — no aliasing, no borrow checker fights.
  • Systems declare their access patterns. A system that queries (&mut Position, &Velocity) can't accidentally touch Health data. The type system enforces separation.
  • Cache-friendly iteration. Components of the same type are stored contiguously in memory. Iterating over all Positions is a linear scan, not pointer-chasing through a heap of heterogeneous objects.
What ECS library should I use?

For learning: hecs — minimal, no macros, easy to understand the model. For a real game: bevy_ecs — more features (resources, events, scheduling), larger ecosystem. The bracket-lib tutorial uses specs, which is older but well-documented. All three implement the same core pattern — the concepts transfer.

The Mental Model

Think of it as a spreadsheet:

Entity | Position | Health | AI       | Renderable | BlocksMovement
-------|----------|--------|----------|------------|---------------
#42    | (5, 3)   | 10/10  | Wander   | 'g' green  | ✓
#43    | (7, 1)   | 30/30  | —        | '@' white  | ✓
#107   | (5, 3)   | —      | —        | '!' blue   | —
#89    | (2, 8)   | —      | —        | —          | —

Entity #42 is a goblin. #43 is the player. #107 is a potion. #89 is a hidden trap. Each row is an entity; each column is a component type. Systems iterate over columns, not rows.

What Breaks Without ECS?

Roguelikes are combinatorially complex — any item might interact with any creature in any environment. A wand of polymorph turns a dragon into a newt. A scroll of teleportation works on monsters too. Fire melts ice walls. If you hardcode relationships (Dragon.polymorphInto(Newt)), you'll never ship. ECS lets you express these as generic systems: "anything with Polymorphable transforms when hit by polymorph effect." The system doesn't know what a dragon is.

Check Your Understanding

Exercise: A designer asks you to add "mimics" — monsters that look like treasure chests until the player gets close. In an inheritance model, is a mimic a Monster or an Item? In ECS, how would you model it?

Hint

Think about which components a mimic needs in each state (disguised vs revealed).

Key points to hit

In inheritance: it's both, which breaks the hierarchy. In ECS: it's an entity with Renderable('!' looks like chest), Position, Hidden, TriggersOnProximity — and when triggered, you add Health, AI, BlocksMovement and change Renderable to 'M'. No class change, just add/remove components.
