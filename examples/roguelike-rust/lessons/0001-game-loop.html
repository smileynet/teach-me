The Game Loop — Getting @ On Screen

Lesson 1 · Roguelikes in Rust · ~10 min read
Win: You understand how a turn-based game loop works and why it's shaped differently from a real-time loop. You have a mental model of input → update → render.
After this lesson: You can explain why a roguelike's game loop waits for player input (unlike a real-time game that runs continuously), and you understand the render → input → update cycle that every roguelike shares.

Why Start Here?

The most common mistake new roguelike developers make is overengineering before they have a game. Experienced devs on r/roguelikedev consistently say: get @ on screen first, make it move, then build from there. Architecture decisions (ECS, entity systems, component models) come later — after you have gameplay to organize. [r/roguelikedev FAQ]

The game loop is the foundation everything else sits on. Get this right and the rest is incremental.

Real-Time vs Turn-Based

A real-time game loop runs as fast as possible:

loop {
    process_input();    // check for keypresses
    update(delta_time); // advance physics, AI, animations
    render();           // draw the frame
    // repeat immediately — 60+ times per second
}

A roguelike loop is fundamentally different — nothing happens until the player acts:

loop {
    render();           // show current state
    let action = wait_for_input();  // BLOCK here until keypress
    update(action);     // player moves, then world responds
    // only loops when player does something
}

This is called a player-centric loop. The world is frozen between turns. This is why roguelikes feel like puzzles — you have infinite time to think. [Game Programming Patterns: Game Loop]

Why This Matters

The loop structure determines everything downstream:

  • No frame budget pressure. You don't need 16ms frames. Your update can take 100ms and nobody notices — the player is reading the screen.
  • Simpler concurrency model. Nothing runs in parallel. Input → process → render, sequentially. This is why Rust's borrow checker is less painful for roguelikes than for real-time games.
  • Monsters take turns after the player. The "update" phase processes player action, then each monster acts in sequence. No simultaneous resolution needed (yet — energy systems come later).
What about animations?

Traditional ASCII roguelikes have no animations — the screen redraws instantly after each turn. If you want tile-based animations (attack flashes, movement tweening), you add a brief non-blocking render loop WITHIN the update phase. But that's polish — skip it for now.

The Minimal Structure in Rust

Using ratatui + crossterm (the current recommended stack for terminal roguelikes — bracket-lib is unmaintained since 2022):

use crossterm::event::{self, Event, KeyCode};
use ratatui::prelude::*;

struct GameState {
    player_x: i32,
    player_y: i32,
}

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let mut terminal = ratatui::init();
    let mut state = GameState { player_x: 40, player_y: 12 };

    loop {
        // RENDER: draw current state
        terminal.draw(|frame| {
            let area = frame.area();
            let buf = frame.buffer_mut();
            buf.set_string(
                state.player_x as u16,
                state.player_y as u16,
                "@", Style::default().fg(Color::White),
            );
        })?;

        // INPUT: block until keypress
        if let Event::Key(key) = event::read()? {
            match key.code {
                KeyCode::Char('q') => break,
                KeyCode::Up    => state.player_y -= 1,
                KeyCode::Down  => state.player_y += 1,
                KeyCode::Left  => state.player_x -= 1,
                KeyCode::Right => state.player_x += 1,
                _ => {}
            }
        }
        // UPDATE: (trivial for now — just the position change above)
    }

    ratatui::restore();
    Ok(())
}

This is a complete, runnable roguelike skeleton. The @ appears, moves with arrow keys, and quits with 'q'. Everything else builds on this loop. [ratatui Tutorial]

What Comes Next (Not Now)

The temptation is to immediately add ECS, or a map, or monsters. Resist. The learning path that experienced roguelike devs recommend is:

  1. @ on screen + movement (this lesson) ✓
  2. A generated map with walls (next lesson)
  3. Field of view (can't see through walls)
  4. Monsters that exist and block
  5. Combat (hit things, things hit you, things die)
  6. → MVP. Only now consider architecture refactoring.

At step 6, your code will be messy — and that's when you have the information to make architecture decisions. You'll know which entities need dynamic composition (ECS territory), which are simple (struct + enum), and which patterns keep appearing (extract them). Deciding architecture before you have gameplay is guessing. [gridbugs.org]

Check Your Understanding

Exercise: A colleague asks: "Why not just use a real-time game engine like Bevy for a roguelike?" Explain why a turn-based loop is simpler and what you'd lose by using a real-time engine.

Hint

Think about what runs between frames in a real-time engine vs what happens between turns in a roguelike.

Key points to hit

A real-time engine runs systems every frame (60+ fps) whether anything happened or not. For a turn-based game, that's wasted work — nothing changes until the player presses a key. A blocking input loop is simpler (no delta-time, no frame budget, no concurrent access), and Rust's borrow checker is less painful when you process sequentially. Bevy works but adds compile time, API churn, and complexity you don't need for grid-based turns.
