The Iceberg Metadata Tree

Win: You can explain how Iceberg tracks table state without a database — and why that matters for your customer's lakehouse.

The Problem Iceberg Solves

A traditional data lake is just files in S3 with a schema bolted on top (think Hive metastore pointing at s3://bucket/table/year=2024/month=01/). This breaks in three specific ways that matter for your customer:

  • Listing is the bottleneck. To plan a query, the engine must list directories to discover files. At scale (millions of files), listing is slow and eventually rate-limited by S3.
  • No isolation. A reader scanning files mid-write sees partial data. There's no "transaction" — just files appearing.
  • Schema and partition changes are surgery. Changing a partition scheme means rewriting all existing data. Evolving a schema risks breaking downstream consumers.

Iceberg solves all three with a single design: it tracks exactly which files belong to a table at any point in time, in a metadata tree stored alongside the data. [Iceberg Spec]

The Three Layers

Every Iceberg table has three layers of metadata, each pointing to the next:

Catalog → Metadata File → Manifest List → Manifest Files → Data Files
Each layer answers a different question. The catalog says "where is the current version?" The metadata file says "what's the schema, partitioning, and snapshots?" The manifests say "which specific files, with what stats?"
LayerWhat it storesWhere it lives
Catalog A pointer to the current metadata file (one per table) AWS Glue Data Catalog, or a REST catalog endpoint
Metadata file Schema, partition spec, sort order, snapshot history, and pointers to manifest lists JSON files in S3 (metadata/ prefix)
Manifest list One per snapshot — lists which manifest files are included Avro files in S3 (metadata/)
Manifest file Lists data files with per-file stats (row count, min/max per column, null counts) Avro files in S3 (metadata/)
Data files The actual rows (Parquet, ORC, or Avro) Parquet files in S3 (data/ prefix)

Why This Matters for Your Customer

No more file listing

Query engines read the manifest files to find exactly which data files to scan — they never list S3 directories. The manifests also carry column-level stats, so the engine can skip entire files that can't contain matching rows. This is called manifest-level pruning. [AWS Prescriptive Guidance]

How does pruning actually work?

Each manifest file records min/max values per column for every data file it references. When a query has a WHERE timestamp > '2024-06-01' predicate, the engine checks the manifest stats first. If a data file's max timestamp is 2024-05-15, that entire file is skipped without opening it. This can eliminate 90%+ of I/O for selective queries.

Snapshot isolation (MVCC)

Every write creates a new snapshot — a manifest list pointing to the file set as of that write. Readers see a consistent view by reading from a snapshot. Writers create a new snapshot atomically (the catalog pointer updates, or it doesn't). No partial reads, no coordination needed between readers and writers.

Schema and partition evolution without rewrites

The metadata file stores schema history and partition spec history. Old data files keep their original schema and partitioning; new files use the new spec. The engine handles the translation at query time. Your customer's producers can evolve schemas without rewriting their lake. [Iceberg Docs]

The One-Liner to Remember

Iceberg is a file-tracking metadata tree on top of object storage — it gives you transactions, time travel, and schema evolution without a database, without rewriting data, and without listing directories.

Limitations Worth Knowing

  • Metadata accumulates. Every write adds metadata files and manifests. Without compaction (called "rewriting manifests" or table maintenance), metadata bloats and query planning slows. This is an operational concern for the PoC.
    What does compaction look like in practice?

    You run a periodic job (e.g., daily via Glue or Spark) that merges small manifest files into fewer, larger ones and removes snapshots older than a retention threshold. AWS Glue has a built-in OPTIMIZE command for this.

  • Catalog is a single point of coordination. Concurrent writers must go through the catalog for atomic commit. On AWS, Glue handles this — but its throughput has limits (more on this in a later lesson).
  • Not a query engine. Iceberg is a table format — it doesn't execute queries. You still need Athena, Spark, Trino, etc. on top.

Key points to hit

A crawler still lists directories (slow at scale, rate-limited). It gives no isolation — a query mid-crawl sees partial state. And changing the partition scheme requires rewriting all existing data. Iceberg's metadata tree solves all three: manifests replace listing, snapshots give isolation, and versioned specs enable evolution without rewrites.
