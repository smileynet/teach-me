Explain to a colleague why Iceberg uses a metadata tree instead of flat file listing.

A metadata tree enables atomic multi-file commits without locking the catalog. Each snapshot points to a manifest list → manifests → data files, so readers and writers never block each other.

Key benefits:

  • No directory listing at query time
  • Snapshot isolation (MVCC)
  • Schema evolution without data rewrites

What's wrong with this query for reading an Iceberg table?

SELECT *
FROM iceberg_table
WHERE year = 2024
  AND month BETWEEN 1 AND 6;

Uses Hive-style partition predicates (year, month) but Iceberg uses hidden partitioning. Filter on the source column instead:

SELECT * FROM iceberg_table
WHERE event_time >= '2024-01-01'
  AND event_time < '2024-07-01';

Iceberg prunes automatically based on the partition spec — you don't reference partition columns directly.

Explain what this function does and why it might fail under concurrent writes:

def commit_snapshot(catalog, table, new_files):
    current = catalog.load_table_metadata(table)
    manifest = build_manifest(current.snapshot, new_files)
    new_metadata = current.with_snapshot(manifest)
    catalog.update_metadata(table, new_metadata)

This is an optimistic concurrency commit — reads current state, builds new metadata, writes back. It fails because there is no conflict check: between load_table_metadata and update_metadata, another writer could have committed.

Fix: compare-and-swap on the catalog pointer (check it hasn't changed since you read it).
