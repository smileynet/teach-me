glTF Anatomy & the Standard

Lesson 1 · glTF 2.0 · ~7 min read
Win: You can open a .glb/.gltf, name its object graph, and explain how a chunk of bytes becomes a typed array of vertex data.
glTF is "the JPEG of 3D": a delivery format for runtime-ready models — not an authoring format like a .blend. A .gltf is a JSON scene graph; a .glb is that same JSON plus a binary blob packed into one file. Every other topic in this track hangs on the object model you meet here.

Start from the smallest complete file

The fastest way to understand glTF is to read the smallest file that renders: one triangle. Here it is in full, the canonical minimal glTF from the Khronos glTF-Tutorials. Don't memorize it. Read it as a chain of references, top to bottom.

{
  "scene": 0,
  "scenes": [ { "nodes": [0] } ],
  "nodes": [ { "mesh": 0 } ],
  "meshes": [
    { "primitives": [ { "attributes": { "POSITION": 1 }, "indices": 0 } ] }
  ],
  "buffers": [
    { "uri": "data:application/octet-stream;base64,AAABAAIAAAAAAAAAAAAAAAAAAAAAAIA/AAAAAAAAAAAAAAAAAACAPwAAAAA=",
      "byteLength": 44 }
  ],
  "bufferViews": [
    { "buffer": 0, "byteOffset": 0, "byteLength": 6,  "target": 34963 },
    { "buffer": 0, "byteOffset": 8, "byteLength": 36, "target": 34962 }
  ],
  "accessors": [
    { "bufferView": 0, "componentType": 5123, "count": 3, "type": "SCALAR", "min": [0], "max": [2] },
    { "bufferView": 1, "componentType": 5126, "count": 3, "type": "VEC3", "min": [0,0,0], "max": [1,1,0] }
  ],
  "asset": { "version": "2.0" }
}

Each line below references the next by array index:

  • scene → picks scene 0; scenes[0].nodes → node 0.
  • nodes[0] → references mesh 0.
  • meshes[0] has one primitive: its POSITION attribute reads accessor 1, and its triangle indices read accessor 0.
  • Each accessor points at a bufferView, which points at a buffer: the actual bytes.

The last link — accessor to bufferView to buffer — is where the file stops being obvious. Three levels of indirection sit between "draw this triangle" and the raw bytes, so it gets its own section.

How the bytes are stored: buffer → bufferView → accessor

The bytes are stored once and interpreted in three layers, each adding exactly one thing. A buffer is raw bytes. A bufferView is a window into those bytes. An accessor reads that window as N typed elements.

The payoff is that closing equation: the position accessor declares VEC3 of FLOAT (componentType 5126) with count: 3. One element is 4 bytes × 3 = 12 bytes; three of them is 36 bytes — exactly bufferView[1].byteLength. When those numbers reconcile, you know you've read the layout correctly.

Why two objects (bufferView and accessor)? The split lets several accessors read the same buffer — interleaved vertex data (position + normal + UV in one strided window) or two attributes sharing one buffer. The bufferView owns where the bytes are; the accessor owns how to interpret them. A few things people get wrong: count is the number of elements, not bytes; the accessor's byteOffset is relative to its bufferView, not the file; and min/max are the data's bounding box, required on POSITION. [Khronos spec §3.6]

Two container forms: .gltf vs .glb

The exact same object graph ships in two shapes. Which one you reach for is a real choice:

.gltf (text): JSON you can open and read, with geometry either in a sibling .bin + texture files, or inlined as a base64 data: URI (as our triangle does). Human-inspectable; multi-file unless embedded.
.glb (binary): one self-contained file — a 12-byte header, then a JSON chunk, then a BIN chunk holding the raw bytes. Smaller, single-file, the usual shipping form. Not human-readable.

The .glb container is simpler than it sounds. Here are the first bytes of our triangle.glb, decoded by hand — read little-endian:

offset 0:  47 6C 54 46   magic     = 'glTF'
offset 4:  02 00 00 00   version   = 2        ← GLB CONTAINER version
offset 8:  BC 02 00 00   length    = 700 bytes (whole file)
offset 12: 74 02 00 00   chunk0 len = 628
offset 16: 4A 53 4F 4E   chunk0 type = 'JSON'
...628 bytes of JSON (space-padded)... then:
           2C 00 00 00   chunk1 len = 44
           42 49 4E 00   chunk1 type = 'BIN\0'   ← the 44 bytes of geometry
Why does the version read "2" when the asset is glTF 2.0? Those are two different numbers. The 02 at byte 4 is the GLB container version — the wrapper format. The asset version is asset.version: "2.0", inside the JSON chunk. A viewer checks the JSON one to decide if it can render the asset. Confusing the two is the classic first-time glTF mistake. [Khronos spec §4.4]

You don't need a library to prove any of this. The parser below reads either form with the Python standard library alone (struct + json), prints the object graph, and asserts the structure — because "it loaded" is not the same as "it's correct":

import json, struct, sys

GLB_MAGIC = 0x46546C67   # 'glTF' little-endian

def load_gltf(path):
    with open(path, "rb") as f:
        data = f.read()
    if data[:4] != b"glTF":          # a .gltf file IS json
        return json.loads(data)
    magic, version, total = struct.unpack_from("<III", data, 0)
    assert magic == GLB_MAGIC, "not a GLB"
    assert version == 2, f"GLB container version {version} != 2"
    off, gltf = 12, None
    while off < total:               # walk length-prefixed chunks
        clen, ctype = struct.unpack_from("<II", data, off); off += 8
        if ctype == 0x4E4F534A:      # 'JSON'
            gltf = json.loads(data[off:off+clen])
        off += clen                  # ignore unknown chunk types
    return gltf

g = load_gltf(sys.argv[1])
assert g["asset"]["version"] == "2.0"          # ASSET version, not container
for a in g["accessors"]:                       # every accessor -> a real bufferView
    assert 0 <= a["bufferView"] < len(g["bufferViews"])
print("ok:", len(g["accessors"]), "accessors,", len(g["bufferViews"]), "bufferViews")

Run it on either fixture and you get the same graph — one scene, one node, one mesh; two accessors reading two bufferViews out of one buffer. The full downloadable version prints a fuller summary and checks more contracts.

Conventions baked into every glTF

A few global rules the format assumes, worth knowing before they surprise you:

  • Right-handed, +Y up, meters, radians. A node's transform is T · R · S (translation, rotation, scale composed in that order). Models face +Z; a camera looks down its local −Z.
  • Little-endian for all binary data (that's why the parser uses < in struct).
  • Color space is per texture channel — base color is sRGB, data maps like roughness are linear. That distinction is the single most common material bug, and it gets its own lesson (Materials & Textures).

Check Your Understanding

Exercise: A teammate opens a .glb in a hex editor, sees the bytes glTF followed by 02 00 00 00, and tells you "good, this asset is glTF version 2." They've read the wrong number. Why, and where is the real asset version?

Hint

There are two versions in a .glb, in two different places. One describes the wrapper; one describes the 3D asset. Which one does a renderer check to decide if it can load the model?

Answer

Should mention: (1) the 02 at byte offset 4 is the GLB container version — the version of the binary wrapper format, not the asset. (2) The real asset version lives in the JSON chunk as asset.version (a required field, here "2.0"). (3) A viewer checks asset.version (and optionally asset.minVersion) to decide whether it can render the model. Key insight: the container format and the asset spec version are independent — a future GLB container version could still carry a glTF 2.0 asset, and vice versa.
