Authoring & Blender Export

Lesson 2 · glTF 2.0 · ~6 min read
Win: You can tell, before you hit Export, whether a Blender material/mesh/animation will survive the glTF round trip — and fix the ones that won't.
The Blender glTF exporter is a translator, not a renderer. It reconstructs a glTF material by pattern-matching a specific arrangement of shader nodes — chiefly the Principled BSDF — into glTF's fixed channel set. Node graphs it doesn't recognize are re-baked or silently dropped. That's why "it looked right in Blender" and "it exported right" are two different claims.

In Lesson 1 you learned the shape a glTF file has. This lesson is the other half of the round trip: how a DCC tool produces that shape, and — more usefully — how to predict what it will quietly lose.

Three outcomes: what survives, what's re-baked, what's gone

Every material channel, mesh feature, and animation you author lands in exactly one of three buckets on export. The bucket is a property of how you authored it, not of glTF — which is why you can predict it:

Read your own material against the left column. If it's a Principled BSDF with UV-mapped image textures (or flat slider values) wired in the layout glTF expects, it exports byte-for-byte. Everything else is a re-bake-or-lose.

The clean material path

glTF's core material is metal/rough PBR with a fixed set of channels: base color, metallic, roughness, ambient occlusion, normal, emissive. The exporter recognizes a specific node arrangement and copies those textures verbatim:

  • Base color / emissive — an Image Texture (sRGB) into the Principled input.
  • Metallic + roughness — glTF packs metallic in Blue, roughness in Green of ONE Non-Color image. Wire it that way and it's copied as-is; wire it any other way and the add-on re-bakes.
  • Ambient occlusion — glTF stores AO in Red (so O/R/M share one image). Blender has no native node that consumes it the glTF way — you add the custom glTF Material Output node group and plug AO into its Occlusion input.
  • Normal — tangent-space, +Y up, Non-Color, through a Normal Map node.
Alternative — the KHR_materials_* escape hatch: non-default Principled inputs (clearcoat, transmission, sheen, specular, emissive strength, unlit) export as KHR_materials_* extensions. A baseline viewer ignores an extension it doesn't understand (graceful degradation) — but a required extension it can't read will refuse to load. Use extensions when the effect matters and your target supports it; otherwise bake to the core channels. [settings card]

The lesson's downloadable cube_metalrough.glb is exactly this clean layout — a cube with a pbrMetallicRoughness material and a base-color texture. It's built two ways: make_cube_glb.py (stdlib, no Blender) and export_cube.py (the Blender path), so you can see the same glTF from both ends.

Geometry & transform: why it loads rotated, huge, or invisible

Three settings cause the most "it broke on import" bugs, and none are about materials:

Why is my model rotated / the wrong size / not there?
  • +Y Up — Blender is Z-up, glTF is Y-up. The single checkbox handles it; off (or forgotten) is the #1 "loads sideways" cause.
  • Apply Rotation & Scale (Ctrl+A) before export — an unapplied scale exports wrong normals and bounding boxes.
  • Apply Modifiers — the mesh you see (armature, subsurf, mirror) isn't in the file unless this is on.

glTF also always triangulates and splits vertices on discontinuous UVs or flat-shaded edges — so the exported vertex count is higher than Blender's. That's expected, not a bug.

Animation: the Mode choice decides what exports

A glTF animation drives only node transforms (translation/rotation/scale), pose bones, and shape-key weights. Material, light, and physics animation are ignored. The pivotal export setting is Mode:

When to use which Animation Mode:
  • Actions (default) — each action becomes its own clip, but only if it's the active action or stashed / pushed down to an NLA track. Best for game animation libraries.
  • NLA Tracks — each track → one glTF animation; use when you rely on strip modifiers.
  • Scene — exactly what plays on the timeline.
Rule of thumb: multiple actions to ship? Use Actions and stash every one — unstashed actions silently do not export.
Why do my IK/constraint animations come out empty? IK, constraints, and drivers don't exist in glTF — the exporter can only bake their result into keyframes, and only if Sampling is on. The manual is blunt: "Do not sample animation can lead to wrong animation export." [Blender manual: glTF exporter]

Check Your Understanding

Exercise: A colleague's model looks perfect in Blender — a rock textured with a Voronoi procedural, and an arm posed by an IK-driven action — but after glTF export the rock is flat grey and the arm doesn't move. Name the two root causes and the fix for each.

Hint

One failure is in the CLEAN/RE-BAKED/DROPPED material bucketing; the other is about what an Animation Mode can and can't carry out of Blender.

Answer

Should mention: (1) the Voronoi is a procedural texture — it's DROPPED (the exporter is a pattern-matcher; procedural nodes "work only inside Blender"). Fix: bake it to an image texture, then wire that image into the base-color input. (2) IK is not a glTF concept — the arm's motion comes from a constraint, which exports as nothing unless you enable Sampling so the exporter bakes the resulting pose into keyframes. Key insight: both bugs are the same principle — glTF only carries a fixed vocabulary, so anything outside it must be baked into something glTF understands (an image, sampled keyframes) before export.
