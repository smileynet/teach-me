Consuming glTF & Engine Import

Lesson 3 · glTF 2.0 · ~8 min read
Win: You can trace any glTF node to the engine scene-node it becomes, explain why the importer is a one-way translator you don't hand-edit, and say what changes between editor-time and runtime import.
An engine doesn't "open" a glTF — it translates it. In Lesson 1 you learned the object graph a glTF file stores: scenes → nodes → meshes → accessors. A runtime doesn't read that graph the way you open a text file. It translates the graph into its own scene-node types, once, on import, using a fixed concept→node dictionary. The translation is one-way and lossy — a projection, not a bijection: you edit the source glTF, not the imported scene. Godot is this lesson's worked example, but the shape — a fixed dictionary plus a "don't hand-edit" contract — is how three.js, Babylon, and Unity all work too.

The mapping: glTF concept in, engine node out

Every glTF concept has an engine home. The importer's whole job is to walk the file's nodes and build the matching engine node for each — one engine node per glTF node, indexed so it can wire up parenting, skinning, and animation targets afterward. This is not a Godot quirk: Unity's glTFast importer literally holds a Dictionary<uint, GameObject> documented as "glTF node index to instantiated GameObject dictionary." Same dictionary, different vocabulary, in every runtime.

Why is one row dashed? The concrete rows — mesh, skin, material, camera, light, animation — are stated in Godot's class reference. The scene-root type is only recommended: the docs say "using node types that inherit from Node3D is recommended, otherwise you'll lose the ability to position the node directly in the 3D editor" — it's configurable, not mandated. Honest diagrams distinguish a documented rule from a recommended default. [Godot docs — Import configuration, Root Type]

The runtime path: GLTFDocument → GLTFState → generate_scene()

So how does a runtime actually build that tree from bytes on disk? Godot exposes the translator as two resources with a deliberate split of responsibility. GLTFDocument is the processor — it reads and writes, but holds no scene data itself. GLTFState is the container — it holds all the nodes and resources parsed from the file. Keeping the data in GLTFState is what lets GLTFDocument stay stateless and reusable.

The minimal runtime load is three lines: make a document, make a state, populate the state from a file, then generate a scene node from it.

var doc := GLTFDocument.new()
var state := GLTFState.new()
doc.append_from_file("res://character.glb", state)   # parse bytes -> populate GLTFState
var scene_root := doc.generate_scene(state)          # translate GLTFState -> a scene node
add_child(scene_root)
Watch the return type. generate_scene() is typed to return a plain Node, not a Node3D — in practice you get a Node3D tree, but the signature is Node generate_scene(state, ...). This is the runtime path: no editor, no import dock, no cached .tscn. [Godot docs — class GLTFDocument]

Two doors: editor import vs runtime import

The snippet above is only one of the two ways an engine ingests glTF, and the difference matters. When you drop a .glb into the Godot project and it appears in the FileSystem dock, a whole extra layer runs — ResourceImporterScene — that the runtime path skips entirely.

Editor import: runs ResourceImporterScene on top of the glTF translation. Adds name-suffix node typing (-col, -noimp, and friends), material extraction, level-of-detail generation, and scene inheritance. Produces a .import sidecar and a cached scene. All of this machinery is the godot-asset-pipeline track's territory — this lesson only names it, doesn't teach it.
Runtime import: append_from_file → generate_scene. Skips ResourceImporterScene completely — no name-suffix typing, no material extraction. Documented precisely: the EXTRACT_TEXTURES binary-image mode "is editor-only; at runtime it acts the same as EMBED_AS_UNCOMPRESSED."
When to use which:
  • Assets you ship inside the project → editor import. You get the suffix conveniences, extracted materials, and a cached scene for free.
  • Assets you load from disk or the network at runtime → GLTFDocument. There's no importer to run the conveniences, so you wire up collisions and node typing yourself.
Rule of thumb: if the file exists when you build the project, let the editor import it; if it arrives while the game is running, use GLTFDocument. [Godot docs — class GLTFState, HandleBinaryImageMode]

Where engines diverge from the spec

A glTF is a request, not a command. Two importers can read the same file and build different scenes, because the spec leaves room and each engine fills it differently. Three places this bites:

  • Material remap vs passthrough. Godot's texture_map_mode defaults to remapping glTF material slots onto StandardMaterial3D; setting DO_NOT_REMAP leaves the slots raw for a custom shader. Same file, two different material results.
  • Root node modes. root_node_mode (SINGLE_ROOT by default, or KEEP_ROOT / MULTI_ROOT) changes the top-level shape of the imported tree — the same glTF can come in under one root or several.
  • Extension support varies. An importer silently ignores any KHR_materials_* extension it doesn't implement, even though the exporter wrote it.
An extension in extensionsUsed is a request, not a guarantee. The exporter listing an extension means "I used this"; it does not mean the importer honors it. This is the same viewer-dependent behavior you saw with the KHR_materials_* escape hatch in Lesson 2, and it's exactly what the Extensions & Optimization lesson picks apart later.

Try it: see the scene a file becomes

The mapping isn't abstract — you can run it. The companion tool map_to_nodes.py parses a real .glb with the Python standard library alone (no Godot, no dependencies), prints the engine scene tree the importer would build, and asserts the mapping contract holds. Here is its core — the concept→node dictionary applied to a parsed file:

import json, struct, sys

def load_gltf(path):
    with open(path, "rb") as f:
        data = f.read()
    if data[:4] != b"glTF":                       # a .gltf file IS json
        return json.loads(data)
    magic, version, total = struct.unpack_from("<III", data, 0)
    assert magic == 0x46546C67 and version == 2   # 'glTF', container v2
    off, gltf = 12, None
    while off < total:                            # walk length-prefixed chunks
        clen, ctype = struct.unpack_from("<II", data, off); off += 8
        if ctype == 0x4E4F534A:                   # 'JSON'
            gltf = json.loads(data[off:off+clen])
        off += clen                               # ignore unknown chunk types
    return gltf

def map_to_nodes(g):
    nodes = g.get("nodes", [])
    return {                                      # the concept -> engine-node dictionary
        "Node3D": len(nodes),                     # one per glTF node (scene root)
        "MeshInstance3D": sum(1 for n in nodes if "mesh" in n),
        "Skeleton3D": len(g.get("skins", [])),    # + a Skin resource each
        "StandardMaterial3D": len(g.get("materials", [])),
        "Camera3D": len(g.get("cameras", [])),
        "AnimationPlayer": 1 if g.get("animations") else 0,   # all anims -> ONE player
    }

g = map_to_nodes(load_gltf(sys.argv[1]))
print(g)     # {'Node3D': 25, 'MeshInstance3D': 1, 'Skeleton3D': 1, ...}

Run on a rigged character with 17 animations, the full downloadable version prints the whole tree and asserts every mesh, skin, and material resolves:

$ python map_to_nodes.py Wizard.glb
  Engine scene the importer would build (Godot node types, one consumer of many):
    Node3D            x25   (one per glTF node; scene root)
    MeshInstance3D    x1    (nodes carrying a mesh)
    Skeleton3D        x1    (one per skin, + a Skin resource)
    StandardMaterial3D x7   (one per glTF material)
    Camera3D          x0
    AnimationPlayer   x1    (holds all 17 glTF animation(s))

Notice how 17 glTF animations collapse into one AnimationPlayer, and a single skin becomes one Skeleton3D with a Skin resource. That's the dictionary from the diagram, applied to a real file.

Check Your Understanding

Exercise: A teammate imports character.glb, then in the Godot editor renames a bone and tweaks a material directly on the imported scene. Later the artist re-exports the glTF and Godot reimports it — and the teammate's edits are gone. Why did the edits vanish, and where should the change have been made instead?

Hint

The imported scene isn't a file the engine "keeps open" — it's an output. What happens to an output when you re-run the thing that produced it?

Answer

Should mention: (1) the imported scene is generated from the source glTF on every reimport — import is a one-way, lossy projection, so hand-edits to the generated tree are overwritten, not merged. (2) The fix belongs upstream: change the bone name and material in the DCC tool / source glTF, then re-export. (3) If the edit must live on the Godot side, use a sanctioned escape hatch that survives reimport — scene inheritance, extracted (saved-out) materials, or a post-import script — never a direct edit to the generated scene. Key insight: the importer is a translator, not a live link; you edit the input, never the output.
