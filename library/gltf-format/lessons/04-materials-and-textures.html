Materials & Textures

Lesson 4 · glTF 2.0 · ~9 min read
Win: You can read a glTF material object slot by slot, say which texture slots are sRGB and which are linear and why tagging one wrong fails silently, and explain what a KHR_materials_* extension adds and what happens when a viewer doesn't support it.
A glTF material is a tiny fixed object; the subtle part is color space, and the file can't tell the engine which is which. In Lesson 2 you saw the exporter's view: a Principled BSDF pattern-matched into glTF's channels. This lesson is the spec's view: the actual material JSON object, and the one property that isn't in the file at all. Each texture slot has a mandated color space, and glTF says the engine ignores any color info baked into the PNG. Get it wrong and nothing errors; the render is just subtly wrong.

The material object, slot by slot

glTF's core material is deliberately small: a metallic-roughness model plus a handful of texture slots. You met the channels in Lesson 2. What matters here is that each slot carries a mandated color space, and the two families live in the same file with nothing marking them apart. Same bytes, two color worlds, and only the engine knows which slot means which.

The color families are verified against the spec: base color and emissive are sRGB (§5.22.2, §5.19.7); normal, metallic-roughness, and occlusion are linear (§5.19.5, §5.22.5, §5.19.6). The metallic-roughness texture packs roughness in G, metalness in B, and occlusion sits in R — so occlusion and metallic-roughness can share one linear image, the "ORM" layout you met in Lesson 2. [Khronos glTF 2.0 §5.19–5.22, material/texture reference]

Factor × texture

Each metallic-roughness parameter can be a scalar factor, a texture, or both. When both are present, the factor is a linear multiplier of the sampled texel; when a texture is absent, that value is taken as 1.0. So baseColorFactor (a vec4, default [1,1,1,1]) tints the base-color texture, and metallicFactor/roughnessFactor (each default 1.0) scale their slots.

"materials": [{
  "pbrMetallicRoughness": {
    "baseColorTexture": { "index": 0 },        // sRGB image
    "metallicRoughnessTexture": { "index": 1 },// linear image (G=rough, B=metal)
    "metallicFactor": 1.0,
    "roughnessFactor": 1.0
  },
  "normalTexture":    { "index": 2 },          // linear image
  "occlusionTexture": { "index": 1 }           // same linear ORM image, R channel
}]

The color-space trap

Here is the property that isn't in the file. The spec (§3.6.3) is explicit: "Any colorspace information … from PNG or JPEG images MUST be ignored. Effective transfer function is defined by a glTF object that refers to the image." The texture's color space is defined by the slot that references it — not by the image's own metadata. The engine decides; the file only names the slot.

That is why the mistake is silent. Nothing throws — the pipeline loads, exits cleanly, and produces a valid image that is simply wrong:

Base color decoded as linear (missing the sRGB decode): washed-out, too bright, low-contrast albedo. Often reported as "why does my model look faded in the browser?"
A normal or roughness map decoded as sRGB: the sRGB→linear curve distorts the data — warped bumps and lighting, or a mid-gray roughness shift. Subtle, and no error anywhere.
Why is it silent? Every step succeeds at the protocol level — no exception, exit code 0 — so the only evidence is the pixels. It's a common mistake. Each engine surfaces the choice in its own vocabulary: three.js texture.colorSpace, Godot's texture "sRGB" / "Normal Map" import mode, Blender's "Non-Color" dropdown. Same engine-agnostic idea as Lesson 3 (one file, many consumers). [Khronos glTF 2.0 §3.6.3]

Try it: read the color space off a real file

Because glTF has no color-space flag, you can't check the trap by reading a field — you check it structurally: an image must never be used in both an sRGB slot and a linear slot, because the engine can't decode the same bytes both ways. The companion tool parses a real .glb with the standard library alone, prints the slot→color-space table, and asserts exactly that.

import json, struct, sys

SRGB_SLOTS = ("baseColorTexture", "emissiveTexture")
LINEAR_SLOTS = ("normalTexture", "metallicRoughnessTexture", "occlusionTexture")

def load_gltf(path):
    data = open(path, "rb").read()
    if data[:4] != b"glTF":
        return json.loads(data)                    # a .gltf file IS json
    magic, version, total = struct.unpack_from("<III", data, 0)
    assert magic == 0x46546C67 and version == 2    # 'glTF', container v2
    off, gltf = 12, None
    while off < total:
        clen, ctype = struct.unpack_from("<II", data, off); off += 8
        if ctype == 0x4E4F534A:                    # 'JSON'
            gltf = json.loads(data[off:off+clen])
        off += clen
    return gltf

def slot_tex(mat, slot):                           # slot lives at root or under pbrMetallicRoughness
    return mat[slot] if slot in mat else mat.get("pbrMetallicRoughness", {}).get(slot)

def check(gltf):
    textures = gltf.get("textures", [])
    srgb, linear = set(), set()
    for mat in gltf.get("materials", []):
        for slot in SRGB_SLOTS + LINEAR_SLOTS:
            tex = slot_tex(mat, slot)
            if not tex: continue
            img = textures[tex["index"]].get("source")   # texture -> image
            (srgb if slot in SRGB_SLOTS else linear).add(img)
    conflict = srgb & linear                       # an image in BOTH families = the bug
    return conflict

conflict = check(load_gltf(sys.argv[1]))
print("conflict:" , sorted(conflict) or "none")
sys.exit(1 if conflict else 0)

Run it on the both-families cube and every image stays in its lane; feed it an asset that reuses one image across families and it fails with exit 1. The full downloadable version prints the whole slot table and is gated in mise run verify. The cube itself is generated by a second stdlib file:

Extensions add to the base — when the viewer supports them

The core metal-rough model is limited by design. The KHR_materials_* extensions layer more physically-based behavior on top: emissive_strength (HDR emission past the [0,1] clamp), transmission (real refraction rather than alpha coverage), clearcoat, sheen, ior, and specular.

An extension in extensionsUsed is a request, not a guarantee — the same point from Lesson 3, sharpened. A material extension should not appear in extensionsRequired, because the core metal-rough material is a valid fallback: a viewer that doesn't implement the extension simply drops the effect silently — glass renders opaque, clearcoat vanishes, HDR emission clamps. (Only things with no fallback, like compression, belong in extensionsRequired, where an unsupporting loader must refuse the whole asset.) So the same file can look markedly different across engines. [Khronos glTF 2.0 §3.12]

Check Your Understanding

Exercise: An artist's model looks perfect in Blender but washed-out and too bright in a web viewer. The base-color PNG is correct. Given the image is just raw bytes like [188, 188, 188], how does the renderer decide whether to treat that as sRGB or linear — and why does neither tool show an error?

Hint

The PNG's own color tags are ignored (§3.6.3). If the answer isn't in the bytes, where must it live?

Answer

Should mention: (1) the file can't tell it — absent any honored metadata, the color space is a convention the consumer assumes, defined by the glTF slot that references the image, not the bytes. (2) Here the base-color slot's texture was decoded as linear instead of sRGB, so the sRGB decode never happened → washed-out/too-bright. (3) No error because every step succeeds at the protocol level — it's a semantic failure, visible only in the pixels; the fix is to assign the base-color slot the sRGB transfer function. Key insight: the correct answer lives in the slot/pipeline contract, never in the image bytes.
