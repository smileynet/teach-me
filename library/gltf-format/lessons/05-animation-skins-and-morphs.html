Animation, Skins & Morphs

Lesson 5 · glTF 2.0 · ~10 min read
Win: You can explain what an inverse-bind-matrix does and why a skinned mesh must export in bind/rest pose, read a glTF animation as channels + samplers with an interpolation mode, and say how a morph target differs from a skinned deformation.
A skinned mesh is stored once, in bind pose — animation never edits vertices, it moves joints. In Lesson 3 you saw a skin collapse into a Skeleton3D and 17 animations into one AnimationPlayer. This lesson is the model underneath: each vertex rides a chain of matrices from the joint that drives it, the inverse-bind-matrix is the hinge that makes it work, and it only works if the geometry is in the bind pose those matrices were computed for. That one fact is the spec-level reason rigged meshes must export in rest pose.

The skinning chain

Animation doesn't touch vertices. It moves joints, and every vertex follows the joints that influence it through a short chain of matrices. Read it right to left, like function calls — the rightmost runs first and hands its result leftward:

The trick is the InverseBind matrix. A vertex is authored once, in model space. To let a joint rotate that vertex "around itself," you first re-express the vertex relative to the joint's own origin — that's exactly what the inverse-bind-matrix does ("if the bind-pose joint sat at the origin, where is this vertex?"). Then the joint's current animated world transform carries it to its posed location. Notice how the space labels line up: model → joint-local → world. Get the order wrong or drop the inverse, and the labels stop matching — that's the whole check, no arithmetic needed.

New concept — change of basis: the inverse-bind-matrix is a change of basis — it describes the same vertex in the joint's grid instead of the model's grid. The vertex doesn't move; only the numbers describing it change. (The spec's full form also normalizes by the skinned node's own transform, which is usually identity — the three-factor chain here is the teaching form.)

Why bind pose matters

Here is the payoff every earlier lesson pointed at. All glTF animation is expressed as a delta from the bind pose — a channel that says "rotate 30°" means 30° beyond the bind-pose rotation. The bind pose is the shared reference frame that ties the animation to the geometry, and the inverse-bind-matrices encode each joint's bind-pose world transform. If the exported geometry isn't actually in that bind pose, InverseBind · RestPos lands every vertex in the wrong joint-local space and the mesh contorts.

Why does my imported character look like spaghetti? Stretched-to-origin limbs, exploded joints, or a mesh rotated 90° off its skeleton are all one bug: the bind pose the mesh was exported in doesn't match the bind pose the inverse-bind-matrices encode. The classic Blender trigger is a non-identity armature-object transform (Mixamo rigs import with a +90° X rotation and ~0.009 scale); on export that transform merges into the root bone and shifts the bind pose. The fix is to apply all transforms before export. This is the spec-level root of Lesson 2's "Export Deformation Bones Only" gotcha — and because it's a spec-level contract, the same failure shows up in Unity, three.js, and Babylon too. Animation = channels + samplers

A glTF animation is two arrays working together. A channel says what to animate; a sampler says how it changes over time.

"animations": [{
  "channels": [
    { "sampler": 0, "target": { "node": 3, "path": "rotation" } }
  ],
  "samplers": [
    { "input": 8, "interpolation": "LINEAR", "output": 9 }
  ]
}]

The channel's target is a node plus a path — one of translation, rotation, scale, or weights (animated nodes use TRS, never a matrix). The sampler's input is an accessor of strictly-increasing FLOAT timestamps, and output is the matching values. Samplers can be shared across channels. That's it — 17 animations on a character are just many of these channel/sampler pairs pointing at the skeleton's joint nodes.

Interpolation: how the sampler fills the gaps

When to use which:
  • LINEAR (the default) — straight-line blend between keyframes; rotations slerp. Output count equals input count. Use for most motion.
  • STEP — hold the previous value until the next key. Output count equals input. Use for discrete switches (a light toggling, a hard pose swap).
  • CUBICSPLINE — smooth authored curves. Stores an in-tangent, the value, and an out-tangent per key, so its output has 3× the keyframes and needs at least 2 keys. Use for hand-tuned easing, at 3× the data cost.
Rule of thumb: LINEAR unless you specifically need STEP's snapping or CUBICSPLINE's authored curves.

Morph targets: a different kind of deformation

Skinning re-poses shared geometry with rigid joints. A morph target does something different: it moves vertices by per-vertex deltas. Each target stores POSITION (and optionally NORMAL/TANGENT) offsets, and the rendered vertex is base + Σ weights[j] · target[j]. Animate the mesh.weights via a channel whose path is "weights", and you blend smoothly between shapes.

Skin: rigid joints re-pose one shared mesh through the matrix chain. Good for skeletal motion — walking, waving.
Morph: blend between stored geometry snapshots by weight. Good for shapes a skeleton can't express — facial expressions, a smile dialing in. "Blend shapes" and "shape keys" are the same thing.

Try it: read the rig off a real file

The companion tool parses a real rigged .glb with the standard library alone and asserts the contracts above — the skin's inverse-bind-matrices are MAT4/float with one per joint, a skinned primitive carries JOINTS_0 + WEIGHTS_0, and every animation sampler has a valid time input and interpolation mode:

import json, struct, sys

def load_gltf(path):
    data = open(path, "rb").read()
    if data[:4] != b"glTF":
        return json.loads(data)
    magic, version, total = struct.unpack_from("<III", data, 0)
    assert magic == 0x46546C67 and version == 2
    off, gltf = 12, None
    while off < total:
        clen, ctype = struct.unpack_from("<II", data, off); off += 8
        if ctype == 0x4E4F534A:
            gltf = json.loads(data[off:off+clen])
        off += clen
    return gltf

g = load_gltf(sys.argv[1])
accessors = g.get("accessors", [])
for si, skin in enumerate(g.get("skins", [])):        # the skin/IBM contract
    ibm = skin.get("inverseBindMatrices")
    if ibm is None: continue
    acc = accessors[ibm]
    assert acc["type"] == "MAT4" and acc["componentType"] == 5126   # float MAT4
    assert acc["count"] >= len(skin.get("joints", []))              # one IBM per joint

for ai, anim in enumerate(g.get("animations", [])):    # channels + samplers resolve
    for s in anim.get("samplers", []):
        interp = s.get("interpolation", "LINEAR")
        assert interp in ("LINEAR", "STEP", "CUBICSPLINE")
        assert accessors[s["input"]]["type"] == "SCALAR"           # time is scalar
print("ok:", len(g.get("skins", [])), "skin,", len(g.get("animations", [])), "animations")

Check Your Understanding

Exercise: An artist poses their character mid-crouch, exports to glTF, and in the engine the imported mesh is contorted — limbs stretched toward the origin. The rig and weights are fine. What went wrong, and what's the one-line fix?

Hint

All animation is a delta from the bind pose, and the inverse-bind-matrices encode a specific pose. What did exporting mid-crouch do to the pose the mesh was stored in?

Answer

Should mention: (1) the mesh was exported in the current (crouch) pose, but the inverse-bind-matrices encode a different bind pose — so InverseBind · RestPos sends every vertex into the wrong joint-local space. (2) Because all animation is a delta from the bind pose, a mismatched bind pose corrupts every frame, not just the first. (3) The fix: export in the rest/bind pose the skin was bound in — apply the rest pose / apply all transforms before exporting. Key insight: the bind pose is the shared reference frame; the mesh and its IBMs must agree on it, or the whole chain lands in the wrong space.
