Extensions & Optimization

Lesson 6 · glTF 2.0 · ~9 min read
Win: You can explain the extensionsUsed-vs-extensionsRequired contract and why a compression extension must be required while a material extension should not, choose between Draco and meshopt, and name the tool that tells you whether a file is spec-conformant before you ship it.
An extension is how glTF grows — and extensionsRequired is the promise "you can't render this without me." Lesson 3 introduced the idea that an extension is a request, not a guarantee, and Lesson 4 sharpened it into a rule. This capstone turns that rule into a mechanism you can apply to any extension with one question: does the core still render without this? If yes, it's optional; if no, it's required. That single split is what lets you shrink a file to ship it without breaking older viewers.

The one decision: used vs required

Every extension is named by who authored it — KHR_ (Khronos-ratified), EXT_ (multi-vendor), or a vendor prefix. But the property that matters at ship time isn't the prefix; it's which of two arrays the extension goes in. A file lists everything it uses, and separately lists what a viewer must understand. Decide with one question:

The two arrays borrow their meaning from RFC 2119: required = MUST understand, used-only = MAY ignore. A real file shows the split plainly — Kenney's truck-green.glb lists KHR_materials_unlit and KHR_texture_transform in used, but only KHR_materials_unlit in required.

The extension set evolves. The Khronos glTF extension registry is the source of truth for what's ratified. As of this writing (2026), the ratified KHR_ set includes the compression, texture, and material extensions named in this lesson (Draco, texture_basisu, materials_variants, materials_* PBR extensions) plus KHR_texture_transform, KHR_mesh_quantization, and KHR_lights_punctual; EXT_meshopt_compression is the multi-vendor geometry compressor. Check the registry for the current list before relying on any one extension.

Geometry compression: Draco vs meshopt

The most common reason to reach for a no-fallback extension is size. Two extensions compress geometry, and they trade off differently:

When to use which:
  • Draco (KHR_draco_mesh_compression) — the smallest files (roughly 70–90% off mesh geometry, reported). Cost: decode is markedly slower and needs a ~200 KB WASM decoder; geometry only.
  • meshopt (EXT_meshopt_compression) — a lightweight decoder that decodes near-instantly with SIMD, produces GPU-friendly quantized data, and covers geometry, morphs, and animation.
Rule of thumb: Draco when transmission bytes dominate and decode budget is generous (one-time load, slow network); meshopt when decode latency, mobile, or animation matter. Both must be extensionsRequired — the buffer bytes are literally unreadable without the decoder. Neither raises framerate (both CPU-decode before GPU upload).

Texture supercompression and variants

KHR_texture_basisu wraps a KTX2 / Basis Universal payload that transcodes to the GPU's native block format and stays compressed in VRAM — unlike PNG/JPEG, which decode to raw RGBA (large memory, slow upload). It's also a no-fallback, required extension. And KHR_materials_variants stores several material sets over one mesh (per-primitive name→material mappings) so a product viewer can swap colorways with no geometry duplication — it can fall back to the default material, so unlike compression it needn't be required.

Validate, then optimize

Two tools bracket the ship step, and the order matters. First check the file is correct; only then change it.

Validate first, optimize second. The Khronos glTF Validator is the reference conformance checker (severities: Error / Warning / Information / Hint). It catches semantic bugs a structural parser misses — misaligned accessor offsets, bufferViews exceeding the buffer, non-monotonic animation sampler inputs, a skin joint referencing a missing node. It's a Node tool (gltf-validator) with a CI-gateable CLI. Then gltf-transform (a separate CLI) optimizes — it is not a validator, so run it after. Its passes apply in order: prune/dedup → quantize → Draco/meshopt → KTX2 → and gzip/brotli last (a transport layer on the finished bytes, never gzip-then-optimize).
Don't over-optimize. A Draco file can render slower to first frame on a low-end device than an uncompressed one — the ~200 KB decoder plus decode time can outweigh the smaller download. Export two candidates and test on the weakest device you support. And remember the contract: making Draco, meshopt, or KTX2 required breaks every non-supporting baseline viewer — that's the whole point of the decision above.

Try it: read the contract off a real file

The companion tool parses a .glb/.gltf with the standard library alone, prints a per-extension table (its class and whether it has a fallback), and asserts the contract — a compression extension left out of extensionsRequired is a hard error; a material extension forced into it is a note:

import json, struct, sys

COMPRESSION_EXTS = {"KHR_draco_mesh_compression", "EXT_meshopt_compression", "KHR_texture_basisu"}
MATERIAL_EXT_PREFIX = "KHR_materials_"

def load_gltf(path):
    data = open(path, "rb").read()
    if data[:4] != b"glTF":
        return json.loads(data)
    magic, version, total = struct.unpack_from("<III", data, 0)
    assert magic == 0x46546C67 and version == 2
    off, gltf = 12, None
    while off < total:
        clen, ctype = struct.unpack_from("<II", data, off); off += 8
        if ctype == 0x4E4F534A:
            gltf = json.loads(data[off:off+clen])
        off += clen
    return gltf

g = load_gltf(sys.argv[1])
used = g.get("extensionsUsed", [])
required = set(g.get("extensionsRequired", []))
errors = []
for ext in required:                                  # spec 3.12: required is a subset of used
    if ext not in used: errors.append(f"{ext} required but not used")
for ext in used:                                      # a no-fallback ext MUST be required
    if ext in COMPRESSION_EXTS and ext not in required:
        errors.append(f"{ext} is compression but not required (viewer would read garbage)")
print("errors:", errors or "none")
sys.exit(1 if errors else 0)

Run it on the truck and it passes with a note about the required unlit material; the full downloadable version prints the fallback table and is gated in mise run verify. A minimal fixture demonstrates the correct compression placement:

Check Your Understanding

Exercise: A teammate ships a product-viewer model that renders fine on their machine but shows nothing on an older device. The file lists KHR_materials_unlit in both extensionsUsed and extensionsRequired, and the geometry is Draco-compressed but KHR_draco_mesh_compression appears only in extensionsUsed. Which of those two choices is backwards, and what breaks in each case?

Hint

Apply the one question to each extension: does the core still render without it? One has a fallback; one doesn't.

Answer

Should mention: (1) Both are backwards. (2) KHR_materials_unlit has a valid fallback — core metal-rough — so forcing it required makes a non-supporting viewer refuse a file it could have rendered (per the spec it SHOULD NOT load an asset whose required extension it can't support); move it to used-only. (3) Draco has no fallback — the buffer bytes are unreadable without the decoder — so leaving it used-only lets a non-supporting viewer try to read garbage geometry; it must be required. Key insight: required means "the bytes are unreadable without me" — true for compression, false for materials.
