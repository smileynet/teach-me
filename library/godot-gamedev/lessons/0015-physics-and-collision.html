Physics & Collision Systems

Lesson 15 · Game Development with Godot · ~8 min read
Win: You can pick the right body type for an object, wire up collision layers and masks so the right things collide, move a character with the correct method, and cast a ray to sense the world — and explain why each choice is the right one.
After this lesson: You know Godot's four collision-object node types and when to use each, how collision layers and masks decide what collides, the difference between move_and_slide() and move_and_collide() for moving a CharacterBody, and how raycasting lets an object sense the world without touching it.

The Problem: Which Node Enforces Physical Rules?

Everything in Godot is a node, but a bare node has no notion of "solid." To make a floor a character can stand on, a crate that tumbles when hit, or a coin that vanishes on touch, you need a collision object. Godot offers four of them, and picking the wrong one is the most common beginner mistake — a player built as a RigidBody fights your input; a falling crate built as a CharacterBody just floats. The choice comes down to one question: how should this object move and react? [Godot Docs: Physics Introduction]

When to use which:
  • StaticBody3D — level geometry that never moves dynamically. Default for the world.
  • RigidBody3D — you want "realistic" motion for free (debris, dropped props). Apply forces; never set position directly.
  • CharacterBody3D — a player or NPC needing precise, code-controlled movement with slope/wall detection.
  • Area3D — you only need to detect overlap or override gravity in a region, not block movement.
Rule of thumb: if you write the movement, use CharacterBody; if the engine should, use RigidBody; if it never moves, StaticBody; if it only senses, Area.

All four extend CollisionObject3D, and every one needs at least one CollisionShape3D child holding a shape — the node itself has no size until you give it one. The three that are physics bodies (Static, Rigid, Character) also share PhysicsBody3D. A RigidBody even goes to sleep when it comes to rest, so a pile of settled crates costs almost nothing.

Collision Layers and Masks: What Is Allowed to Collide

Having the right body type is only half the story. Two objects only interact if the layer system says they may. Every collision object has 32 physics layers controlled by two properties, and confusing them is the second-most-common beginner trap.

The collision_layer is the set of layers this object appears in — it answers "who am I?" The collision_mask is the set of layers this object scans — it answers "what do I look for?" For object A to detect object B, B must appear in a layer that A's mask includes. [Godot Docs: Physics Introduction]

Say your game has four kinds of thing: Walls, a Player, an Enemy, and a Coin. You want Player and Enemy to collide with Walls, the Player to detect the Enemy and the Coin, and the Enemy and Coin to ignore each other. Name layers 1–4 in Project Settings → Layer Names → 3D Physics ("walls", "player", "enemies", "coins"), put each node in its own layer, then set each node's mask to only the layers it should react to:

# The Player scans for walls (1), enemies (3), and coins (4).
# Bit-shift form: layer N is bit N-1, combined with binary OR.
collision_mask = (1 << 1 - 1) | (1 << 3 - 1) | (1 << 4 - 1)   # = 1 + 4 + 8 = 13

# Clearer, per-layer form — does the same thing:
set_collision_mask_value(1, true)  # walls
set_collision_mask_value(3, true)  # enemies
set_collision_mask_value(4, true)  # coins

The bitmask 13 and the three set_collision_mask_value calls are equivalent — the second is just readable. That single property is why the Player notices the Coin but the Coin never reacts to the Enemy: the Coin's mask simply doesn't include the enemy layer.

Moving a Character: slide vs collide

A CharacterBody won't move on its own — you drive it in code. It gives you two movement methods, and both must be called inside _physics_process() (never set position directly). The difference is who handles the response when you hit something.

move_and_collide() is the general one: you hand it a motion vector, it moves until it hits something, then stops and returns a collision object (or null). You decide what happens next — perfect for a bullet that ricochets off the surface it hits:

var collision = move_and_collide(velocity * delta)
if collision:
    # Reflect off the surface we hit and keep going.
    velocity = velocity.bounce(collision.get_normal())

Most of the time, though, you want a character to slide along walls and floors instead of stopping dead. That's what move_and_slide() automates. Notice what changes: it reads the node's velocity property instead of taking an argument, and it applies the slide response for you.

extends CharacterBody3D

@export var speed: float = 5.0
@export var gravity: float = 9.8

func _physics_process(delta: float) -> void:
    # Gravity is an acceleration, so it IS multiplied by delta.
    if not is_on_floor():
        velocity.y -= gravity * delta

    var input := Input.get_vector("left", "right", "forward", "back")
    velocity.x = input.x * speed
    velocity.z = input.y * speed

    # move_and_slide() already accounts for the timestep —
    # do NOT multiply velocity by delta here.
    move_and_slide()
Why no * delta on velocity? This is the single most common physics bug in Godot. move_and_slide() already includes the timestep internally, so multiplying velocity by delta makes your character crawl at 1/60th speed. Gravity is different — it's an acceleration, so it must be scaled by delta. [Godot Docs: the move_and_slide warning]

Because move_and_slide() also updates velocity on impact (zeroing your downward speed the instant you land), the helpers is_on_floor(), is_on_wall(), and is_on_ceiling() become reliable right after the call. The docs frame it plainly: slide is the special case, collide is the general one — anything slide does, collide can do with a few more lines. [Godot Docs: Using CharacterBody]

Raycasting: Sensing Without Touching

Sometimes an object needs to know what's ahead of it without moving there — is the ground still under my feet? is the player in my line of sight? what did the mouse click on? That's raycasting: fire an invisible ray and report the first thing it hits.

The simplest approach is the RayCast3D node — drop it in the scene, point it, and it reports every frame what it hit. For a one-off query in code, ask the physics space directly. The catch: the space is locked outside _physics_process(), so the query only works there.

extends CharacterBody3D

func _physics_process(delta: float) -> void:
    var space_state := get_world_3d().direct_space_state
    var from := global_position
    var to := from + Vector3.DOWN * 2.0

    var query := PhysicsRayQueryParameters3D.create(from, to)
    query.exclude = [self]              # don't let our own body block the ray
    query.collide_with_areas = true     # Area3D is off by default

    var result := space_state.intersect_ray(query)
    if result:
        # Dictionary is EMPTY on a miss; on a hit it has these keys.
        print("Standing on: ", result.collider)
        print("Ground normal: ", result.normal)

The result is a plain dictionary — empty when the ray hits nothing, otherwise carrying position, normal, and the collider it struck (plus its id, rid, and shape index). Two details save hours of debugging: set exclude = [self] so a body's ray doesn't hit its own collider, and enable collide_with_areas when you need to detect an Area3D. To pick an object under the mouse, build the ray from a Camera3D with project_ray_origin() and project_ray_normal(). [Godot Docs: Ray-casting]

Check Your Understanding

Exercise: A teammate is building a floating platform that carries the player. They chose a RigidBody3D and are calling move_and_slide() on it every frame to make it travel. It behaves erratically — jittering, sometimes launching the player. What did they get wrong, and which body type and control approach should they use instead?

Hint

Match the body type to who controls the motion. move_and_slide() is a CharacterBody method. What is a RigidBody controlled by? And for a platform that follows a fixed path, does the engine need to simulate it at all?

Answer

Should mention: (1) move_and_slide() is a CharacterBody movement method — calling it on a RigidBody is the category error; a RigidBody is controlled by forces/impulses the engine simulates, not by direct movement calls, so fighting the simulation causes the jitter. (2) A platform on a fixed path shouldn't be physics-simulated at all — the right choice is an AnimatableBody3D (a StaticBody subclass), moved by code or animation, which cleanly imparts its motion to bodies riding on it. (3) A CharacterBody could also work if you drive it manually, but AnimatableBody is simpler for a scripted path. Key insight: pick the body type by asking "who moves this?" — engine (Rigid), my code with collision response (Character), a fixed path (Animatable/Static), or nothing (Static).
