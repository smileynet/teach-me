Albedo Posterization in Blender Nodes

Lesson 16 · Blender to Godot Texture Prep · ~14 min read
Win: You can build a reusable Blender node group that posterizes any albedo to N color bands, explain why it's the same floor-divide math your toon shader uses for lighting, and choose N (and truncate vs. round) for a given look.
After this lesson: Posterizing albedo and banding lighting are the same floor(x*N)/N operation at two different stages. Matching their band counts is what makes a prepped texture and a toon shader look like they belong together.

The Problem

In the previous lesson you diagnosed why a photoreal albedo fights toon shading: its continuous, high-frequency color detail gets amplified into noise when the shader quantizes lighting. The fix isn't to delete the albedo — you need base color — it's to simplify it: reduce its thousands of colors to a handful of flat bands that harmonize with your toon shader's band count.

The tool for that is posterization, and the surprise is that it's the exact same math your toon shader already runs. This lesson builds a reusable Blender node group that posterizes any texture, using the same floor-divide operation the shader uses on lighting.

Posterization is the shader's banding, applied to color

Your toon shader turns smooth lighting into discrete bands with a floor-divide. In posterize_albedo.gdshader the light banding is literally:

float bands = floor(NdotL * shadow_bands) / shadow_bands;

Take that same expression and feed it a color channel instead of a lighting value, and you get color posterization. The same shader does exactly this to its albedo:

// posterize_albedo.gdshader — albedo posterize
float n = float(color_levels);      // 2..16
ALBEDO = floor(tex_color * n) / n;  // quantize each channel to N levels

floor(x * N) / N multiplies a 0–1 channel up to the range 0–N, floors away the fractional part (collapsing everything between two integers into one value), then divides back down. The result: any input color snaps to one of N flat levels per channel. We're going to build that in Blender's node editor so you can bake it into a texture — reducing color complexity before it ever reaches the shader.

Build the Posterize RGB node group

Blender's shader editor has no built-in posterize node (that only exists in the compositor), so we build one from Vector Math nodes. Vector Math operates on all three RGB channels at once, so a single chain quantizes the whole color — no need to split channels.

Step 1 — scale the color up by N

Feed the texture color into a Vector Math → Multiply, multiplying by (N, N, N). A channel value of 0.42 at N=4 becomes 1.68. This spreads the 0–1 range across 0–N so the floor has integers to snap to.

Image Texture (Color) ─▶ Vector Math: Multiply  ×(N, N, N)

Step 2 — floor away the fraction

Pass the scaled color into a Vector Math → Floor. 1.68 becomes 1.0; everything from 1.0 to 1.999 collapses to 1.0. This is the quantization step — the moment a continuous range becomes a single discrete value.

Vector Math: Multiply ─▶ Vector Math: Floor

Step 3 — scale back down

Divide by (N, N, N) to return to the 0–1 range. 1.0 becomes 0.25. Now every pixel sits on one of N flat levels: 0, 1/N, 2/N, … Wire the result to Base Color (or an Emission node if you're going to bake it).

Vector Math: Floor ─▶ Vector Math: Divide  ÷(N, N, N) ─▶ Base Color

To make N a single adjustable knob, drive all three components of the multiply/divide vectors from one Combine XYZ node fed by a group input called Levels. Wrapping the whole chain in a node group ("Posterize RGB") makes it a one-click, reusable tool with a Color input, a Levels input, and a Color output.

The complete node group

Rather than click the graph together by hand every time, this script builds the whole group in one run. Open it in Blender's Scripting workspace and press Run, then add Group → Posterize RGB to any material.

import bpy

GROUP_NAME = "Posterize RGB"

def build_group(levels_default: int = 4):
    if GROUP_NAME in bpy.data.node_groups:
        bpy.data.node_groups.remove(bpy.data.node_groups[GROUP_NAME])
    ng = bpy.data.node_groups.new(GROUP_NAME, "ShaderNodeTree")

    ng.interface.new_socket("Color", in_out="INPUT", socket_type="NodeSocketColor")
    lv = ng.interface.new_socket("Levels", in_out="INPUT", socket_type="NodeSocketFloat")
    lv.default_value, lv.min_value, lv.max_value = float(levels_default), 2.0, 16.0
    ng.interface.new_socket("Color", in_out="OUTPUT", socket_type="NodeSocketColor")

    nodes, links = ng.nodes, ng.links
    gin = nodes.new("NodeGroupInput")
    gout = nodes.new("NodeGroupOutput")

    # Broadcast scalar Levels to a vector so Vector Math can scale RGB by it
    combine = nodes.new("ShaderNodeCombineXYZ")
    for axis in ("X", "Y", "Z"):
        links.new(gin.outputs["Levels"], combine.inputs[axis])

    mul = nodes.new("ShaderNodeVectorMath"); mul.operation = "MULTIPLY"
    flr = nodes.new("ShaderNodeVectorMath"); flr.operation = "FLOOR"
    div = nodes.new("ShaderNodeVectorMath"); div.operation = "DIVIDE"

    links.new(gin.outputs["Color"], mul.inputs[0])
    links.new(combine.outputs["Vector"], mul.inputs[1])   # color * N
    links.new(mul.outputs["Vector"], flr.inputs[0])       # floor(color * N)
    links.new(flr.outputs["Vector"], div.inputs[0])
    links.new(combine.outputs["Vector"], div.inputs[1])   # / N
    links.new(div.outputs["Vector"], gout.inputs["Color"])
    return ng

if __name__ == "__main__":
    build_group()

Choosing N: too few kills form, too many keeps noise

Here's the barrel's albedo baked through the group at three band counts, next to the original. These are real Blender Emit bakes of the node group — the actual tool output, not a mock-up.

At N=4 the barrel reads as a few flat color zones — strongly stylized, but the rust and wear that give it character are gone. At N=16 most of that detail survives, but so does much of the noise the toon shader will amplify. The sweet spot is usually a small multiple of your shader's light-band count: enough color steps to keep recognizable form, few enough to stay flat. Match, don't fight, the shader.

Why not just use N = your shader's band count? A 4-band toon shader does not require a 4-level albedo — lighting bands and color bands are independent axes. Posterizing albedo to 4 usually looks lifeless (that's the exercise below). Start around 8–12 for albedo and tune by eye.

Truncate vs. round: preserving white

The group above uses floor(x·N)/N — faithfully mirroring the shader. But notice its output levels for N=4 are 0, 0.25, 0.50, 0.75: the brightest a channel can get is (N-1)/N = 0.75. Pure white never survives — every highlight is dimmed. That truncation also biases the whole image slightly dark.

The textbook fix is to round to the nearest level and spread the levels across the full 0–1 range, using N-1 as the divisor:

// canonical: exactly N levels, anchored at BOTH 0.0 and 1.0
result = floor(x * (N - 1) + 0.5) / (N - 1);   // N=4 → 0, 0.333, 0.667, 1.0

The + 0.5 turns the floor into round-to-nearest (unbiased), and dividing by N-1 makes black stay black and white stay white. In the node group, that's a Round node instead of Floor, with the multiply/divide using N-1.

When to use which:
  • floor(x·N)/N (truncate) — use when you want to match a shader that bands this way, or deliberately want a darker, punchier palette with no pure white.
  • floor(x·(N-1)+0.5)/(N-1) (canonical) — use when highlights matter and you want black and white preserved as clean anchors. This is what image editors call "posterize."
Default: the canonical form for albedo prep — you almost always want white to stay white. Reach for truncate only to match specific shader behavior.
Gotcha — pin the input Color Space. Blender decodes an sRGB ("Color") texture to linear before it reaches these math nodes, so equal-width bands in linear space bunch up in the shadows. A "Non-Color" texture is quantized on its stored values, giving perceptually even bands. Neither is "correct" — it's a style choice — but Blender auto-guesses the space (sRGB for PNG/JPG), so set it explicitly on the Image Texture node or your bake won't be reproducible. The bakes above used Non-Color.

Check Your Understanding

Exercise: A teammate's toon shader uses 4 lighting bands. Reasoning that "everything should match," they posterize their character's albedo to 4 levels with the truncate form floor(x·4)/4. The result looks flat, muddy, and the character's white gloves have gone gray. They ask you to explain both problems and fix them. What do you tell them?

Hint

Two separate issues. One is about matching band counts across two independent axes. The other is about what floor(x·N)/N does to a value of 1.0.

Answer

Muddy/flat: lighting bands and albedo levels are independent — a 4-band shader does not need a 4-level albedo. Four color levels is far too few to preserve a character's form; the albedo should be posterized to something like 8–12 and tuned by eye. Matching the number to the shader's band count is a false intuition.

Gray gloves: the truncate form tops out at (N-1)/N — at N=4 the brightest any channel reaches is 0.75, so pure-white gloves become 75% gray. Switch to the canonical form floor(x·(N-1)+0.5)/(N-1) (a Round node, divide by N-1), which keeps white at 1.0. So: raise the level count, and use the round-to-nearest form so highlights survive.
