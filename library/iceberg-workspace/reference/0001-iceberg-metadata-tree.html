Iceberg Metadata Tree

Reference · Companion to Lesson 1

Core Concept

Iceberg is a metadata tree stored alongside data in S3. Instead of listing directories to find files, query engines follow the tree: catalog → metadata file → manifest list → manifests → data files. The tree replaces listing (manifests know the files), gives isolation (snapshots are immutable), and enables evolution (specs are versioned).

The Metadata Tree (4 layers below catalog)

LayerWhat it storesFormat / Location
Catalog (external)Pointer to current metadata fileAWS Glue / REST endpoint
Table metadata fileSchema history, partition specs, snapshots (each → manifest list)JSON in S3 metadata/
Manifest listWhich manifests are active for one snapshotAvro in S3 metadata/
Manifest fileData file + delete file paths, per-file column statsAvro in S3 metadata/
Data filesTable rowsParquet in S3 data/
Delete files (V2+)Row-level deletes/updates (position, equality, or deletion vectors)Parquet in S3 data/

Key detail: Snapshots live INSIDE the metadata file (not a separate layer). Each snapshot = timestamp + sequence number + pointer to a manifest list.

Why This Design

ProblemHow Iceberg solves it
S3 listing is slow/rate-limited at scaleManifests track files directly — no listing needed
No read isolation during writesSnapshots = MVCC — readers see a frozen file set
Schema/partition changes require rewritesVersioned specs — old files keep old schema, engine translates
Row-level deletes impossible on immutable filesDelete files mark rows as removed; applied at read time (V2+)

Mandatory Maintenance (5 operations, in order)

  1. Expire snapshots — remove old snapshot references
  2. Remove orphan files — delete unreferenced files
  3. Rewrite manifests — merge small manifests
  4. Compact data files — merge small data files
  5. Remove delete files — apply and clean up deletes

Skip these → metadata bloats → query planning slows → S3 costs climb.

Decision Aid

"Should this table use Iceberg?"

  • Multiple teams reading/writing concurrently → yes
  • Schema will evolve over time → yes
  • Millions of files, need fast scan planning → yes
  • Need time travel / audit → yes
  • Small table (<100 GB), single writer, append-only → no, plain Parquet is simpler
  • Sub-second visibility needed → no, Iceberg is batch-atomic
  • High-frequency keyed upserts → consider Hudi instead

Key Terms

TermMeaning
SnapshotJSON object in metadata file — frozen view of table state (pointer to manifest list)
Scan planningUsing manifest stats to skip files that can't match the query predicate
Schema evolutionChanging columns without rewriting files — engine translates at read time
Delete fileMarks rows as removed (position/equality/vector) — applied at read time, not modifying data files
OCC (optimistic concurrency)Writers build metadata optimistically; commit fails if catalog changed since read — retry with backoff
