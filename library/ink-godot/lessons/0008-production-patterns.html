Production Patterns

Lesson 8 · Ink + Godot · ~18 min read
Win: You can architect a multi-story ink game the way a shipped title does — a handful of state-bus variables carrying cross-story state, each dialog stateless so it starts fresh, and one hub-and-spoke loop driving every conversation.
After this lesson: You've built every primitive — flow, choices, variables, functions, integration, tags, and the two-way bridge. This capstone adds almost no new syntax. Instead it answers the question a real game forces: where does the state live, and how do hundreds of story files share it without turning into spaghetti? The answer, drawn from Esoteric Ebb (286 stories, 500K words), is three patterns you already have the pieces for.

The Scaling Problem

One story is easy. A hundred is an architecture problem. When the blacksmith needs to know the player insulted the mayor in a different conversation yesterday, where does that fact live? The tempting answer — store it inside the blacksmith's ink file — collapses the moment a second file needs the same fact. Ebb ships 286 story files and about 1,800 shared variables; the patterns below are how they stay coherent.

The through-line is one idea: ink is not the game — it's a narrative layer the engine drives. Durable world state lives in the host engine; each ink file is a stateless view onto it. That single boundary decision is what the three patterns implement.

Pattern 1: State-Bus Variables

Instead of separate systems for quests, factions, and inventory, a production ink game often uses one flat namespace of variables as a shared state bus. Any file can write a flag; any file can read it. You already know the mechanism — it's just VAR from lesson 03, used as a communication channel rather than local bookkeeping:

VAR asked_name = false

=== ask_name ===
"Name's Mara," the keeper says.
~ asked_name = true
-> tavern

A different topic — even a different file in the full game — reads that same flag to change what it offers:

+ {asked_name} [Greet her by name] -> greet

One flag set in one place, read in another. In Ebb a variable like Snell_helped set in a single scene is read by more than half the game's other files — a cheap mesh of reactivity with no bespoke quest system. The whole "state" is just named booleans and integers on the bus.

Pattern 2: Stateless-Per-Dialog

Here's the pattern that surprises people: a production game often doesn't let ink own the save. It doesn't call get_state() to persist a conversation. Instead the engine keeps the state-bus variables in its own store, and for each conversation it creates a fresh InkPlayer and pushes the current values in with set_variable before the first line:

# Engine owns the bus. Each dialog starts fresh and is seeded from it.
for key in game_state.flags:
    _ink_player.set_variable(key, game_state.flags[key])
# ...run the dialog...
# On exit, harvest anything the story changed back into the engine:
for key in game_state.flags:
    game_state.flags[key] = _ink_player.get_variable(key)

Why give up ink's built-in save? Because it makes every dialog enterable in any order, keeps saves a flat list of flags (trivial to patch when you ship an update), and means no single ink file is the source of truth. This is the direct payoff of lesson 07's bridge: get_variable/set_variable are the seam between the story and the engine's durable state.

Trade-off — no mid-conversation save: because state syncs at dialog boundaries, you can't save halfway through a single conversation. Production games accept this: conversations are short, and the flat, order-independent save is worth far more than resuming mid-sentence. If you need mid-conversation resume, use lesson 07's get_state() instead — but you lose the flat-save benefit.

Pattern 3: Hub-and-Spoke

How does one player script drive 286 different conversations? Because they all share one shape: a hub-and-spoke loop. The hub is a re-enterable knot listing topics; each topic (spoke) does its bit and diverts back to the hub; one choice exits. The player's job is the same two-phase loop from lesson 06 — drain the lines, render the choices — running until the player leaves:

=== tavern ===          // the hub
The tavern is warm and loud. # speaker: Narrator
+ [Ask the keeper's name] -> ask_name
+ {asked_name} [Greet her by name] -> greet
+ [Leave] -> leave

=== ask_name ===        // a spoke: do something, divert BACK
"Name's Mara," the keeper says. # speaker: Mara
~ asked_name = true
-> tavern
Why divert back to the hub — never self-loop: a knot's read count reflects entry. Re-entering the hub by a fresh divert (spoke → hub) advances counts correctly and re-evaluates every choice condition, so gated content appears the moment its flag flips. This is the sticky-choice-and-gather discipline from lessons 02 and 04, now the backbone of the whole game. A knot that tried to loop on itself would freeze its own read count — the classic bug.

Here is the entire player. It is lesson 06's loop, unchanged — the architecture lives in the story, not the engine code:

# story_player.gd
# Production-patterns player for an ink story using the inkgd runtime.
# This is the SAME single-step drain loop from lessons 05-07 -- the capstone adds
# no new engine API. What changes is the STORY's architecture, not the player:
#   * Hub-and-spoke  -- the loop naturally drives a re-enterable hub: drain lines,
#                       render choices, pick one, drain again. One loop, any number
#                       of topics, visited in any order.
#   * State-bus VARs -- the story reads/writes a few flags (asked_name, helped_cook)
#                       to carry cross-topic state. In a real multi-story game you'd
#                       read them out with get_variable and push them into the NEXT
#                       story's fresh InkPlayer with set_variable -- that's the
#                       "stateless-per-dialog" pattern: durable state lives HERE, in
#                       the engine, not inside any one ink file.
#
# Node setup (attach this to a Control):
#   Control (this script)
#   +- SpeakerLabel     : Label          -- who is speaking
#   +- TextLabel        : RichTextLabel   -- story text (BBCode enabled)
#   +- ChoicesContainer : VBoxContainer   -- choice buttons appear here
extends Control

var InkPlayerFactory := preload("res://addons/inkgd/ink_player_factory.gd") as GDScript

var _ink_player = null

@onready var _speaker_label: Label = $SpeakerLabel
@onready var _text_label: RichTextLabel = $TextLabel
@onready var _choices_container: VBoxContainer = $ChoicesContainer


func _ready():
	_ink_player = InkPlayerFactory.create()
	_ink_player.loads_in_background = false
	add_child(_ink_player)

	_ink_player.ink_file = load("res://stories/08_production_patterns.ink.json")
	_ink_player.connect("loaded", Callable(self, "_on_story_loaded"))
	call_deferred("_create_story")


func _create_story():
	_ink_player.create_story()


func _on_story_loaded(successfully: bool):
	if not successfully:
		_text_label.text = "[color=red]ERROR: Story failed to load.[/color]"
		return
	_advance_story()


# Phase 1 of the hub loop: drain every available line (single-step, so per-line
# tags survive -- the lesson 06 rule). Phase 2 (render choices) happens when the
# drain stops at a choice point.
func _advance_story():
	while _ink_player.can_continue:
		var text = _ink_player.continue_story()
		var show_line = _process_tags(_ink_player.current_tags)
		if show_line and text.strip_edges() != "":
			_text_label.text += text

	if _ink_player.has_choices:
		_show_choices()


func _process_tags(tags: Array) -> bool:
	var show_line := true
	for tag in tags:
		var parts = (tag as String).split(":", false, 1)
		var key = parts[0].strip_edges()
		var value = parts[1].strip_edges() if parts.size() > 1 else ""
		match key:
			"speaker":
				_speaker_label.text = value
			"hidden":
				show_line = false
			_:
				pass
	return show_line


# Read a state-bus flag out of the story -- this is how a real game would harvest
# ink's variables to persist them (get_variable) and later push them into the next
# dialog's fresh InkPlayer (set_variable). Shown here for the harness/demo.
func read_flag(name: String):
	return _ink_player.get_variable(name)


func _show_choices():
	for child in _choices_container.get_children():
		child.queue_free()

	var choices = _ink_player.current_choices
	for i in range(choices.size()):
		var btn = Button.new()
		btn.text = choices[i].text
		btn.connect("pressed", Callable(self, "_on_choice_selected").bind(i))
		_choices_container.add_child(btn)


func _on_choice_selected(index: int):
	for child in _choices_container.get_children():
		child.queue_free()
	_ink_player.choose_choice_index(index)
	_advance_story()

The Payoff: Combat as Dialog

Once you have these three patterns, something surprising falls out: you don't need a separate combat system. Ebb runs combat inside ink using the exact same machinery. A turn is a hub; the player's actions are choices; the resolution is a tag the engine acts on. Ink never sees the dice — it emits the intent and reads the result back off the bus on the next entry:

=== attack_turn ===
+ [Swing the axe] -> resolve_axe
+ {has_spell} [Cast ember] -> resolve_ember

=== resolve_axe ===
You swing. # hploss: 2d6      // engine rolls, writes the result to the bus
-> attack_turn                // back to the hub for the next turn

Choices are actions, tags are resolution, a state-bus variable tracks whose turn it is — combat is just a conversation with the world. Four encounters in Ebb are authored exactly like dialog, with no bespoke combat code. That is the whole point of the architecture: once the boundary is right, new systems are content, not engineering.

Note — determinism: real combat rolls dice, so its output changes every run. This lesson's reference story stays deterministic (no RANDOM) so it can be regression-tested with a golden transcript. In a shipped game the roll happens in the engine (behind the hploss tag), and ink reads the outcome back off the bus — keeping the story itself deterministic and the randomness in one testable place.

Check Your Understanding

Exercise: You're building a game with a blacksmith, a mayor, and a tavern keeper in three separate ink files. Requirements:

  • If the player insulted the mayor, the blacksmith is cold to them in a later, separate conversation.
  • Each conversation is a menu of topics the player works through in any order.
  • The player can quit between conversations and resume.

A teammate proposes storing the "insulted the mayor" fact inside mayor.ink as a read count, and having smith.ink check it. It compiles, but it doesn't work — the blacksmith never reacts. For each requirement, name the pattern that handles it, and explain why the teammate's approach fails.

Hint

Which file "owns" the insulted fact in their design? When smith.ink runs as its own fresh story, can it see a read count that lives inside a different story file?

Answer

Requirement → pattern: the cross-conversation memory is a state-bus variable (VAR mayor_insulted) that mayor.ink writes and smith.ink reads; the menu-in-any-order is hub-and-spoke; quit-and-resume is stateless-per-dialog — the engine owns the flags and reseeds each fresh story.

Why the teammate's approach fails: a read count inside mayor.ink is local to that story instance. When smith.ink runs, it's a different, freshly-created story that has never entered mayor.ink's knots — so the count it checks is always zero. They tried to make one ink file own world state, but ink files are stateless views; durable facts have to live on the bus, in the engine, where every story can be seeded from them.

Key insight: ink is not the game. The story is a narrative layer; the engine owns the durable state. The moment a fact must outlive or cross a single conversation, it belongs on the state bus — not inside any one .ink file.
